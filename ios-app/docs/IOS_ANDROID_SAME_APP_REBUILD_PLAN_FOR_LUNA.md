### B. 不再循环等待的阶段依赖

P0–P6 是责任域和验收阶段，不是每个阶段所有条件都必须先完成、下一阶段才能写一行代码的全局锁。

| 门禁 | 负责什么 | 未通过时阻止什么 | 可以继续什么 |
|---|---|---|---|
| P0-DEV：批次开发准入 | 明确双端 SHA/基线差异、目标真实入口、fixture/时钟、改前证据、保护数据范围与回退点 | 无可信入口/数据却宣称对齐；从混乱基线大面积移植 | 已有可信基线覆盖的局部实现、测试和候选代码；必须标明尚未最终验收 |
| P0-DATA：数据安全 | 旧模型来源、升级/恢复样本、附件和失败回滚合同；由 P3 实现恢复闭环，所有 schema 变更批次提前证明安全 | 未证明升级安全的 schema 变更合入；在唯一用户数据上试恢复；宣称数据兼容 | 不改 schema/存储格式的 UI 工作、隔离样本上的迁移开发 |
| P0-DEVICE：设备可行性 | 用户环境、侧载方向、包变体、身份映射、签名和扩展限制风险 | 把 unsigned IPA 或模拟器成功当成真机交付 | 不需要用户凭据的编译、模拟器、UI和规则开发；早期装机试验与 P1/P2 并行 |
| P1–P5：功能合同关闭 | 各自页面、业务与交互证据；共同组件回归归修改它的批次负责 | 本批未关闭却报功能完成；已知回归转移给下一阶段 | 非依赖项的只读审计、测试设计；最多另准备一个不重叠候选批次 |
| P6：交付关闭 | 同一个集成候选上的全部必需证据、真实设备和可恢复交付 | 全量完成、可安装正式交付、上架等结论 | 如实交付带限制的开发预览，不能因此减去原有产品目标 |

P0 总状态仍保持 PARTIAL，直到原开放项被逐项验证、映射并同步合同；P0-DEV 是新增的人工准入判据，**目前不是 CI 已实现的状态字段**。允许准入不等于 P0 完成。数据升级缺口和设备限制不得被改名后消失，最终仍在 P6 复验。

### C. 母版冻结与增量追踪

1. 区分三个身份：**线上 APK**（版本/公告/下载哈希）、**源码快照**（干净 SHA，若含未提交修改须先安全保全并形成可审计快照）、**截图构建**（实际构建 SHA、fixture 与构建配置）。版本号相同不证明三者一致。
2. 当前 312 公告和本地 APK 是母版候选依据；先核对已发布源码、用户认可的产品状态、308→312 有效变化。不得 reset 主目录、把脏树全复制到 iOS 工作树，或擅自发布/重新打包安卓。
3. 每批冻结一个已记录的 Android 参考版本和一个 iOS 候选 SHA。不同平台不要求 SHA 字面相同；要求来源关系、差异与任务范围明确。跨批次复用旧图必须证明对应源码、资源、配置、fixture 未变，否则标为“历史参考”并补采。
4. 新 Android 版本进入“增量差异队列”：列功能、UI、业务规则、资源、数据格式、安全修复及对应文件。安全/账务正确性变化优先；其他变化在批次边界升级母版，避免移动目标导致无限返工。最终候选前必须清空用户要求范围内的未决差异。
5. Android 是产品基线，不要求复制已证实的金额错误、数据丢失或安全缺陷。发现母版缺陷时建立最小复现和双方当前结果，登记问题并确认正确规则；不能悄悄改 iOS 口径或硬编码错误期望值来“通过对账”。

### D. 统一状态和完成定义

页面/能力台账至少记录以下相互独立字段，不再用一个“已完成”同时表示有代码、截图成功和真机通过：

| 字段 | 允许值/内容 |
|---|---|
| `implementation` | missing / partial / implemented / blocked；blocked 必须写外部条件和解除方式 |
| `buildTests`、`visual`、`interaction`、`dataSafety`、`device` | not-run / running / pass / fail / not-applicable；N/A 必须给理由 |
| `integration` | local / pushed / integrated；提交推送不是阶段验收 |
| `identity` | 功能 ID、唯一主责阶段、Android/iOS SHA、fixture ID/hash、OS/Xcode/runtime、包变体 |
| `evidence` | run ID、命令与退出码、测试数量、原图/JSON/日志路径与哈希、人工复核结论 |
| `remaining` | 本批缺陷、后续合同 ID、接受的平台差异、阻塞条件、下一步 |

状态演进：代码实现 → 构建/测试通过 → 原图和字段核对 → 真实交互与持久化验证 → 集成回归 → 所需真机验证。只有某功能适用的门禁均通过才写“功能验收通过”；某阶段所有必需功能和门禁通过才关闭阶段。41 个静态场景和 12 条旅程是范围，不是完成分母，不报无可审计分母的整体百分比。

“本批缺陷为 0”指无未处置的阻断缺陷、无新增回归、无已约定合同偏差，不是保证软件数学意义绝无 bug。非阻断观察可以登记但不得偷偷降标准；涉及金额、数据安全、主要入口、缺失操作的差异不能按美化项延期。若用户接受阶段性交付，必须列出限制，最终同款范围不随之缩减。

### E. 截图、交互、业务三条证据分别成立

- **截图证据**：同时保留 Android 母版、iOS 改前、iOS 改后原图及 sidecar；输出编号标注的并排图，多页面补联系图。截图来源不得跨 SHA 冒充；新增页面没有改前图时明确写“此前无目标页”，以缺失状态和旧入口证据替代，不伪造旧图。有 UI 的功能交付时必须把截图直接展示给用户，只有文件路径或“CI 已产图”不算完成这项沟通。
- **几何与视觉**：1080×1920 和 1260×2736 是当前采集配置，不是所有未来设备的固定分辨率。保留原图，另做保持比例的内容宽度归一化；状态栏/安全区单独说明，不拉伸、不裁掉失败内容。`dimension_mismatch` 归为“未作视觉判断”，不得算 visual pass；正文/操作可见性、层级、数值和点击区域逐锚点人工复核。阈值只能辅助找回归，不能代替产品判断。
- **实际交互**：冷启动参数、demo 自动跳转只能证明目的页面可绘制。图例下钻必须真的点图例，返回必须真的返回，保存必须真的触发并跨重启查库；使用 XCUITest、可审计的模拟器交互或用户真机录像。长页面补滚动后的关键区域，不能只交首屏。系统权限/真实 OAuth/扩展不能用 demo 路由替代。
- **业务对账**：保留原始 JSON 和规范化 JSON。只按显式白名单将 `platform` 等来源信息移到 provenance 区，仍验证其平台值；金额、币种、日期、主键、关联、缺字段、未知字段不得被通用 ignore 丢弃。对平台差异通过、金额/日期/实体改动失败分别加测试；没有输出的领域标“未覆盖”，不能算相等。
- **计算规则**：金额用 Decimal/整数分语义，明确舍入时机；净额、全退笔数、独立调整、预算和账户余额分别对账。日期按合同固定时区/日历，含结束日整天，覆盖跨月、闰年和周期端点；不要用统一 86400 秒替代全部日历加天逻辑。AI 文本和动画等非确定输出验语义/状态/结构，不要求字面或像素完全相同。
- **证据归档**：建议长期目录为工作区外独立存储或经用户同意的持久目录，组织成 `<batch>/<platform>/<sha>/<run>/`，附 manifest、哈希、原图、字段 JSON、日志摘要及结论；当前 `.tmp` 仅作临时缓存。生成物不自动进 Git。真实账本、备份、凭据不传公开 Actions Artifact；公共证据只用合成 fixture，授权真实样本需脱敏和访问控制。

### F. 用户环境与早期安装验证

已知条件：Windows、无自有 Mac、无付费 Apple Developer Program、iPhone Air、用户报告 iOS 27 预览版。测试前记录实际系统完整 build，不能自行推断 beta 版本、更新手机系统、要求购买设备/账号或把凭据交给代理。

| 路径 | 可以证明什么 | 必须另外证明什么 |
|---|---|---|
| GitHub macOS CI | Swift/Xcode 编译、核心与 App 测试、所用 runtime 的模拟器截图、设备架构 unsigned IPA | 不证明签名有效、iOS 27 真机兼容、Windows 重签或安装成功 |
| Windows 侧载候选 | 用用户自己的 Apple Account，在用户本机尝试受支持工具的签名/安装；优先小范围可逆试验 | 工具当前版本与手机 build 兼容性、签名后身份/entitlements、启动、重签续期、升级保留数据 |
| 无扩展兜底包 | 受限签名条件下验证 App 主路径的候选；仓库已配置单独构建 | 移除扩展/清空 entitlements 后 App Group、Keychain、store URL 是否变化；不得算 Widget/Share 已通过 |

Apple 官方 Personal Team 说明适用于其 Xcode 管理的个人设备测试，并存在 7 天 provisioning 等限制；不能直接推导第三方重签工具的所有功能。AltStore 官方提供 Windows 安装说明，故不能把“用户必须有 Mac”写成唯一通路；也不能据此保证当前 iOS 27 预览版和肥喵完整扩展可用。依据：[Apple 账号/Personal Team](https://developer.apple.com/help/account/basics/about-your-developer-account)、[AltStore Windows 说明](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows)（本次核查 2026-09-23，执行安装前再次核对）。

早期设备试验最小链：用户同意并自行输入凭据 → 下载与核验候选 IPA → 重签并检查实际 Bundle ID/Team/App Group → 安装与冷启动 → 创建合成账目 → 重启保留 → 导出恢复点 → 同身份更新/续签后复查。失败时保留错误、签名元数据和已脱敏日志；不让用户先卸载唯一有数据的 App。改 Bundle ID/签名 Team/包变体可能成为不同安装身份，不能承诺覆盖升级；先设计并实测迁移路径。

首次可安装预览应尽早尝试，不必等 P5 做完；但它必须标明扩展、AI、后台和数据兼容限制。TestFlight/App Store 是另需用户选择和条件的分发项目，不默认加入本轮。安装流程只有在目标设备实际走通后才标“已验证”，此前为试验步骤。

### G. CI 与批次节奏

1. Windows 先做 diff、Python 合同/工具定向检查；SwiftUI/Xcode 无本地等效验证，不假装通过。
2. 无关文档修改不触发整套 App 构建。代码批次只触发一次适用 CI；若工作流只支持全量，诚实使用现有流程，不写不存在的参数。未来可增加“快速核心/App tests＋目标截图”和集成全量层，但必须先实现且不得以快速层替代最终矩阵。
3. 每个 run 绑定固定 SHA；失败按编译、测试、采集、上传、对账分类，读最窄日志找根因。无证据不连续重试；新代码需新 SHA 的验证。不得降阈值、删断言或用旧图补数。
4. 默认最多一个未视觉封板的 UI 批次在开发；现有周、月两批先收口。等待外部 CI 时可读代码/设计测试，不继续在共享组件上堆三四批未经视觉核验的修改。用户明确要求并行时记录依赖与最后统一回归范围。
5. 用户已拒绝每 15 分钟的后台查询：不建自动轮询/提醒，不高频重复读取无变化状态。收到用户结果通知后查一次，失败再取必要日志；运行中如无其他有价值工作，说明等待项并交还，不通过反复报“仍运行”消耗 token。
6. 在早期统计增量中用到的 `f872e3e`、`436c94d`、`32876ec` 都保留精确范围；公共 mini-card、颜色、格式等变化影响多个统计维度时，周/月/年/自定义均列入回归，而不是只验当前截图。

## 0. 结论先行

用户目标只有一个：**iOS 版就是现有 Android「肥喵记账」在 Apple 平台上的原生实现，不是重新设计的新记账软件。**

当前 iOS 不是“功能全无”，真正的问题是：仓库同时存在两套 iOS 方向，截图证据又混用了不同提交、不同日期和不同页面。结果是部分业务能力已经很多，但入口、页面骨架、品牌组件和首屏信息经常按“通用 SwiftUI App”重新组织，用户自然会觉得它是另一款软件。

本方案的核心决策如下：

1. **Android 当前生产 App 是唯一产品母版。**入口、信息层级、页面顺序、字段、文案语义、品牌素材和业务结果均以 Android 为准。
2. **保留功能更完整的 `ios-app/QingJi` 作为生产功能主干。**它已有 SwiftData、核心账务、预算、资产、AI、OAuth、备份、Widget、Share Extension、App Intents 等大量能力。
3. **不得把 `ios-app/FeiMiao` 整套替换为生产 App。**该分支基于较旧的 Android `1.197.0+199`，使用另一套 GRDB 数据层、Bundle ID、版本线和工程目标，只完成批次 1–5；整套切换会造成已完成业务能力大幅倒退，并形成第二款 App。
4. **只审计性移植 `FeiMiao` 中有价值的同款 UI。**可以移植品牌素材、主题 token、推开式抽屉、首页汇总卡、筛选、按日卡、底部记账入口、按压反馈等；不得移植它的 `AppStore`、`FeiMiaoKit`、GRDB 数据库、`project.yml`、Bundle ID 和版本线。
5. **先满足本批 P0-DEV 准入，再按“壳层 → 核心记账 → 业务管理 → 资产 → AI/系统 → 全量交付”推进。**数据安全与设备可行性按当前入口 B/F 节并行；缺证据只阻止它所影响的结论和操作，不把全项目永久锁死。每批最多一个完整用户链或 2–4 个紧密页面，按 D 节分别记录实现、测试、视觉、交互和集成。

这不是“像素复制 Android”。iOS 可以保留状态栏、安全区、系统键盘、日期选择器、照片/文件选择器、触觉、VoiceOver、侧滑返回和系统权限弹窗；但这些原生能力不能改变页面身份、入口层级、字段顺序或业务结果。

### 0.1 复盘后的可执行性结论

原始版本存在四个会阻碍交付的问题：P0 与后续业务阶段循环依赖、多个场景没有唯一主责阶段、缺少已有 iOS 数据升级合同、发布门禁偏向截图和构建而缺少完整用户旅程。本文已按以下原则修订：

- P0 只关闭“母版、工程起点、页面身份、固定时钟、fixture、metadata 和验收合同”，不要求尚未实现的 P1–P5 页面在 P0 先变成同款；
- 每个场景只有一个主责阶段，P0 只负责取证，P6 统一复验；
- 每批只要求本批范围内缺陷为 0，后续计划项必须有阶段归属，禁止用“以后再说”掩盖回归；

**按修订后的计划完整执行并通过 P6，可以做成真正的 iOS 版肥喵；只做到截图相似、模拟器可运行或 CI 出 IPA，仍不算完成。**

## 2. “同一款 App”的强制合同

### 2.1 必须完全一致

以下内容不属于平台适配，必须与 Android 一致：

- 根信息架构：主页 + 左侧推开式抽屉，不增加五栏 Tab，不另造第二套首页；
- 每个入口的名称、位置、层级和目标页面；
- 页面首屏的信息顺序、主要卡片、主要操作和空态含义；
- 支出/收入/转账、账本、账户、分类、标签、日期、备注、附件、待报销、不计入等字段；
- 金额精度、符号、正负、净额、退款/报销归属、余额、预算、统计和净资产口径；
- Android 已有的肥喵 Logo、猫咪、分类图标、账本封面、暖色背景和语义色；
- 正常、空态、错误、取消、重复提交、删除/撤销后的可见结果；
- 设置项默认值和持久化结果；
- 同一输入产生的数据库、文件、任务或网络状态变化。

### 2.2 可以 iOS 原生化

允许不同，但不得改变产品任务的内容：

- iPhone 状态栏、Dynamic Island、安全区；
- 系统键盘、日期/时间选择器、PhotosPicker、文件选择器；
- 按压动画、触觉、侧滑返回、sheet 转场；
- VoiceOver、Dynamic Type、Reduce Motion、深色模式；
- 系统权限申请、通知和分享面板；
- iOS 无法读取第三方 App 通知、无法自替换二进制、后台定时不保证精确时刻等硬限制。

### 2.3 明确禁止

- 用 `Form` / `List` / 大标题导航把 Android 的工作台页面改成另一套信息架构；这些 SwiftUI 控件本身不禁用，只要信息顺序、密度、品牌、可达操作和无障碍合同一致即可；
- 因为“iOS 原生”而删除、合并、改名或移动 Android 入口；
- 用 SF Symbol 替代肥喵 Logo、猫咪、账本封面或分类品牌图标；
- 用一张静态页面或 mock 数据假装功能闭环；
- 用相近页面、资产资金 tab 或首页截图替代目标页面；
- 先大面积重写再补测试和截图；
- 同时维护 `QingJi` 与 `FeiMiao` 两个生产数据层和两个 Bundle ID；

## 3. 历史差异诊断（2026-09-02，逐项重验后才进入当前缺陷台账）

### 3.1 根壳层

Android 的产品身份来自“主页 + 跟手推开式抽屉 + 暖色连续背景 + 自绘圆形/胶囊控件”。当前 `QingJi` 已有抽屉，但仍更像覆盖式 iOS 面板，页面之间大量回到系统 NavigationStack、Section 和白卡列表。需要统一为同一套肥喵壳层，而不是每页各自决定风格。

### 3.2 页面骨架

最明显的差异不是字号，而是信息顺序：

- 统计：Android 以“大总额卡 + 两个摘要卡 + 洞察/环图/趋势/排行”的可管理卡片序列为中心；iOS 常改成“三个小指标 + 环图 + 系统图表”的另一套仪表盘；
- 预算：Android 是计划查看/切换/进度/分类额度的管理页；iOS 截图更接近单个“月度预算”编辑表单；
- 资产/净资产：Android 使用一个资产管理 hub 的“总览/资金/物品”层级；iOS 把账户、负债、净资产拆成多个独立系统列表；
- 设置：Android 是可关闭的半屏/全屏设置面板并保留头像、分组和业务入口；iOS 是标准 push 设置页；
- AI 设置：Android 是完整 AI 能力总入口；iOS 当前截图只突出账号与迁移，层级明显缺失。

### 3.3 组件语言

Android 已形成稳定组件语言：暖橙到奶白背景、半透明暖白卡、低饱和蓝灰主色、铜金收入、柔和橙警示、预算健康绿、48dp 圆/胶囊操作、发丝线、连续圆角、肥喵空态和分类彩色图标。

当前 iOS 虽有暖色背景，但仍大量使用系统蓝、纯白卡、标准 Toggle、默认 Section 间距和 SF Symbol，造成“品牌背景上放了另一款 iOS App”的感觉。应建立单一 token 和组件库，所有业务页只消费组件，不再各自手搓。

### 3.4 数据与状态

当前还存在同款体验无法靠视觉修复的问题：

- 逻辑日期未真正锁住，月份、持有天数、报销到账日期漂移；

### 5.2 从 `FeiMiao` 分支可移植的内容

每一项先与当前 Android（不是 1.197 旧基线）复核，再移植到 `QingJi`：

- `FeiMiao/App/AppStore.swift`；
- `FeiMiaoKit/FeiMiaoData`、GRDB schema 和仓储；
- `FeiMiaoKit/AndroidBackupImporter`；
- `FeiMiao/project.yml`、`com.feimiao.app`、版本 `0.2.0`；
- 旧 Android v40 的页面/功能假设；
- 任何会丢失现有 AI、预算、资产、扩展、备份或迁移能力的重写。

### 5.4 分支整合策略

- 优先续接已核实的 `.tmp/repository-cleanup` / `codex/screenshot-stability`；先记录 HEAD、未提交改动及远端真实 SHA。只有明确需要隔离且已记录移交关系时才新建 worktree，不能每换模型重新开线。
- `main` 是最终集成主线，但其当前内容必须现场核对；不覆盖脏主目录、不整支合并历史候选。完成批次可在授权后精确提交推送，集成 main/PR/发布分别按用户授权执行。
- `0600683` 作为一个独立候选变更审计：测试和数据合同成立才 cherry-pick/重做，不把整个审计分支继续长期分叉；
- `FeiMiao` 只允许逐文件移植纯 UI/资产；移植文件不得引用 `FeiMiaoDomain`、`FeiMiaoData`、GRDB 或第二个 `AppStore`；
- `FeiMiao` worktree 中的未提交文件视为未审计个人工作，不直接消费；先由原作者提交或导出精确 diff，再决定采用；
- 每批提交必须可独立回退；禁止跨阶段大提交和“先整分支 merge 再修”。

### 5.5 建议的 UI 分层

在 `QingJi` 内建立统一层次，避免业务页直接散落系统默认样式：

### P3.6 数据安全验证的最小矩阵（与 P0-DATA 共用，不重复记完成数）

| 输入/故障 | 操作 | 必须保存的证据 |
|---|---|---|
| 旧 QingJi 实际 schema 的磁盘 store | 用旧提交模型建库并写入哨兵记录、关闭进程；目标提交在同一 URL 升级并再次写入/重启 | 源/目标模型版本、稳定 ID 与关系、数量、金额、附件字节哈希、store 路径；不能由目标模型生成所谓“旧库” |
| Android 当前 DB、v48、v40 | 各自真实格式的合成/脱敏备份导入，核对主外键与完整字段 | 格式版本/输入哈希/实体清单/未支持字段、统计与余额、退款关系；只验 JSON 往返不能覆盖原 SQLite ZIP |
| 损坏 manifest/hash、路径穿越或解压限额 | 在正式写库前拒绝 | 明确错误，原模型和附件完全不变，无越界文件，无敏感路径泄漏 |
| 中途数据库保存、附件安装失败 | 可控注入失败，再恢复/重开 | 恢复前后实体/关系/附件集合与哈希，旧文件未丢，本批临时文件不泄漏，不污染其他并发操作 |
| 重复导入、取消、崩溃重启 | 同输入第二次执行，或在关键阶段取消/中断 | 幂等策略、无重复落账、待确认状态可恢复；实际数据库读回，不只看 toast |

现有 `AppModelContainer` 仍使用 inferred Schema，并存在容器打开失败直接终止的路径；需要审计其真实升级能力。引入 `VersionedSchema` 不是改一个类型名即可完成：必须证明旧 schema 与新定义匹配，既有文件能打开，失败时不会清库重建。没有旧 store 实物时，用旧源码模型在隔离环境生成并注明来源，不声称覆盖未知历史版本。

回退分开验：代码 revert、旧包重签安装、数据兼容/恢复。新 schema 不一定能被旧二进制读取，所以“保留旧 IPA”不是数据回退方案；保留升级前可恢复的备份与附件，在副本上演练，不能用用户唯一数据试验。跨 Team/Bundle ID/扩展包变体亦须先备份并验证实际安装身份。

### P3 关闭门

## 7. Luna 每个小批次的固定工作法

Luna 每次只执行一个小批次，必须按以下顺序：

### 7.1 开工前

1. 读取 `AGENTS.md`、本方案、阶段合同和上一批复盘；
2. 检查精确分支、HEAD、工作区状态和并行 worktree；
3. 读取 Android 目标页面及其直接依赖组件；
4. 读取 `QingJi` 对应页面、Store 和测试；
5. 查看同提交、同 fixture 的 Android 原图和 iOS 改前图；
6. 写出本批“必须相同 / 允许不同 / 不在本批”三栏；
7. 若本批截图或路由证据错误，先修本批取证；其余无依赖的只读审计/测试设计可以继续，不凭猜测完成对齐、不因为旧全局 marker 重新做已通过的工作。

### 7.2 实施中

- 先改公共组件，再改页面；
- View 只绑定现有 Store，不另建第二套数据模型；
- Android 合同需要现有 `QingJi` 缺失字段/状态时，在 `QingJiCore`/SwiftData/现有 Store 中增量实现并提供迁移测试；“不建第二套模型”不等于禁止完善唯一模型；
- 不修改稳定分类 key、UUID、退款家族、备份 schema 和 OAuth 安全边界来迁就 UI；
- 不使用假数据填充生产页面；demo fixture 只在明确的截图环境开启；
- 不触碰 Android 无关改动；
- 不做整分支 merge；从 `FeiMiao` 只移植经审计的文件/逻辑；
- 每 2–4 个紧密页面或一个完整操作链形成单独提交。

## 9. 最终判断标准

完成后，用户不需要理解“SwiftUI 原生适配”才能认出它。打开 iOS 肥喵时，应当立即看到与 Android 相同的品牌、主页、抽屉、记账入口、账单卡、统计层级、预算、资产和 AI 入口；在相同数据下得到相同金额和状态；换成 iPhone 后，只感受到更自然的键盘、触觉、安全区、权限和系统集成，而不是换了一款软件。

最终交付结论分为以下两类；开发过程使用当前入口 H 节四级里程碑，不能抹去真实的阶段性进展：

- **可以称为真正的 iOS 版**：P0–P6 全部关闭，规范化后的全部页面合同和新增操作状态通过，12 条黄金旅程通过，已有 iOS 数据升级和 Android 备份恢复无丢失，真实 OAuth/扩展/权限在真机运行，选定分发方式真实安装或上传成功且可回退；
- **仍是开发预览版**：上述任一项未验证、用 mock/静态图替代、存在第二数据真相、只出 unsigned IPA、或页面相似但业务副作用不同。
