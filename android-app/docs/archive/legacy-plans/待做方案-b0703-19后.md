## ① 统计卡真懒加载

### 问题
`views/statistics/statistics_view.dart` 的 `_ManagedCards.build`（~588-628 行）用的是
`ReorderableListView(children: [...])`，**把所有可见卡一次性全部 layout+paint**，
包括屏幕外看不到的（每张卡里有 fl_chart，离屏也在算 layout/paint）→ 统计页首次打开
和滚动时容易掉帧。

### 改法
换成 `ReorderableListView.builder`，只 layout 当前视口内的卡；离屏的滚到才建。

关键点：
1. `visible = visibleKeys(repo)` 仍先算（廉价，只是一串 key）。
2. `items = <(String, Widget)>[]`：仍要过滤掉 `buildCard(k)==null`（该维度无数据的卡跳过但保留顺序）。
   - **注意**：`buildCard(k)` 返回的是 Widget **构造**（廉价），真正贵的是 fl_chart 的
     layout/paint（在渲染时才发生）。所以预先构造 `items` 里的 Widget 对象没问题，
     `.builder` 负责让离屏的**不 layout**——省的就是这部分。
3. `ReorderableListView.builder(itemCount: items.length, itemBuilder: (c,i){...}, header: header,
   footer: _CustomizeButton(...), onReorder: 同现有, buildDefaultDragHandles: false)`。
4. itemBuilder 里返回和现在 children 一样的结构：
   ```dart
   ReorderableDelayedDragStartListener(
     key: ValueKey('stat_card_${items[i].$1}'),
     index: i,
     child: Padding(
       padding: const EdgeInsets.only(bottom: 16),
       child: RepaintBoundary(child: items[i].$2),
     ),
   )
   ```
5. `onReorder` 回调逻辑原样搬（`if (n>o) n--` 等）。

### 注意 / 坑
- `ReorderableListView.builder` 支持 `header`/`footer`/`onReorder`，签名和现有一致，改动很小。
- 现有 `onReorder` 已有 deprecated 警告（Flutter 3.41 后建议用 `onReorderItem`），**这次不动**，
  保持行为一致，避免引入新风险（warning 不阻断 CI）。
- 三个维度（月/周/年/自定义）都走同一个 `_ManagedCards`，改一处全生效。

### 验证
- 纯 UI/性能改动，难写单测；本地 `flutter analyze` 0 error + 手动滚统计页确认不掉帧、
  拖排序仍正常、图表库开关卡仍正常。

### 成本
低（一个类的 build 方法改造）。

## ④ 喵助手记账卡跨重启恢复

### 问题
`chat_messages` 表只存 `role/text/question/created_ms`（纯文本）。喵助手里的**记账明细卡**
（`_RecordMsg`，带「改分类」「删除」芯片的漂亮卡）在 `_restoreHistory`（ai_chat_panel.dart ~226）
**只认 user/answer/info_err/info 四种角色**，`record` 类根本没存也没恢复 → 关 App 再开，
记账卡消失（连带芯片、可操作性一起没了）。

### 目标
把**已保存的**记账卡结构化持久化，重启后重建 `_RecordMsg`，芯片（改分类/删除）继续可用。

### 数据模型（不动 schema，复用 text 列存 JSON）
- 新增角色 `role='record'`，把结构化数据 JSON 序列化后存进现有 `text` 列（避免 DB 迁移）。
- 每张记账卡持久化字段（来自 `_RecordMsg`，ai_chat_panel.dart ~994）：
  - `entries`: List<ParsedEntry> → 每条存 `{amount(字符串/null), kind(json), categoryKey, note, date(ms), confidence}`
    - ParsedEntry 字段见 `natural_language_entry_parser.dart:7`（amount Decimal?/kind/categoryKey/note/date/confidence）。
  - `cats`: List<CategoryEntity?> → 每条存 **categoryId**（int?，null 表示未认出/占位）。恢复时用 `repo.categories` 按 id 查回。
  - `saved`(bool)、`txnIds`(List<int?>)、`savedFeedback`(String)、`deletedIdx`(List<int>)。
- JSON 顶层示例：
  ```json
  {"saved":true,"feedback":"...","deleted":[1],
   "entries":[{"amt":"23.88","kind":"expense","catId":42,"note":"烧烤","date":1720051200000,"txnId":1001,"conf":0.95}]}
  ```
  （把 cats 的 catId、txnIds 的 txnId 并进每条 entry，读写更顺手。）

### repo 层新增/改动（app_repository.dart）
- `addChatRecordMessage(String json)`：insert role='record'、text=json，**返回新行 id**（供之后 update）。
  - 现有 `addChatMessage` 不返回 id（~1200）；新方法要 `return await _db!.insert(...)`。
- `updateChatRecordMessage(int rowId, String json)`：`_db!.update('chat_messages', {'text':json}, where:'id=?')`。
  - 供「改分类」「删除条目」后把最新状态写回。
- `loadChatMessages` 原样（已返回全部行含 record）。

### ai_chat_panel.dart 改动
1. `_RecordMsg` 加一个可空字段 `int? chatRowId`（持久化行 id，运行时用来 update；不进 JSON）。
   `deletedIdx` 已是运行时 Set，恢复时从 JSON 灌回。
2. **写入时机**：在 `_save`（~484）保存成功、`setState` 里 `msg.saved=true` 之后，
   序列化 msg → `chatRowId = await repo.addChatRecordMessage(json)`，存到 msg。
   - 决策：**只持久化已保存的卡**（pending 未保存的卡不跨重启——和「你没存」的语义一致，且省去重跑解析）。
3. **改分类**（`_pickCategory` ~558）、**删除条目**（`_deleteEntry` ~604）成功后：
   若 `msg.chatRowId != null` → 重新序列化 → `repo.updateChatRecordMessage(msg.chatRowId!, json)`。
4. **恢复时**（`_restoreHistory` ~226）：`role=='record'` 分支 → `jsonDecode(text)` →
   重建 `_RecordMsg`（entries/cats 用 repo 按 catId 查回、saved/txnIds/savedFeedback/deletedIdx 灌回、
   chatRowId=行 id）→ 加入 `_chatHistory`。
   - 边界：catId/txnId 指向的分类/账单可能已被删 → 查不到就 cat=null（卡仍显示，改分类时重新选即可）；
     改分类调用 `repo.setTransactionCategory(txnId)`，txn 已删则 no-op（可加 existence 检查，非必须）。

### 序列化 helper
- 在 ai_chat_panel.dart 内加私有 `_recordToJson(_RecordMsg)` / `_recordFromJson(Map, repo)`，
  不动 core 模型（ParsedEntry 不必加 toJson，避免污染核心）。
- Decimal 用 `.toString()` / `Decimal.parse`；kind 用 `TransactionKind.toJson()` / 反解；date 用 ms。

### 验证
- 加一个纯逻辑单测：构造一个 `_RecordMsg` → `_recordToJson` → `_recordFromJson` → 断言
  entries/amount/kind/note/date/catId/txnId/saved/deletedIdx 往返一致。
  （helper 若放私有类里不好测，可抽成顶层函数或 `@visibleForTesting`。）
- 手动：记一笔 → 杀 App 重开 → 记账卡还在、芯片能改分类/删除。

### 成本
中等（repo 两个方法 + panel 序列化/恢复/三处写回 + 一个往返测试）。

### 注意 / 坑
- `_pruneChatMessages` 按 `created_ms` 清理超期 → record 卡也会被超期清理，符合预期。
- 只存已保存卡：确认中的 pending 卡重启后消失，是刻意取舍（不重跑 AI 解析）。
- 别把 `deletedIdx` 当运行时丢了——要进 JSON，否则重启后已删条目复活。
