# 肥喵记账：资产管理、定时记账、自动记账、会员体系执行蓝图

> 目标：把“想法”拆成 Claude 或人工可以直接执行的产品/技术任务。  
> 说明：外部没有检索到足够可靠的“有数”公开功能资料，因此这里不假装复刻某个具体 App，而是按成熟个人资产管理产品的通用模型，结合肥喵当前代码现状设计。

## 1. 当前基线

当前已有能力：

- `accounts` 表已有账户名称、币种、软删除。
- 交易已带 `account_id` / `to_account_id`，转账已能区分转出和转入账户。
- 已有 `AccountBalanceCalculator`，能按交易计算账户账面余额。
- `AccountsView` 当前只是账户管理：新增、改名、删除，标题已是“资产管理”。
- `recurring_rules` 已有定时记账基础能力：金额、分类、账户、周期、启停、下次执行。
- 自动记账已有通知监听服务、通知队列、通知解析、授权入口。

当前缺口：

- 账户没有类型、期初余额、信用额度、账单日、还款日、是否计入净资产。
- 没有资产快照，无法做净资产趋势和对账。
- 信用卡、贷款、投资账户没有独立语义。
- 定时记账缺少“待确认/仅提醒/跳过本期/顺延/结束日期”等控制。
- 自动记账还是粗筛通知，缺少候选池、置信度、撤销、规则记忆和异常处理。
- 会员体系没有服务端账户、权益表、额度消耗记录和支付回调。

## 2. 资产管理执行方案

### 2.1 P0：账户从“名字列表”升级成“资产账户”

数据库迁移：

- `accounts.account_type`：`cash`、`debit_card`、`credit_card`、`payment`、`investment`、`loan`、`receivable`、`other`。
- `accounts.opening_balance`：期初余额，默认 `0`。
- `accounts.include_in_net_worth`：是否计入净资产，默认 `1`。
- `accounts.institution`：银行/平台。
- `accounts.credit_limit`：信用额度，信用卡可用。
- `accounts.billing_day` / `repayment_day`：信用卡/贷款提醒。
- `accounts.sort_order`：用户排序。

页面：

- 资产首页：
  - 顶部主指标：净资产。
  - 次指标：资产、负债、本月净变化。
  - 账户分组：现金/银行卡/支付/信用卡/贷款/投资。
  - 每个账户显示：账户名、余额、较上次快照变化。
- 新增/编辑账户：
  - 半屏 sheet，左上关闭，中间标题，右上保存。
  - 类型用图标网格，不用下拉列表。
  - 余额、是否计入净资产、账单日/还款日按类型动态出现。

验收：

- 新建现金账户，期初余额 100，净资产增加 100。
- 支出 20 后，该账户余额显示 80。
- 信用卡消费 50 时，负债增加 50，净资产减少 50。
- 删除账户不删除历史交易，历史交易仍显示旧账户名。

### 2.2 P1：资产快照和净资产趋势

新增表：

- `asset_snapshots`
  - `id`
  - `account_id`
  - `snapshot_date`
  - `balance`
  - `source`：manual / transaction / import / adjustment
  - `created_ms`

逻辑：

- 每次交易保存后，更新受影响账户当天快照。
- 用户可手动“对账”：输入当前真实余额，生成 adjustment 快照。
- 趋势图优先使用快照；无快照时用期初余额 + 交易推导。

页面：

- 账户详情：
  - 当前余额。
  - 近 30 天余额趋势。
  - 近期交易。
  - “调账/对账”按钮。

验收：

- 用户手动调账不会进入收支统计。
- 账户趋势能显示调账点。
- 转账不会改变净资产，只改变账户结构。

### 2.3 P2：负债中心

能力：

- 信用卡、花呗、贷款统一归入负债。
- 展示本月应还、还款日倒计时、额度使用率。
- 支持还款交易：从现金/银行卡转到信用卡，减少负债，不计入支出。

验收：

- 信用卡消费不会被当作现金账户直接减少。
- 信用卡还款不进入支出统计。
- 还款日前可提醒。

### 2.4 P3：资产分析

指标：

- 净资产趋势。
- 资产结构：现金、支付账户、投资、应收。
- 负债结构：信用卡、贷款、其他。
- 流动性覆盖天数：现金类资产 / 近 30 天日均支出。
- 负债率：负债 / 资产。

UI 标准：

- 资产页不是统计页的复制品，要以“现在是否安全”为核心。
- 一个卡片只回答一个问题。
- 顶部最多 1 个主数字 + 2 个辅助数字。

## 3. 定时记账优化方案

### 3.1 当前问题

- 规则创建后缺少未来日期预览，用户不确定是否设置正确。
- 到期只能自动补记，缺少“待确认/仅提醒”模式。
- 缺少跳过本期、延期本期、结束日期、工作日顺延。
- 生成的账单没有强规则追溯能力，后续排查困难。

### 3.2 数据模型扩展

`recurring_rules` 增加：

- `action_mode`：auto_post / pending_confirm / remind_only。
- `end_ms`：结束日期。
- `skip_weekends`：遇周末顺延到工作日。
- `last_materialized_ms`：最近一次生成日期。
- `paused_until_ms`：暂停到某日。

`transactions` 增加：

- `recurring_rule_id`：由哪条规则生成。
- `source`：manual / ai / import / recurring / auto_record。

### 3.3 UI

新增/编辑定时记账半屏：

- 顶部：左上关闭，标题居中，右上保存。
- 金额与备注沿用手动记账标准。
- 分类选择复用统一分类 picker。
- 周期选择用分段/列表，不用廉价下拉。
- 底部展示“未来 3 次”：例如 `7月10日、8月10日、9月10日`。

列表页：

- 每条规则显示：标题、金额、周期、下次执行。
- 右侧开关为全局 AppSwitch 标准。
- 长按菜单：暂停、跳过本期、删除。

### 3.4 验收

- 每月 31 日规则在 2 月能正确落到 2 月最后一天。
- 设置工作日顺延后，周末规则顺延到周一。
- 删除规则不删除已生成账单。
- 关闭规则后不再生成新账单。

## 4. 自动记账方案

### 4.1 P0：通知候选池

当前已有通知监听和解析，下一步不要直接自动入账，而是先做候选池。

新增表：

- `auto_record_candidates`
  - `id`
  - `source_app`
  - `title`
  - `text_hash`
  - `raw_text`
  - `amount`
  - `kind`
  - `merchant`
  - `occurred_ms`
  - `confidence`
  - `status`：pending / accepted / rejected / merged
  - `created_ms`

流程：

1. 原生通知服务只负责收集通知文本。
2. Flutter 侧解析金额、商户、方向。
3. 去重后进入候选池。
4. 首页或自动记账页提醒“有 N 笔待确认”。
5. 用户确认后生成正式账单。

### 4.2 P1：高置信自动入账

只在满足全部条件时自动入账：

- 支付 App 在白名单。
- 金额解析唯一。
- 商户不是空。
- 过去同商户分类稳定。
- 非退款、非转账、非余额变动、非红包。

用户体验：

- 自动入账后发本地通知：`已自动记一笔 12.00 餐饮，可撤销`。
- 账单详情保留来源：自动记账。
- 用户改分类后写入商户记忆。

### 4.3 P2：截图/OCR/导入联动

- 截图 OCR 识别出的账单先进入候选池。
- 导入账单时用交易 UUID / 订单号 / hash 合并候选。
- 同一笔通知 + 导入账单不能重复入账。

### 4.4 风险控制

- 通知读取权限必须单独解释，不能藏在普通隐私文案里。
- 自动入账必须可撤销。
- 不确定的通知不能丢弃，必须进入待确认或忽略列表。
- 原始通知文本默认只本地保存，可设置保留天数。

## 5. Free / Pro / Max 会员方案

### 5.1 核心原则

- Free 不是残缺版，必须能完整本地记账。
- Pro 提升效率：更多 AI、报告、小组件、自动化。
- Max 提升洞察和长期价值：深度报告、云同步、资产管理高级能力。
- 用户自带 API Key 只解决模型调用成本，不等于解锁会员功能。

### 5.2 权益表

| 能力 | Free | Pro | Max |
| --- | --- | --- | --- |
| 本地手动记账 | 不限 | 不限 | 不限 |
| 导入导出 | 基础 | 高级筛选/批量 | 高级筛选/批量 |
| AI 记账 | 每月少量 | 较高额度 | 大量额度 |
| AI 问账 | 每月少量 | 较高额度 | 大量额度 |
| 周/月/年报告 | 试用或低频 | 标准报告 | 深度报告 |
| 自动记账 | 待确认少量 | 待确认不限 | 高置信自动入账 |
| 小组件 | 基础总览 | 多样式 | 多样式 + 高级洞察 |
| 资产管理 | 基础账户 | 净资产趋势 | 负债中心/高级分析 |
| 云同步 | 无 | 可选 | 包含 |
| 模型优先级 | Flash | Pro 模型额度 | Pro/Max 模型优先 |

### 5.3 技术实现

必须有服务端：

- `users`
- `subscriptions`
- `entitlements`
- `usage_ledger`
- `payment_orders`
- `payment_webhooks`

AI 调用流程：

1. App 请求服务端创建 AI 任务。
2. 服务端检查会员和额度。
3. 服务端调用模型。
4. 成功写 usage ledger。
5. 失败不扣或回滚。

不要在客户端只靠本地开关判断会员，否则非常容易被绕过。

### 5.4 收款

国内 Android：

- 首选应用商店订阅/内购，或合规第三方支付。
- 如果 App 市场规则允许外部支付，可做官网/小程序支付，但必须处理订单、退款、发票/凭证、风控。

海外：

- Google Play Billing。

不建议：

- 个人微信/支付宝收款后手工开会员。问题是不可扩展、难退款、难对账、容易出错。

## 6. 下一步实施顺序

推荐顺序：

1. 先完善账户模型和资产首页 P0。
2. 给交易增加 `source` 和 `recurring_rule_id`，为定时/自动记账追溯打底。
3. 定时记账加未来 3 次预览和 `action_mode`。
4. 自动记账先做候选池，不急着自动入账。
5. 会员体系先做本地假门面和服务端接口设计，正式收费前必须接真实服务端。

不建议顺序：

- 不要先做 Max 会员页面再补服务端。
- 不要先让自动记账静默入账。
- 不要先做投资资产行情，多币种和价格波动会显著放大复杂度。

## 7. 给 Claude 的可执行拆解

这一节是后续真正开工时的任务单。每个阶段都要做到“数据库迁移 + UI + 测试 + 回归验证”一起交付，不要只画页面。

### 7.1 资产管理 P0 任务单

目标：把当前“账户管理”升级为“基础资产管理”，先不碰投资行情和多币种估值。

代码入口：

- 数据层：`lib/data/app_repository.dart`
- 当前页面：`lib/views/settings/accounts_view.dart`
- 当前模型：`AccountEntity`
- 当前计算：`AccountBalanceCalculator`

迁移顺序：

1. 给 `accounts` 增加：
   - `account_type TEXT NOT NULL DEFAULT 'cash'`
   - `opening_balance TEXT NOT NULL DEFAULT '0'`
   - `include_in_net_worth INTEGER NOT NULL DEFAULT 1`
   - `institution TEXT NOT NULL DEFAULT ''`
   - `credit_limit TEXT NOT NULL DEFAULT '0'`
   - `billing_day INTEGER`
   - `repayment_day INTEGER`
   - `sort_order INTEGER NOT NULL DEFAULT 0`
2. 扩展 `AccountEntity`，所有新增字段都必须有默认值，避免老数据库崩。
3. `AccountBalanceCalculator` 改为：账户余额 = `opening_balance + 交易推导余额`。
4. `AccountsView` 改名和定位保持“资产管理”，页面结构改为：
   - 顶部：净资产、资产、负债。
   - 分组：现金/银行卡/支付账户/信用卡/贷款/投资/其他。
   - 列表项：账户名、机构、余额、是否计入净资产。
5. 新增/编辑账户半屏统一使用现有 `SheetHeader`、`SettingsGroup`、`AppSwitch`。

验收测试：

- 老数据库迁移后仍能打开，默认现金账户类型为 `cash`。
- 新建现金账户 `opening_balance=100`，无交易时余额为 100。
- 支出 20 后余额为 80，净资产减少 20。
- 新建信用卡账户 `opening_balance=0`，支出 50 后负债增加 50。
- `include_in_net_worth=false` 的账户不进入净资产，但仍显示账户余额。

### 7.2 定时记账 P0 任务单

目标：先解决“用户不知道规则是否设置正确”和“生成后无法追溯”的问题。

迁移顺序：

1. `recurring_rules` 增加：
   - `action_mode TEXT NOT NULL DEFAULT 'auto_post'`
   - `end_ms INTEGER`
   - `skip_weekends INTEGER NOT NULL DEFAULT 0`
   - `last_materialized_ms INTEGER`
   - `paused_until_ms INTEGER`
2. `transactions` 增加：
   - `source TEXT NOT NULL DEFAULT 'manual'`
   - `recurring_rule_id INTEGER`
3. `runDueRecurring()` 生成账单时写入 `source='recurring'` 和 `recurring_rule_id`。
4. `RecurringRule` 增加“未来 3 次”计算方法，2 月/31 日/闰年必须有单测。
5. 编辑页底部展示未来 3 次日期；列表项展示“下次执行”。

验收测试：

- 每月 31 日在 2 月落到最后一天。
- 周末顺延开启后，周六/周日落到下一个周一。
- `end_ms` 之后不再生成。
- 关闭规则不生成新账单。
- 删除规则不删除历史账单，历史账单仍保留 `recurring_rule_id`。

### 7.3 自动记账 P0 任务单

目标：先做“候选池”，不要直接静默入账。

迁移顺序：

1. 新增 `auto_record_candidates`：
   - `id INTEGER PRIMARY KEY AUTOINCREMENT`
   - `source_app TEXT NOT NULL`
   - `title TEXT NOT NULL`
   - `raw_text TEXT NOT NULL`
   - `text_hash TEXT NOT NULL`
   - `amount TEXT NOT NULL`
   - `kind TEXT NOT NULL`
   - `merchant TEXT NOT NULL DEFAULT ''`
   - `occurred_ms INTEGER NOT NULL`
   - `confidence REAL NOT NULL DEFAULT 0`
   - `status TEXT NOT NULL DEFAULT 'pending'`
   - `created_ms INTEGER NOT NULL`
2. Kotlin 通知监听只负责写队列，不直接决定分类。
3. Dart 侧读取通知队列后解析成候选，按 `source_app + text_hash + occurred_ms 近似窗口` 去重。
4. 自动记账设置页增加“待确认候选”入口。
5. 候选详情支持：确认入账、忽略、删除、修改分类后入账。

验收测试：

- 同一条通知重复上报不会重复生成候选。
- 金额解析失败的通知不丢弃，进入低置信候选或忽略列表。
- 用户确认候选后正式生成交易，候选状态变为 `accepted`。
- 用户撤销交易时，候选状态可以回到 `pending` 或标记 `rejected`。

### 7.4 会员 P0 任务单

目标：先把权益模型和 AI 次数控制跑通，不急着接真实支付。

服务端表设计：

- `users`：用户身份。
- `subscriptions`：当前订阅层级、到期时间、平台订单号。
- `entitlements`：权益开关，如 `ai_quota_monthly`、`reports_deep`、`widgets_advanced`。
- `usage_ledger`：每次 AI/报告/自动记账消耗。
- `payment_orders`：支付订单。
- `payment_webhooks`：支付平台回调原文与处理状态。

客户端只缓存展示，不做最终判定：

- App 可以缓存 `plan=free/pro/max` 和剩余额度用于 UI 展示。
- 真正扣次数、调用模型、生成深度报告必须走服务端。
- 用户自带 API Key 只绕过模型成本，不自动解锁 Pro/Max 权益。

推荐权益：

- Free：手动记账不限、导入导出基础、AI 少量试用、基础总览小组件。
- Pro：AI 记账/问账高额度、标准周/月/年报告、多样式小组件、自动记账待确认不限。
- Max：深度报告、年度复盘、资产高级分析、云同步、高置信自动入账、优先模型。

验收测试：

- Free 用完 AI 次数后，服务端拒绝继续调用模型，客户端展示升级引导。
- Pro 到期后自动降级 Free，历史数据不删除。
- Max 用户可以生成深度报告，但报告失败不扣次数。
- 退款/取消订阅后，权益状态以服务端为准。
