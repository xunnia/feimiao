```dart
class _IosPickerField extends StatelessWidget {
  final String? text;
  final String hint;
  final void Function(BuildContext menuContext) onTapMenu;

  const _IosPickerField({
    super.key,
    required this.text,
    required this.hint,
    required this.onTapMenu,
  });

  @override
  Widget build(BuildContext context) {
    final scheme = Theme.of(context).colorScheme;
    final hasText = text != null && text!.trim().isNotEmpty;

      builder: (menuCtx) => PressableScale(

            color: AppColors.inputFill(scheme),
            borderRadius: BorderRadius.circular(12),
          ),
          child: Row(
            children: [
              Expanded(
                child: Text(
                  hasText ? text! : hint,
```

```dart
void _showPickerMenu(BuildContext menuCtx, List<IosMenuItem> items) {
  if (items.isEmpty) return;
  showIosMenu(
    menuCtx,
    items,
    width: _pickerMenuWidth(menuCtx),
    alignToAnchorLeft: true,
  );
}

double _pickerMenuWidth(BuildContext context) {
  final screenMax = MediaQuery.sizeOf(context).width - 16;
  final renderObject = context.findRenderObject();
  final fieldWidth =
      renderObject is RenderBox ? renderObject.size.width : 260.0;
  final minWidth = fieldWidth < 220.0 ? 220.0 : fieldWidth;
  return minWidth > screenMax ? screenMax : minWidth;
}
```

## 四、统一后 AppPickerField 的 API 建议

放 `lib/widgets/app_picker_field.dart`（或并入 `ios_form.dart` 与 AppLabeledField 作伴），以套1为底座合并另外三套的能力：

```dart
/// 全局「点击弹菜单选值」表单字段。视觉=iosInputDecoration 同款
/// （inputFill 底、radius 12、h14 v10、minHeight 42），按压=PressableScale。
class AppPickerField extends StatelessWidget {
  /// 当前值文案；null/空 = 显示 hint（占位色 AppTextColor.hint）。
  final String? text;
  final String hint;

  /// 可选前置件（Icon / CatIcon 都行，套2、套3的场景）。
  final Widget? leading;

  /// 尾部图标，默认下箭头；日期字段可传 calendar（套4场景）。
  /// 统一不再用 chevron_right（那是"进入下一页"语义）。
  final IconData trailingIcon; // = Icons.keyboard_arrow_down_rounded

  /// 点击回调，内置 Builder 提供锚点 menuCtx；null = 禁用置灰（套4场景）。
  final void Function(BuildContext menuCtx)? onTap;

  const AppPickerField({
    super.key,
    required this.text,
    required this.hint,
    this.leading,
    this.trailingIcon = Icons.keyboard_arrow_down_rounded,
    required this.onTap,
  });
}

/// 配套：菜单跟随字段宽度弹出（合并 _showPickerMenu/_pickerMenuWidth/_menuWidth 两份拷贝）。
/// 内部 = showIosMenu(menuCtx, items, width: 字段宽 clamp(220, 屏宽-16), alignToAnchorLeft: true)。
void showPickerMenu(BuildContext menuCtx, List<IosMenuItem> items);
```

设计决策建议（对着差异表逐条收口）：
1. **标签一律外置**：统一走已有的 `AppLabeledField(label:…, child: AppPickerField(…))`，砍掉套2的内置 label（它的 13px 手写样式和 AppType.secondary 本来就不一致）。
2. **占位统一走 text==null → hint**：套2 的 `placeholder:bool`、套3 的「'未设置' 拼 text」都改掉，占位色统一 `AppTextColor.hint`。
3. **按压统一 PressableScale**（守「同类功能同一种设计」铁律），套3 的 InkWell 水波纹抹掉；沿用套1的 0.985/0.92 参数。
4. **尾图标默认下箭头、可换**：菜单类=下箭头，日期类可传 calendar；chevron_right 禁用。
5. **锚点 Builder 内置**：`onTap(menuCtx)` 直接给锚点 ctx，调用方不用再手包 Builder（套3、套4 调用点可各删一层 Builder）。不弹锚点菜单的（日期选择器、全屏分类弹层）忽略参数即可，现有 `(_) => _pickDate()` 写法天然兼容。
6. **禁用态保留**：`onTap == null` 置灰（套4的 accounts.isEmpty 场景）。
7. **菜单宽度辅助收成一个公开函数** `showPickerMenu`，顺手把 recurring_view 三个调用点的「默认宽菜单+换图标表选中」升级成「跟随字段宽+alignToAnchorLeft+selected:」，观感即与资产表单拉齐。
8. **可选一并收**：a) `AppReadOnlyField`（合并 `_ReadOnlyValueField` 与 `_ReadOnlySettlementField`，同壳无点击）；b) accounts_view 的 `_EnumDropdown/_AccountDropdown/_CategoryDropdown/_NullableDateField` 这层语义包装很好用，可提成 `AppEnumPicker<T>` / `AppAccountPicker` / `AppNullableDateField` 公开件，资产之外（recurring 的账户/账本）直接复用；c) recurring_view 409-443 的内联「起始日期」手写块换成 AppPickerField。
9. **顺手清尸**：edit_transaction_sheet.dart 的 `_accField`（PopupMenuButton）在死代码里，收口时可整文件评估删除。

迁移量预估：4 个文件、直接调用点 12 处 + 包装类间接点 17 处，包装类若同步提公可让 accounts_view 一次瘦身约 250 行。

## 1. accountBalanceResultOf 实现与复杂度

位置：`C:\src\xunni-codex\android-app\lib\data\app_repository.dart:9876`


真正的工作在 `_accountBalanceResultAt`（9886–10141），**零缓存，每次调用从头算**，主体流程：

1. `_effectiveAccountCheckpoint`（9840 附近）：过滤 `_accountBalanceCheckpoints` 找最优锚点 — O(C)。
2. **第一遍全量交易扫描**（9925 `for (final transaction in _allTransactions)`）：为每笔交易构造 `AccountSettlementEvent`，按 checkpoint/开户时点分流 — O(T)。
3. **第二遍全量交易扫描**（9964 `for (final transaction in _allTransactions)`）：`_accountBalanceMovementLegs(transaction)` 展开每笔的余额腿（movement legs）— 又一个 O(T)（含分配对象）。
4. `AccountBalanceCheckpointResolver.resolve`（10009）+ `AccountMovementProjection.resolve`（10043）：对上面收集的 events/movements 做结算重放 — 至少再 O(T)，还有排序开销。

**结论：单次调用 ≈ O(2T 扫描 + resolver 重放 + 大量临时 List/对象分配)，T = 全库交易数。asOf 固定取 `DateTime.now()`，意味着结果只依赖(数据版本, 当天日期)，天然可缓存。**

- `AppRepository extends ChangeNotifier`（2530）。**没有全局版本号/revision 计数**（`budget_plan_revisions` 是预算业务表，无关）。
- **已有 memoize 先例**（8209-8247）：`_refundTotalsCache/_globalRefundTotalsCache/_visibleTxCache/_allRecordsCache` 等惰性 `??=` getter + 统一失效函数 `_invalidateTxDerived()`（8229），唯一调用点在 `_applyCurrentBookTransactionView()`（8161）——所有交易写路径（含 `_refreshTransactionRows` 增量回读，8167）最终都会走它。注释明确写了这套把"每次访问全表扫 O(n²) 压到 O(n)"。
- 另有"稳定引用视图缓存"（8220-8227，`_booksViewCache` 等）专供 `select<>` 按对象标识判变。
- DB 层持久缓存先例：`_syncAssetPurchasePriceCache`（14508）。
- 测试钩子先例：`transactionFullReloadCount`（8136）。

## 5. 缓存方案建议

### 方案A（推荐，最小侵入）：账户余额 per-account memo，挂现有失效钩子
- 位置：`app_repository.dart` 8212 附近加 `Map<int, MetricResult<AccountBalanceValue>>? _accountBalanceCache;` 和 `int _accountBalanceCacheDay;`（存"当天"yyyymmdd）。
- `accountBalanceResultOf`（9876）改为：日期没变则 `_accountBalanceCache[account.id] ??= _accountBalanceResultAt(...)`；日期变了先整体清。
- 失效点：①`_invalidateTxDerived()`（8229）里顺手清——覆盖所有交易写路径；②**必须新增**：账户表写路径（开户余额/币种/删除）、`_accountBalanceCheckpoints` 写路径（新建/撤销校准）、`_checkpointCoveredUnknownEventIds` 变更、`_books` 增删（bookIds 进 MetricQuery）。这些不经过 `_invalidateTxDerived`，是**漏失效的最大风险**。建议抽一个 `_invalidateBalanceDerived()`，从 `_invalidateTxDerived` 和上述账户/锚点写方法都调。
- 收益：资产页 build 从 3A 次重放降到 A 次首帧+后续 0 次；`currentNetWorthResult` 内部的重复调用自动共享。

### 方案B（兜底正确性最强）：全局 revision 计数
- 加 `int _revision = 0`，把 121 处 `notifyListeners()` 收敛到一个 `_notify() { _revision++; notifyListeners(); }`（或在关键写方法里 bump）。memo 记 `(revision, 当天, value)`，revision 或日期不同即重算。
- 优点：不用逐一枚举失效点，任何写都失效，不可能算错；也给未来其它派生量（趋势、净资产、物品卡数据）复用。缺点：粒度粗——无关 mutation（如改一个开关）也会击穿缓存，但击穿后也只是回到现状的开销。
- 可与方案A结合：revision 当 key，精细失效当优化。

### 方案C（视图层局部化，独立可做）
1. `physical_asset_grid.dart:73` 的 `context.watch<AppRepository>()` 改 `context.read`（外层 `accounts_view` 的 Consumer 已负责因数据变化重建子树，卡内 watch 冗余）；或者更进一步：上层 `_buildItems` 一次性把每张卡需要的展示数据算成不可变 record 传进来，配合 repo 内 per-asset memo（`physicalAssetAdditionalCost` 的 O(L×T) 内层 `_allTransactions.where(id==...)` 线性查也该换成一个惰性 `Map<int,TransactionEntity>` by-id 索引——同样挂 `_invalidateTxDerived`）。
2. `_AccountDetailPage`（accounts_view.dart:1705）的 `accountBalanceTrend(days:90)` 是单点最重（~91 次全量重放/帧），给它单独 memo：key = (accountId, days, revision, 当天)。
3. 资产页 `Consumer` 中 `balances` 循环只有 overview/funds 视图用，items 视图 build 时可跳过（`_view == _AssetView.items` 时不算 balances/netWorth）。

### 共同风险：缓存失效时机
- **`DateTime.now()` 依赖**：asOf/knowledgeCutoff 都取 now，跨午夜后窗口端点变化（以及"今天到账"的边界判断）→ 缓存必须带"当天"维度，日期翻转即作废（方案A/B 都已含）。
- **不经交易写路径的变更**：账户开户余额编辑、余额校准锚点增删、账本增删——现有 `_invalidateTxDerived` 覆盖不到，纯方案A若漏挂会出现"改了校准但余额不变"的脏读；revision 计数（方案B）天然免疫。
- **测试路径**：`test/app_repository_test.dart:3361` 直接连调两次并断言中间 mutation 生效，可当缓存失效的回归用例基础；建议仿 `transactionFullReloadCount` 加 `@visibleForTesting balanceRecomputeCount` 断言缓存命中。

```dart
/// 顶部轻提示（对齐 Claude 的「已复制」toast）：
```

`paint()` 核心（119-193 行）：

```dart
  @override
  void paint(Canvas canvas, Size size) {
    final points = segments.expand((segment) => segment.points).toList();
    if (points.length < 2 || size.isEmpty) return;
    // minDate/maxDate、minValue/maxValue 归一化（min==max 时 ±1 撑开）
    const inset = 6.0;
    final chart = Rect.fromLTWH(inset, inset,
        math.max(1, size.width - inset * 2), math.max(1, size.height - inset * 2));
    // 两条 1/3、2/3 高度的水平网格线（gridPaint 0.7 宽）

    Offset position(ComputedNetWorthSnapshot point) { ... 按 asOf/netWorthMinor 线性映射到 chart ... }

    final linePaint = Paint()
      ..color = lineColor
      ..strokeWidth = 2
      ..strokeCap = StrokeCap.round
      ..style = PaintingStyle.stroke;
    final pointPaint = Paint()..color = lineColor..style = PaintingStyle.fill;
    for (final segment in segments.where((item) => item.points.isNotEmpty)) {
      final path = Path();
      for (var index = 0; index < segment.points.length; index++) {
        final offset = position(segment.points[index]);
        if (index == 0) { path.moveTo(offset.dx, offset.dy); }
        else { path.lineTo(offset.dx, offset.dy); }
        canvas.drawCircle(offset, 2.7, pointPaint);   // 每个点 2.7 半径圆点
      }
      if (segment.points.length > 1) canvas.drawPath(path, linePaint);
    }
  }

  @override
  bool shouldRepaint(covariant _NetWorthTrendPainter oldDelegate) =>
      oldDelegate.segments != segments ||
      oldDelegate.lineColor != lineColor ||
      oldDelegate.gridColor != gridColor;
```

**加渐变填充改哪里**：就在这个 for 循环里，每段（per-segment，别跨断点连成一片）在 `drawPath(path, linePaint)` 之前，克隆一条 fill path：`final fill = Path.from(path)..lineTo(lastX, chart.bottom)..lineTo(firstX, chart.bottom)..close();` 然后

```dart
final fillPaint = Paint()
  ..shader = ui.Gradient.linear(  // 或 LinearGradient(...).createShader(chart)
    Offset(0, chart.top), Offset(0, chart.bottom),
    [lineColor.withValues(alpha: 0.18), lineColor.withValues(alpha: 0.0)],
  );
canvas.drawPath(fill, fillPaint);
```

注意：①先画填充再画网格线会被盖住——现在网格线在最前画，填充画在网格之后、线之前即可（填充半透明，压在网格上视觉可接受，或把网格挪后）；②`shouldRepaint` 已比较 lineColor，渐变随主题自动对；③透明度走 `withValues`（项目已全面弃用 withOpacity）；④配色铁律：渐变用 `scheme.primary`（蓝灰）系，别引红绿。
