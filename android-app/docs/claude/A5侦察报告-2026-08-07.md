## 二、双算逻辑：唯一一处，已实锤

**位置**：`app_repository.dart` `_computeCurrentNetWorthBreakdown()`（:10548）

```dart
// 第一轮：遍历账户
for (final account in _accounts) {
  final balance = accountBalanceOf(account);
  if (balance >= Decimal.zero) {
    // 正余额 → 资产（investment 分投资、其余分现金）
  } else {
    liabilities -= balance;   // 负余额 → 负债
  }
}
// 第二轮：遍历负债档案
for (final profile in _liabilityProfiles) {
  if (!profile.countsAsLiability) continue;
  final accountBalance = accountBalances[account.id] ?? Decimal.zero;
  if (accountBalance >= Decimal.zero) {
    liabilities += profile.currentPrincipal;   // ← 双算发生在这里
  }
}
```

**判定链**：`countsAsLiability`（:1961）= `status.countsAsLiability && currentPrincipal > 0`；`status.countsAsLiability`（:888）= `status == active`。

**口径实际是自洽的**：第二轮显式检查 `accountBalance >= 0`，所以 `B < 0` 时不会重复计入。verified-checkpoint builder（:10798）用同一条判据，并诚实地给这批 item 打 `quality: 'legacy_hybrid'`（:10817）——**这个字符串目前只是审计标记，不是模式开关**。

**已更正的误判**：`liabilityProfilePrincipalTotal`（:2908）无条件累加所有 `countsAsLiability` 本金、不看余额正负。初看像口径不一致，**查证后是死代码**——全库仅此一处定义、零调用。A5 可顺手删掉，不要花时间追它。

## 三、数据模型现状

### 3.1 `accounts`（:3956）

无 `balance_mode` 列。与 A5 相关的既有列：

```
type                  TEXT NOT NULL DEFAULT 'cash'     -- AccountType
```

`AccountType`（:46）：`cash / debit / credit / savings / investment / loan / other`。注意**负债语义不由 type 决定**——breakdown 只看余额正负，任何 type 的负余额都算负债。

### 3.2 `liability_profiles`（:5882）

```
interest_rate        TEXT NOT NULL DEFAULT '0'
```

`account_id` 有 UNIQUE 约束 → 一个账户最多一个档案，分支判定不会遇到一对多。

- `LiabilityProfileType`（:828）：`creditCard / mortgage / carLoan / consumerLoan / personalBorrow / other`

## 四、absolute checkpoint 地基（含一条硬限制）

### 4.1 可用 API

`createAccountBalanceCheckpoint`（:20000）：

```dart
Future<int> createAccountBalanceCheckpoint({
  required int accountId,
  required Decimal targetBalance,
  String note = '',
  DateTime? effectiveAt,
})
```

`targetBalance` 无符号限制 → **可以直接校准到 `-P`**，正是 §11.3 的 `B = 0 且 P > 0` 分支所需。

写入行为：insert `account_balance_checkpoints`（`event_kind: 'anchor'`, `reason: 'manual'`），吸收 `coveredUnknownIds`（未知日期/未知账户的流水），更新 `accounts.last_verified_ms`，然后 `_refreshCurrentNetWorthSnapshotBestEffort({NetWorthSnapshotCause.account})`。

`reverseAccountBalanceCheckpoint`（:20113）：insert 一条 `event_kind: 'reversal'` / `reason: 'manual_reversal'` / `reversal_of: <id>`，幂等（已撤销直接 return）。**撤销能力现成**，满足 §11.4「所有变化可撤销」。

### 4.2 ⚠️ 硬限制：不能补记历史

```dart
final historical = now.difference(effective).abs() > const Duration(minutes: 1);
if (historical) {
  throw UnsupportedError('当前版本只支持"现在核对"，历史日终需逐项确认未知到账事件后再开放。');
}
```

**影响 A5**：迁移只能以「现在」为生效时点，无法把 ledger 切换补记到历史某天。后果是**历史净资产快照仍按 legacy_hybrid 口径**，迁移日之后按 ledger 口径 → 曲线上会出现一个口径断点。

**处置建议**（三选一，需在施工前定）：
1. 接受断点，用现有 `NetWorthSnapshotCause.migration` + 断代机制显式标注（**推荐**，符合现有诚实性体系，成本最低）
2. 放开 checkpoint 的历史限制（**不建议**，注释明说需要逐项确认未知事件，等于把另一个高风险特性拖进来）
3. 迁移不走 checkpoint，另设专用迁移事件表（成本最高，但审计最干净）

### 4.3 `reason` 字段需要扩

现在硬编码 `'manual'` / `'manual_reversal'`。A5 迁移应该用独立 reason（如 `'a5_migration'` / `'a5_migration_reversal'`），否则审计上分不清「用户手动校准」和「系统迁移校准」。这是 §11.4「所有变化走 absolute checkpoint 和迁移事件」里「迁移事件」的落点。

## 五、本息拆分现状：半成品

### 5.1 A 批已做的（`repayLiabilityProfile`, :18043 文档 / :18064 签名）

文档注释明确写着「守 V2.1 锁定：不做本息 ledger 化、不改历史数据」。现有语义：

- 本金部分 = `min(amount, currentPrincipal)` → 记一笔**转账**（还款账户 → 负债账户），档案 `currentPrincipal` 同额递减
- 超出本金的差额 → 追加一笔**支出**（分类=利息/手续费）
- `currentPrincipal == 0`（如信用卡，欠款在账户负余额上）→ 整笔按转账，**不产生利息支出**（注释：「没有本金基准，把差额说成利息就是编数」）
- 本金减到 0 且 `personalBorrow` → `status = paidOff`

返回 `({transferTransactionId, interestTransactionId, principalPaid, interestPaid})`。

### 5.2 A5 还缺什么

现在是「**超本金的部分**算利息」（事后判定）。§12.2 要的是「**还款本金/利息拆分**」——即按利率和剩余本金**预先算出**这一期该有多少利息、多少本金（摊销表语义）。这是两回事。

可复用：`_interestCategoryFor`（:18009）分类查找已经写好且考虑得很细（收入侧找 `inc_interest`「利息」；支出侧**故意不按名称匹配**，因为种子里唯一带「利息」的是「房贷利息」`house_loan`，非房贷场景挂它会说谎 → 直接落手续费）。A5 做真本息拆分时若涉及房贷，可以正当地用 `house_loan` 分类。

另有 A2 的收回侧利息逻辑（:17399 起，`interestAmount` 参数），已覆盖「对方多还的利息」→ 收入。测试见 §七。

## 六、快照 / 导出 影响面

### 6.1 scope version

`_bumpNetWorthScopeVersion()`（:11103）自增 `app_settings.net_worth_scope_version`。`_persistCurrentNetWorthSnapshot` 写 `scope_version`（:10874/:11063），且 :11014 会比对 `previous.lineage.scopeVersion != _netWorthScopeVersion` 来决定重算。

**A5 必须 bump**：切换 `balance_mode` 改变了净资产的计入口径，等同于 §「资产 A2：净资产计入政策变化会提升 scope version 并重算当天快照」（已有测试，见 §七）。不 bump 会让新旧口径的快照混在同一 lineage 里。

`NetWorthSnapshotCause` 已有 `liability` 和 `migration` 两个现成 cause（枚举定义在 `core/account/net_worth_snapshot.dart:31`），A5 用 `{liability, migration}` 即可，无需新增。

### 6.2 `balance_mode` 挂哪张表 + 导出 / 导入影响面

**挂 `accounts`，不挂 `liability_profiles`。** 规格 §11.2 原文就是「每个负债账户增加 `balance_mode`」，且有两条代码层面的硬理由：

1. **模式决定「余额」怎么解释，余额是账户的属性。** ledger 模式下正余额算资产、负余额算负债，profile 本金退化成参考资料——被规定语义的是余额。
2. **`deleteLiabilityProfileForAccount`（:17996）存在。** 若模式挂在档案上，删档案会连模式一起删掉，已迁到 ledger 的账户会**静默退回**旧解释。同理 `status` 在还清时会被改成 `paidOff`（:18170），档案的生命周期和余额的生命周期不是一回事，绑在一起会互相污染。

因此需要同步改的是 **`accounts` 的映射**（已查证两处都逐列显式列出）：

- `AccountEntity.toMap()`（:163）→ 加 `balance_mode`
- `AccountEntity.fromMap()`（:185）→ 加 `balance_mode`，**必须给默认值 `legacy_hybrid`**，否则老备份读进来会变成 ledger、口径静默翻转
- accounts 的导入路径同理

`liability_profiles` 的 `toMap`（:2025）/ `fromMap`（:2003）/ 导入（:19791）虽然也都是逐列显式，但**这批不用动**。

⚠️ 这条与「A5 = 负债档案的事」的直觉相反，施工前请确认。

### 6.3 迁移写法模板

v42 的写法（:4479）是标准范式，A5 照抄即可：

```dart
if (oldVersion < 43) {
  final cols = await _columnNamesFor(db, 'accounts');
  if (cols.isNotEmpty && !cols.contains('balance_mode')) {
    await db.execute(
      "ALTER TABLE accounts ADD COLUMN balance_mode TEXT NOT NULL DEFAULT 'legacy_hybrid'",
    );
  }
}
```

**默认值必须是 `legacy_hybrid`**——老库升级后行为逐分不变，这是等价性的前提。

`migration_ladder_test.dart` 需补一条 v43 断言（现有 v41/v42 断言在 :145-159，照格式加）。

**关键发现：这两条用例的断言在等价迁移后应当逐字不变。**

- 用例 1 = §11.3 的 `B = 0 且 P > 0` 分支。迁移后余额校准到 `-780000` 并切 ledger，第一轮 `liabilities -= (-780000)` → 仍是 780000。断言成立。

也就是说**这两条现成用例就是等价性的判据本身**。A5 施工时如果它们变红，说明迁移不等价，不是测试该改。这是很强的安全网，应当在 A5 的 PR 描述里明确写出「这两条不许改」。

## 八、分支分布：需真机数据，但不该阻塞

我原先说「各分支有几个账户只能在你设备的数据库里查」。仓库里确实没有可供统计的备份 JSON（查过，无）。

**但这个数不该成为开工前置条件**，理由：§11.4 的分支分类器**本身就是 A5 的交付物**——迁移 UI 必须先把每个账户归类、再给用户预览。所以正确顺序是：

1. 先写**纯逻辑分类器**（输入：账户余额 `B` + 档案本金 `P` + 档案 status；输出：5 个分支之一），全可单测，不依赖设备
2. 分类器写完后，做一个「迁移预览」页把分布**显示给用户自己看**
3. 分布数自然就有了，同时它还是产品功能的一部分，不是一次性调研

这样既不用等真机数据，也不会白做。分类器建议落 `lib/core/account/liability_balance_mode.dart`（对齐 A1 的 `core/assets/credit_card_terms.dart` 纯逻辑范式）。

**唯一真正需要提前知道的**：`B > 0 且 P > 0` 的歧义账户在你库里是否存在。若为 0，§11.4 那套 5 分支交互可以先做最小版（只留「保持现状」+ 提示），把工期砍掉一大半；若存在，5 个选项都得做全。这个可以等预览页出来后再决定要不要补全 UI——**不阻塞第 1、2 步**。
