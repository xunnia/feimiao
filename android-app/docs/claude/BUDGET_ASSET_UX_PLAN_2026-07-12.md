## 0. 结论先行

### 预算

预算页不能只在「月卡片」和「周预算」之间二选一。正确模型是把两个概念拆开：

| 概念 | 用户在回答什么 | 可选项 | 是否改数据 |
|---|---|---|---|
| **浏览维度** | 我现在想看哪段时间的执行情况？ | 月 / 周 / 自定义 | 否，只改变展示窗口 |
| **计划周期** | 这笔预算多久重置一次？ | 每月 / 每周 / 一次性专项 | 是，决定额度生成方式 |

因此，主页式大卡片可以放心用于「月」浏览；当实际计划是周预算时，月卡片汇总当月各周，并在卡片下展开周明细，不需要把周预算硬塞成月预算。

### 资产

资产管理应固定为**全局个人资产口径**，不能随着抽屉账本暗中改变。账本只作为实物资产/权益资产的归属标签和筛选条件。页面重构为四条主线：

1. **总览**：净资产、趋势、结构、待处理事项。
2. **清单**：账户 / 实物 / 权益 / 负债，可搜索、筛选、排序。
3. **详情**：每类对象都有金额、历史、关联记录和生命周期操作。
4. **余额校准**：记录一笔不计收支的审计调整，不再靠修改期初余额篡改全部历史。

当前顶部净资产已经是全局口径，但实物/权益列表按当前账本过滤，这是资产页最先要修的信任问题。

## 1. 当前实现审计

## 1.1 预算现状

相关代码：

- `lib/core/budget/budget_period.dart`
- `lib/core/budget/budget_engine.dart`
- `lib/core/budget/budget_suggestion.dart`
- `lib/views/settings/budget_setting_view.dart`
- `lib/data/app_repository.dart` 的 `budget_periods`、resolver 和 CRUD

| 已有能力 | 当前行为 | 问题 / 边界 |
|---|---|---|
| 阶段性预算 | `start/end` 保留历史期间 | 编辑开放式循环计划仍会覆盖历史；只有弹窗警告，没有真正版本化 |
| 每月循环 | `recurring_monthly=true` | 不能表达每周重置 |
| 一次性区间 | `recurring_monthly=false` | 与日常预算重叠时采用隐式替代优先级，用户无法理解它究竟是追加还是替换 |
| 自定义期间内每月额度 | `recurring_monthly=true + end != null` | 字段语义已过载，继续加周循环会变成布尔组合爆炸 |
| 分类预算 | 顶级分类 key -> 金额 | 只有金额分配，没有专项预算的消费范围（分类/标签）概念 |
| 智能建议 | 收入 80% 或近 3 月平均，按历史结构切分 | 只按月解释；`fixedExpenses` 虽有字段，当前表单没有保存它 |
| 历史月总额 | 按天重叠折算 | 内部转 `double` 再四舍五入，复杂跨周期时可能有分钱误差 |
| 账本范围 | `book_id=null` 表示全部账本 | 与特殊的「总账本聚合视图」并存，用户和代码都容易混淆 |
| 执行页 | 只展示当前月 | 无法浏览历史月、周或自定义区间，无法回答「上个月预算为什么不同」 |
| 计划列表 | 全部计划平铺在当前页下方 | 执行与管理混在一条长列表，计划多时很难扫描 |
| 首页 / Widget | 只认识月预算总额 | 新周预算必须先定义如何映射到月视图和“今日可用”，不能只改预算页 |

需要保留的正确地基：

- 退款按原单净额计入支出；排除项和转账不进入预算。
- 分类按顶级分类归并。
- 历史期间不能被后来调整污染。
- 预算始终绑定一个账本视图口径。

## 1.2 资产现状

相关代码：

- `lib/views/settings/accounts_view.dart`（当前约 3900 行，账户、实物、权益、负债和全部弹层混在一个文件）
- `lib/data/app_repository.dart` 的资产实体、快照、生命周期和 CRUD
- `test/app_repository_test.dart` 的资产 P1-P4 测试

当前数据能力其实已经不弱：

- 账户：现金、储蓄卡、信用卡、存款、投资、贷款、其他；支持期初余额和是否计入净资产。
- 实物资产：来源、当前价值、购买信息、凭证、估值历史、线性折旧、出售/报废/丢失/赠送/归档及撤销。
- 权益资产：押金、借出款、应收款、预付卡等；支持部分收回、全部收回、损失、归档及撤销。
- 负债档案：类型、原始金额、剩余本金、利率、还款日、还款账户、状态。
- 净资产快照：已有 `global + snapshot_date` 唯一约束，结构字段足以画趋势。
- 数据安全：资产均有 UUID、事件/估值/流水关联，导入导出按唯一 ID 恢复。

主要问题不是“没有功能”，而是信息架构和口径没有把这些能力讲清楚：

| 问题 | 当前证据 | 用户后果 |
|---|---|---|
| 顶部与清单口径不一致 | `currentNetWorthBreakdown()` 使用全部实物/权益；`visiblePhysicalAssets` / `visibleReceivableAssets` 使用当前账本 | 顶部数字包含一项，列表里却找不到它 |
| 账户没有详情页 | 账户行只暴露编辑、删除 | 看不到余额来源、近期活动、趋势，也没有合理的校准入口 |
| 修改期初余额会重写全部历史 | `accountBalanceOf = opening + 全局流水` | 用户只想把今天余额校准，却会让过去每一天都变掉 |
| “本月收支净额”冒充资产变化 | 顶部第三指标只算收入减支出 | 估值、折旧、收回、负债变化都没进入，不能解释净资产变化 |
| 快照只靠手动按钮 | 只有资产结构卡的“快照” | 趋势数据稀疏，普通用户不会主动维护 |
| 页面过长且对象混排 | 总览、分析、实物、权益、七类账户串成一条 ListView | 信息量大但没有主次，越完善越难用 |
| 归档项混在正常清单 | 实物/权益将 visible 与 archived 直接拼接 | 日常清单被历史对象拖长 |
| 负债存在双口径 | 账户为负时取账户余额；账户非负时再取 profile 本金 | 虽避免重复，但用户不知道“当前欠款”到底以谁为准 |
| 投资只到“投资账户余额” | 无持仓/份额/市价模型 | 现阶段能做净资产，不宜承诺证券级收益分析 |
| 非人民币 | 保留但不计人民币净资产 | 当前无汇率，应继续诚实显示，不可静默相加 |

## 2. 预算方案

## 2.1 产品目标与非目标

目标：

1. 进入页面 3 秒内回答：这段时间预算多少、花了多少、还剩多少、是否花快了。
2. 月预算、周预算都能用同一套浏览界面自然展示。
3. 每次调整只影响用户选择的未来周期，不篡改已结束周期。
4. 首页、预算页、统计卡和 Widget 使用同一个预算解析结果。
5. 计划冲突可解释、可测试，不依赖“后创建的偷偷覆盖前面的”。

本轮非目标：

- 不做多人协同审批。
- 不做银行自动同步。
- 不做复杂的滚存、借额度、跨分类自动调拨；这些可在基础模型稳定后增加。
- 不把专项预算和日常预算粗暴相加成一个“总预算”，避免同一支出被重复解释。

## 2.2 信息架构

```text
周计划在“月”浏览下：
```

执行和计划管理仍在同一入口，但视觉顺序固定为：**先看执行，再看分类，再看专项，最后管理计划**。计划很多时，“查看全部”进入独立计划列表，不在首页无限展开。

## 2.3 浏览维度

### 月

- 主卡片沿用主页大卡片的交互：左右滑切月；点年月打开同款 12 个月份网格。
- 月计划：直接显示该自然月额度与执行。
- 周计划：将当月覆盖到的周额度按日折算汇总，并列出周明细。月首/月末的跨月周只计当月所占天数。
- 一次性专项：单独出现在“专项计划”，不混入日常月额度。

### 周

- 默认周一到周日。
- 周计划：显示该完整周的真实额度。
- 月计划：显示“本周参考额度”，即月额度按本月天数分摊到本周所占日期；同时保留“本月总进度”入口，避免用户误以为月预算每周重置。
- 跨月周分两段从各自月份取得参考额度，但 UI 仍显示为一周，并在明细注明来源。

### 自定义

- 使用全局 `showAppDateRangePicker`。
- 用于复盘任意区间，不产生新计划。
- 汇总区间内各日的日常计划参考额度；专项计划仍分别显示。
- 最长建议限制为 366 天，超过时提示缩短，避免把预算页变成年报。

## 2.4 计划周期

| 周期 | 额度含义 | 重置边界 | 适用场景 |
|---|---|---|---|
| 每月 | 每个自然月一份额度 | 每月 1 日 | 工资/月度家庭预算 |
| 每周 | 每个自然周一份额度 | 周一 00:00（推荐） | 每周调预算、生活费 |
| 一次性专项 | 整段日期共用一份额度 | 不重置，到期结束 | 旅行、装修、婚礼 |

“每月/每周”属于**日常主计划**；“一次性专项”属于**独立追踪计划**。专项默认必须选择分类或标签范围，避免所有支出既算日常又无差别算专项。

## 2.5 新建 / 编辑流程

使用 90%-96% 高的标准全屏弹层或独立页面；信息量已经超过小弹窗。顶部始终是 `SheetHeader`：左上关闭、居中标题、右上保存。

### 新建日常计划

```text
1. 计划周期       [每月] [每周]
2. 所属账本       总账本（必选，不再使用模糊的 null=全部）
3. 生效时间       本月 / 下月；本周 / 下周
4. 周期额度       ¥____
5. 分类额度       可选；合计不得超过总额
6. 智能建议       折叠辅助，不抢主流程
7. 保存
```

- 首次创建默认本周期生效。
- 已有主计划时，新建不同周期会明确提示“从某日替换现有日常计划”。
- 修改额度默认**下一个周期生效**；用户可主动选“本周期立即生效”。任何选择都新增 revision，不回写已结束周期。

### 新建专项计划

```text
1. 名称           国庆旅行
2. 起止日期       2026/10/1 - 2026/10/7
3. 总额度         ¥5,000
4. 消费范围       分类 / 标签（至少一种）
5. 所属账本       总账本
6. 分类额度       可选
7. 保存
```

- 专项不改变首页“今日可用”。
- 专项卡单独显示实际花费；同一笔支出可以同时属于日常计划和一个专项，这是两种观察角度，不把两者金额相加。
- 如果未来需要“旅行期间完全替换日常预算”，再增加高级模式，首版不把复杂选择暴露给普通用户。

## 2.6 状态与冲突规则

### 状态

| 状态 | 判定 | UI |
|---|---|---|
| 即将开始 | start > 今天 | 灰色说明 |
| 使用中 | 今天在有效期内 | 主色 |
| 接近上限 | 使用率 >= 80% 且 < 100% | 铜金 |
| 已超支 | 使用率 > 100% | `AppColors.warning` 橙色 |
| 已结束 | end < 今天 | 灰阶，可复盘 |
| 已归档 | 用户隐藏管理项 | 只在归档筛选中显示 |

禁止红色和绿色，沿用现有配色铁律。

### 冲突

1. 同一个账本、同一天最多只有一个日常主计划。
2. 新 revision 自动把旧 revision 的 `effective_to` 截到新 revision 前一天。
3. 月计划切换成周计划属于“替换主计划”，必须显示生效日和受影响周期。
4. 专项可以互相重叠，但每个专项必须有消费范围；同名不视为同计划，以 UUID 区分。
5. 分类额度合计不得超过周期总额；剩余部分显示为“未分配额度”，不是错误。
6. 删除有历史执行的计划改为归档；只有从未生效、无执行的计划允许物理删除。
7. 总账本和子账本的预算不自动相加：当前查看哪个账本视图，就解析绑定该视图的计划。

## 2.7 统一计算口径

所有调用方只使用一个新解析结果 `BudgetWindowResult`，不得各自重新拼公式。

```text
BudgetWindowResult
  viewStart / viewEnd
  scopeBookId
  primaryPlan
  plannedAmount       浏览窗口的日常参考额度
  spentAmount         浏览窗口的净支出
  remaining
  progress
  cycleSlices[]       每个真实月/周周期的额度与支出
  categoryResults[]
  specialResults[]
```

统一规则：

- 只统计支出；转账、不计入收支行不统计。
- 附着式退款使用原单净额，日期归属原单日期。
- 总账本使用它现有的聚合账本集合；子账本只使用该账本。
- 月计划日额度 = 当月额度 / 当月天数。
- 周计划日额度 = 周额度 / 7。
- 跨窗口按覆盖天数取额度；分钱使用 Decimal/整数分，不再经 `double`。
- 除不尽的分按照“前 N 天多 1 分”的固定规则分配，保证一个完整周期各日之和严格等于周期额度。
- “今日可用”只使用日常主计划；专项不参与。
- 历史窗口按当时 revision 解析，不使用今天的计划设置。

## 2.8 推荐数据模型

不要继续给 `recurring_monthly` 增加更多布尔组合。建议正规化为计划身份 + 历史版本：

### `budget_plans`

| 字段 | 含义 |
|---|---|
| id / uuid | 本地 ID + 同步稳定 ID |
| book_id | 必填，绑定一个真实账本视图；总账本也使用其 ID |
| name | “日常预算”“每周生活费”“国庆旅行” |
| role | `primary` / `special` |
| cadence | `monthly` / `weekly` / `one_off` |
| anchor_start_ms | 周期锚点或专项开始日 |
| end_ms | 专项结束日或计划终止日 |
| week_start | 1=周一，首版固定但保留字段 |
| expense_scope_json | 专项的分类/标签范围；日常为空表示全部支出 |
| status | active / archived |
| created_ms / updated_ms | 审计与同步 |

### `budget_plan_revisions`

| 字段 | 含义 |
|---|---|
| id / uuid / plan_id | revision 身份 |
| effective_from_ms / effective_to_ms | 本版本生效区间 |
| amount | 每月、每周或专项整段额度，继续用 Decimal TEXT |
| category_budgets | 顶级分类额度 JSON |
| income_reference | 建议时输入的收入，仅回显 |
| fixed_expenses | 建议输入，仅回显 |
| created_ms / updated_ms | 审计与同步 |

计划身份负责“这是什么计划”，revision 负责“这段历史用多少钱”。改变周期类型应新建计划；只改额度/分类应新建 revision。

## 2.9 DB 迁移

1. 新建两张表，不立即删除 `budget_periods`，保留一个版本用于回滚核对。
2. 每条旧 `budget_periods` 迁移为一个 plan + 一个 revision：
   - `recurring_monthly=true` -> monthly。
   - `recurring_monthly=false` -> one_off。
   - `book_id=null` -> `defaultBookId`（总账本聚合视图）。旧 UI 把 null 写成“全部账本”，但 resolver 还会把它当作每个子账本的兜底预算；新模型按用户看到的名称解释为聚合预算，不再暗中复制到子账本。若确实需要某个子账本单独预算，由用户在计划管理中显式复制。
   - 金额、分类、收入、固定支出、起止日期原样保存。
3. 对旧的开放式月计划按现有 resolver 的优先级排序；有重叠时自动截断旧 revision。明确绑定具体账本的计划，迁移前后逐日解析结果必须一致。
4. 旧一次性区间先标记 `legacy_override=true` 走兼容解析，避免升级后首页额度突变；用户首次编辑时再转换为新的独立专项语义。
5. 迁移后运行按日对账：至少比较过去 24 个月与未来 12 个月的日额度和月合计。具体账本计划和总账本聚合计划必须一致；唯一允许的差异是旧 null 预算不再错误落到子账本。其他不一致一律回滚事务。
6. 第二个稳定版本后才考虑移除旧表和兼容字段。

## 2.10 分阶段实施

### B1：只重做浏览与统一 resolver

- 新增月 / 周 / 自定义浏览。
- 大卡片、周期切换、历史复盘。
- 抽 `BudgetWindowResult`，首页/预算/统计/Widget 共用。
- 仍读取旧表，先验证 UX 和计算。

### B2：计划版本化 + 每周周期

- DB 迁移到 plan/revision。
- 新建/编辑流程。
- 周计划、冲突处理、历史不可变。

### B3：专项计划

- 分类/标签范围。
- 专项独立卡、到期状态、归档。
- 不进入首页“今日可用”。

### B4：建议与质量收口

- 月/周分别使用相同长度的历史周期给建议。
- 固定支出真正保存并回显。
- 空态、无历史、跨月周、退款、账本切换、Widget 全面回归。

## 2.11 预算验收标准

1. 月计划 3000 元，切到任意历史月，显示该月当时的 revision，不随今天修改而变化。
2. 周计划 700 元，完整周额度严格为 700；跨月周两个月分摊之和仍严格为 700。
3. 月浏览周计划时，主卡等于当月各日额度之和，周明细之和与主卡完全一致。
4. 周浏览月计划时明确写“参考额度”，不误导为周重置。
5. 退款、排除项、转账口径与主页/统计一致。
6. 切换账本后预算和支出同时切换，不出现预算是 A 账本、支出是 B 账本。
7. 新额度默认从下一周期生效；旧周期金额和分类保持不变。
8. 分类预算合计超总额禁存；未分配额度允许存在。
9. 首页、预算页、Widget 对同一日期和账本的额度一致到 0.01 元。
10. 320dp 宽度下日期、金额、状态不溢出；深色与六种主题均可读。

## 3. 资产管理方案

## 3.1 口径先锁定

**推荐：资产管理永远是全局口径。**

全局净资产：

```text
账户正余额
+ 投资账户正余额
+ 计入净资产的实物当前价值
+ 计入净资产的权益剩余金额
- 账户负余额 / 活跃负债
= 净资产
```

规则：

- 使用全部账本中的账户流水计算账户余额；切换抽屉账本不改变资产总额。
- 实物和权益展示全部账本对象，行内显示所属账本，可按账本筛选。
- `include_in_net_worth=false` 的对象仍在清单，但不进入合计。
- 非 CNY 数据保留并分币种展示；没有汇率前不折算、不进入人民币净资产。
- 归档/结束/损失对象默认不进入净资产，并从活跃清单移到归档筛选。
- “本月收入 - 支出”不是净资产变化，顶部不再使用这个指标。

## 3.3 总览

### 全局净资产卡

```text
全局净资产                         截至今天
¥268,400

总资产 ¥320,000      总负债 ¥51,600
较上次记录 +¥3,240    记录于 7 月 1 日
```

- “较上次记录”来自净资产快照差值；没有两条快照时不显示，绝不拿月收支净额代替。
- 点击总资产/总负债进入已筛选清单。
- 隐私模式继续遮挡金额。

### 净资产趋势

- 时间范围：1 月 / 3 月 / 1 年 / 全部。
- 主线只画净资产；点图例可看总资产和总负债。
- 数据从现有 `net_worth_snapshots` 读取，今天追加一个实时点。
- 不伪造升级前历史；第一条快照之前显示“从开始记录后”。
- 每次资产域有效变更后，当天只 upsert 一条全局快照；应用启动完成折旧后也补当日快照。

### 资产结构

- 流动账户、投资账户、实物、权益、负债五行。
- 金额、占总资产比例、进入对应清单的点击区域。
- 负债率 = 总负债 / 总资产；总资产为 0 时显示暂无，不显示无穷或 999%。

### 待处理事项

最多显示 3 条，按紧急度排序：

1. 7 天内还款。
2. 权益已到期仍未收回。
3. 超过用户设置周期未校准的账户。
4. 折旧待执行或估值长期未更新。

没有事项时整个区块消失，不放“恭喜你”的占位卡。

### 最近变化

- 合并展示：余额校准、估值变化、出售、收回、归档、还款等资产事件。
- 普通收入/支出不在这里重复铺账单，只在账户详情里看。

## 3.4 清单

### 顶部控件

- 搜索：名称、机构、对方、品牌型号。
- 类型：全部 / 账户 / 实物 / 权益 / 负债。
- 账本筛选：只对实物、权益生效；账户和负债是全局对象。选择账户/负债时不显示无意义的账本筛选。
- 状态：使用中 / 不计入 / 已归档。
- 排序：金额降序（默认）/ 最近更新 / 名称。

### 行信息

| 类型 | 主标题 | 副标题 | 右侧 |
|---|---|---|---|
| 账户 | 微信零钱 | 现金 · CNY · 3 天前校准 | 当前余额 |
| 实物 | MacBook Pro | 数码 · 使用中 · 日常账本 | 当前价值 |
| 权益 | 租房押金 | 到期 2027/6 · 房屋账本 | 剩余金额 |
| 负债 | 房贷 | 下次 7/15 · 还款中 | 剩余本金 |

- 行点击进入详情；低频编辑/归档放详情页，不在每行同时摆编辑和删除按钮。
- 归档默认不混入活跃列表，只在“已归档”筛选中出现。
- 分组标题只显示类型合计和数量，不重复放多个 `+`；新增统一走右上角总 `+`。

### 空态

- 整个资产域为空：只显示标准猫空态，右上角 `+` 始终可见。
- 某筛选无结果：只显示小猫，不堆功能说明。
- 点击 `+` 后再展示“账户 / 实物 / 权益 / 负债”的新增选择。

## 3.5 四类详情流程

### 账户详情

```text
微信零钱                                      [⋯]
当前余额  ¥2,680.35
较上次校准 +¥128.20

[余额趋势 1月/3月/1年]

[转账] [校准余额] [编辑资料]

账户信息
  类型、机构、币种、期初余额日期、计入净资产

最近活动
  账单、转账、余额校准混合时间线
```

- 余额趋势从期初、流水和校准记录按日计算。
- 编辑资料不能把“改今天余额”和“改期初基数”混为一个输入。
- 有历史流水的账户不能物理删除，只能归档；归档后仍能查看历史。

### 实物详情

在现有能力上重排，不推翻生命周期：

- 首屏：当前价值、购入价、累计变化、状态。
- 估值趋势：使用 `asset_valuations`。
- 资料：分类、来源、购买日、品牌型号、位置、保修、所属账本、凭证。
- 关联：购买/出售流水。
- 时间线：新增、估值、折旧、出售、撤销、归档等。
- 主操作：更新价值；更多菜单：编辑、折旧、出售、报废、丢失、赠送、归档。
- 终止状态必须走生命周期操作，继续禁止普通编辑绕过事件链。

### 权益详情

- 首屏：原始金额、剩余金额、收回进度、状态。
- 资料：权益类型、对方、到期日、所属账本、备注。
- 时间线：新增、部分收回、撤销收回、损失、归档。
- 主操作：记录收回；到期前后给明确状态。
- 收回仍是资产形态转换，不进入普通收入；目标账户余额增加，权益余额减少，净资产不凭空变化。

### 负债详情

- 首屏：剩余本金、原始本金、偿还进度、状态。
- 资料：类型、利率、还款日、默认还款账户、期限。
- 时间线：建立、校准本金、还款、利息/费用、结清、归档。
- 主操作：记录还款。
- 还款拆分：本金部分是账户间资产/负债转换，不计支出；利息和手续费才计支出。
- 负债本金最终统一以**负数负债账户余额**为唯一金额来源，profile 只保存利率、还款日等合同资料，消除双口径。

右上角 `+` 打开标准半屏选择器：

```text

  新增账户       现金、银行卡、投资账户
  添加实物       数码、车辆、房产、贵重物品
  添加权益       押金、借出款、应收款、预付余额
  添加负债       信用卡、房贷、车贷、消费贷
```

每个多字段表单统一：

- `AppLabeledField` 常驻字段名，hint 只放示例。
- 首屏只放必填字段，“更多信息”折叠可选字段。
- 金额、日期、所属账本、是否计入净资产必须明确。
- 保存防重入，失败留在原表单并给 `showAppToast`。

## 3.7 余额校准

这是资产流程最重要的新能力。

入口：账户详情 -> `校准余额`。

```text
校准余额                                      [保存]

系统计算余额        ¥2,680.35
实际余额            [¥ 2,712.80]
差额                 +¥32.45
校准日期            2026/7/12
说明（可选）        微信实际余额

这笔校准只修正账户余额，不计入收入、支出和预算。
```

保存后新增一条不可静默覆盖的调整记录：

- 账户余额 = 期初余额 + 普通流水净影响 + 截止日期的校准差额。
- 校准不进入收入、支出、预算、报表消费分类。
- 允许撤销最近一笔校准；底层写反向记录，不直接删除审计历史。
- 历史日期校准只影响该日期及之后的余额。
- “编辑期初余额”移到高级操作，并明确提示它会改变全部历史；有校准记录后默认禁止随手修改。

## 3.8 生命周期

| 对象 | 活跃状态 | 终止/隐藏状态 | 恢复 |
|---|---|---|---|
| 账户 | active | archived / closed | archived 可恢复；closed 只读 |
| 实物 | active / idle | sold / disposed / lost / gifted / archived | 出售可撤销；归档可恢复 |
| 权益 | active / partial_recovered | recovered / lost / archived | 收回可撤销；归档可恢复 |
| 负债 | active / paused | paid_off / archived | archived 可恢复；结清保留历史 |

规则：

- 有历史的对象不物理删除。
- 状态变化必须写事件。
- 终止状态默认不计净资产；恢复时由用户确认是否重新计入。
- 所有撤销操作必须同时撤销关联流水/估值影响，继续沿用当前事务化做法。

## 3.10 数据迁移与风险

### 口径迁移

1. 先公开全局实物/权益 getter，资产页清单改为全量；不改现有净资产数值。
2. 现有账户生成 UUID 和时间戳。
3. `opening_balance_date_ms`：有流水的账户取最早关联流水日期；无流水账户取迁移日。该日期之前不画账户趋势，不伪造历史。
4. `is_deleted=0` -> active；已删除且仍有历史 -> archived/migration-hidden，保留数据。
5. 负债迁移：
   - 账户余额已为负：使用 ledger 余额，profile 本金只作旧值留档。
   - 账户余额非负但 profile 有剩余本金：迁移日写一笔专用本金校准，使负债账户达到 `-currentPrincipal`；迁移前后全局净资产必须一致。
6. 迁移前后分别计算全局总资产、总负债、净资产，三项必须逐分一致，否则事务回滚。

### 主要风险

| 风险 | 控制方式 |
|---|---|
| 校准被误算成收入/支出 | 独立表和独立事件，统计引擎不读取它 |
| 负债迁移重复计算 | 迁移前后净资产断言 + 每账户余额/本金对账 |
| 趋势伪历史 | 不回填未知估值，只从首条可信快照开始 |
| 页面性能 | 总览只订阅聚合结果；清单 builder 懒加载；详情按对象读取，不让 3900 行单页全量重建 |
| 多币种误加 | CNY 合计与原币列表分开；没有汇率不折算 |
| 账本筛选再次污染顶部 | 总览固定 global；筛选只存在于清单，并在 UI 明确标注 |
| 删除破坏关联 | 有事件/流水对象只归档；事务化撤销继续保留 |

### A5：负债统一

- 单一本金来源迁移。
- 还款拆本金/利息、事件和撤销。
- 结清与归档流程。

### A6：后续可选

- 投资持仓、份额、成本、市价和收益率。
- 汇率与多币种折算。

这两项都不应塞进前五阶段，否则会拖慢最重要的口径和可用性修复。

## 3.13 资产验收标准

1. 无论抽屉当前选哪个账本，资产总览的全局净资产不变。
2. 顶部合计中的每一项都能在清单中找到；按账本筛选只改变清单，不偷改顶部。
3. 账户校准后余额精确等于目标值，收入、支出、预算和分类统计全部不变。
4. 撤销校准后余额恢复，审计时间线保留正反两条记录。
5. 实物出售、权益收回、负债还本都按资产形态转换处理，不凭空增加收入。
6. 利息/手续费进入支出，本金不进入支出。
7. 净资产趋势只从可信快照开始；同一天多次变更只有一条最终快照。
8. 账户负余额和 profile 本金不会重复计负债。
9. 归档对象不出现在默认清单、不计净资产，但可以恢复并查看完整历史。
10. 非 CNY 不进入人民币合计，原币金额仍可见。
11. 空态、长名称、大金额、320dp、深色和六主题均无溢出或不可见控件。
12. 资产迁移前后总资产、总负债、净资产逐分一致。

## 4. 需要用户拍板的选项

| 编号 | 选项 | 推荐 | 原因 |
|---|---|---|---|
| D1 | 每周从周一还是周日开始 | **周一** | 符合国内工作周和现有统计直觉；字段保留以后可配置 |
| D2 | 一次性专项是追加追踪，还是替换日常预算 | **独立追踪，不改变日常“今日可用”** | 解释最稳定，不会因为旅行计划让主页日常预算突然跳变 |
| D3 | 调整日常额度默认何时生效 | **下一周期** | 保护历史和本周期执行；仍提供“本周期立即生效” |
| D4 | 预算是否继续允许 `null=全部账本` | **不允许；绑定一个真实账本视图，总账本也有 ID** | 消除“全部账本”和“总账本聚合”双重语义 |
| D5 | 资产总览跟随当前账本还是固定全局 | **固定全局** | 账户本来就是全局，个人净资产不应因看哪个账本改变 |
| D6 | 资产详情用半屏还是普通二级页 | **普通二级页** | 信息、历史和生命周期操作已超过半屏承载能力 |
| D7 | 账户差额用改期初余额还是校准记录 | **独立校准记录** | 不篡改历史，不污染收支，可审计和撤销 |
| D8 | 首批是否做证券持仓和自动汇率 | **不做，先保持投资账户余额 / 原币保留** | 先解决口径和全流程；持仓与汇率是另一套高风险数据域 |

如果用户接受全部推荐项，实施时无需再逐条追问；按 B1 -> B2 和 A1 -> A3 的顺序先交付最能改善体验且风险可控的部分。

## 5. 推荐排期顺序

```text
1. 预算 B1：浏览维度 + 统一计算口径
2. 资产 A1：修全局口径 + 总览/清单
3. 预算 B2：版本化 + 周预算
4. 资产 A2/A3：详情、趋势、余额校准
5. 预算 B3：专项计划
6. 资产 A4/A5：完整生命周期与负债统一
```

原因：先让用户“看得懂、对得上”，再动 DB；每个 DB 阶段都能独立回归和回退，不把预算迁移与资产迁移塞进同一个版本。
