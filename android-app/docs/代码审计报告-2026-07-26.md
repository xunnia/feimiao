## 一、高危（6 条）

### H1. 数据库损坏时备份恢复必然失败——灾难恢复在最需要时是死路
- 位置：`android-app/lib/data/app_repository.dart:8649`
- 问题：`_replaceDatabaseFromFile` 恢复前先对**当前库**做一致性副本（VACUUM INTO + quick_check），当前库损坏时这一步必抛错，被外层 `catch(_)` 捕获后整个恢复直接放弃，没有降级为普通文件复制的兜底。
- 场景：手机掉电导致 qingji.db 损坏 → 用户拿完好备份去恢复 → 永远提示「恢复失败」，被锁死在损坏数据上。
- 建议：当前库安全副本失败时降级为普通 `File.copy`（或跳过副本仅记日志），恢复动作本身不应被它阻断；补「当前库损坏 + 恢复完好备份」测试用例。

### H2. markReimbursed 对已关联实物资产的账单必抛错，报销页无 catch，确认报销静默失败
- 位置：`app_repository.dart:9242`；`reimburse_view.dart:208`
- 问题：`markReimbursed` 开头调 `_assertTransactionMutable`，资产关联账单必抛 StateError；但函数体内又写了资产退款分摊逻辑（9284 行，永不可达），与 `refundTransaction` 刻意不做此断言的设计自相矛盾。报销页调用无 try/catch。
- 场景：待报销的笔记本支出 → 加入实物资产 → 报销页点「确认到账」→ 弹层关了但什么都没发生，反复点永远失败、零提示。
- 建议：与 refundTransaction 对齐（去掉该断言、让资产分摊代码生效），或在入口把资产关联账单从待报销列表排除；reimburse_view 补 try/catch + toast。

### H3. 导入退款挂到已关联资产的原单时不更新资产分摊，净资产持续虚高且无提示
- 位置：`app_repository.dart:11469`（importReviewedBillBatch）；同缺口：`11197`（importFeimiaoExportRows）、`8991`（_normalizeStandaloneRefunds）
- 问题：导入路径直接 `txn.insert` 退款行，不调 `_applyNewRefundToAssetAllocations`/`_refreshOrderAllocationQuality`/购置价缓存刷新；资产页「分配退款」入口因 costQuality 未变永不出现。
- 场景：¥5000 京东订单已入资产 → 次月全额退款、重新导入账单 → 账单净额归 0，但资产仍按 ¥5000 计成本，净资产永久高估。
- 建议：三处退款挂接统一走 refundTransaction 的分摊管线，或事务后对受影响原单批量跑 `_refreshOrderAllocationQuality`。

### H4. 同一批导入中同一原单多笔退款被双重扣减，第二笔合法退款被丢弃
- 位置：`app_repository.dart:11451`
- 问题：`remaining = 原额 − dbRefunded − attachedRefunds`，但事务内 query 已能看到本批刚插入的退款行，attachedRefunds 又累加了同一笔 → 双扣。
- 场景：¥100 订单拆 ¥40+¥30 两笔退款（同一 CSV 常见）→ 第二笔 remaining=100−40−40=20<30 被判「未匹配」丢弃，本月支出永久虚高 ¥30。
- 建议：二选一——去掉 attachedRefunds，或 dbRefunded 查询排除本批插入的 id。补多笔部分退款接近全额的测试。

### H5. 微信账单「商户单号/交易单号」列永远匹配不上，orderNo 精确配对对微信全失效
- 位置：`bill_import.dart:238`
- 问题：查找键 `['商户订单号','交易订单号','订单号']` 全含「订」字，微信表头是「交易单号,商户单号」→ contains 全落空，微信所有行 orderNo=''，退款只能走模糊打分（商户名相同即 8 分达标、同分取文件序第一个），错挂概率高。
- 场景：同商户同日两单 ¥50/¥30 + 一条 ¥30 退款 → 退款挂到 ¥50 那单。
- 建议：查找键补「商户单号」「交易单号」；模糊匹配同分并列时（bestScore≥8 分支）拒绝配对而非取第一个。测试补微信 orderNo 断言。

### H6. 按任务分路由的 AI 配置可绕过隐私同意弹窗，未同意也把全量账单上传给 LLM
- 位置：`ai_chat_panel.dart:1486`（同意闸门只在 recordParse-hasKey 分支）
- 问题：记账路由（recordParse）无 key 时跳过 `ensureAiPrivacyConsent` 直落兜底分支，而 `_runQuery` 用的是另一套 chatQuery 路由（可能有 key），把最多 240 笔账单+预算直接 POST 出去，全程无同意检查；报告路径同理。且改用途分配会自动把同意标记重置为 false，使该绕过更易发生。
- 场景：记账=DeepSeek（没填key）、喵助手=自定义服务（有key）、同意标记为 false → 问「这个月花了多少」→ 数据上传、弹窗从未出现。
- 建议：把 `ensureAiPrivacyConsent` 下沉到 `_runQuery` / 报告 job 创建 / `_resumePendingReportJob` 等每一个实际发起上传的入口。

## 二、中危（22 条）

### 导入/退款配对（重灾区）
1. **跨文件/跨月退款必然丢失**（`app_repository.dart:11372`）：订单号不落库，配对只在当前批次内查。微信/支付宝按月导出，月末下单次月退款是常态 → 退款被丢、支出系统性虚高。建议把 orderNo 持久化到 transactions 并支持回查历史原单。
2. **订单号占位符 '/' 未过滤**（`bill_import.dart:254`）：多行共享 orderNo='/'，退款可「精确」错挂到最后一条无关行。parseRow 对商品/备注/方向都识别了 '/'，唯独 orderNo 漏了。
3. **收入行带「退款」字样被强制当退款行**（`bill_import.dart:268`）：朋友转账还钱备注「房租退款」→ 被当退款、找不到原单 → 真实收入静默丢弃。复核页也没有把误判行改回收入的入口。
4. **importFeimiaoExportRows（肥喵备份恢复）没包事务**（`app_repository.dart:11101`）：几千行恢复到一半被杀 → 半截数据、原单缺冲减行净额虚高。
5. **CSV 导出无公式注入防护**（`import_export_view.dart:158`）：商户可控的商品名/备注以 `=` `+` `-` `@` 开头，导出后 Excel/WPS 当公式执行，可数据外带。导出时对这类前缀加 `'` 中和即可。

### 退款/报销闭环
6. **撤销「报销到账」冲减行后不恢复 reimbursable 标记**（`app_repository.dart:11511`）：误点已报销 → 撤销 → 账单从待报销页永久消失。deleteTransaction 删 reimbursement 行时应恢复原单 reimbursable=1。
7. **退款分摊强制「必须完整分配到已跟踪物品」**（`app_repository.dart:14411`）：退款属于订单中未跟踪部分时，用户只能错摊（污染资产成本）或永远卡在待分配。需要「归属未跟踪部分」的出口。
8. **左滑删除/撤销退款不捕获保护性 StateError**（`transaction_actions.dart:108`；`refund_settlement_sheet.dart:401`）：保护规则拦下时静默失败，写给用户看的提示文案永远到不了用户眼前。补 catch + showAppToast。

### AI/LLM
9. **报告重新生成/后台恢复路径无隐私同意检查**（`report_views.dart:307`；`report_generation_service.dart:33`；`report_task_scheduler.dart:39`）：撤回同意后点「重新生成」仍直接上传全周期账单，与设置页承诺矛盾。
10. **账单备注可注入 AI 上下文操纵查账**（`ai_chat_panel.dart:2281`）：note 未剥换行/竖线即拼入上下文，而系统提示词强制模型引用「本期准确合计」行 → 导入的恶意 CSV 可伪造合计行控制答案。拼接前把 note 中的换行和 `|` 替换掉即可。
11. **LLM 解析期间关面板，这笔记账静默丢失**（`ai_chat_panel.dart:1707`）：查账路径专门处理了 unmount 仍落库，记账路径没有——用户消息已存、解析结果丢弃、无任何提示。
12. **_save 中途 unmount：交易已写库但卡片永远停在保存中**（`ai_chat_panel.dart:2961`）：重启后卡片消失、交易还在 → 用户重记一遍 → 重复入账。写库完成后的状态落库不应依赖 mounted。

### 自动记账/原生层
13. **通知监听只按包名过滤，普通聊天消息也入队**（`PaymentNotificationListener.kt:19`）：联系人发「我已支付 ¥2000」→ 进确认表且默认勾选 → 一键记下就入账。应校验 channel id / 发件人为「微信支付/支付宝」。
14. **通知金额正则不支持千位分隔符**（`notification_parse.dart:14`）：「¥1,280.00」被解析成 ¥1 入库，本月统计少 1279。
15. **ACTION_SEND 处理完不清除 intent**（`MainActivity.kt:200`）：进程被回收后从最近任务恢复会重放分享 → 同一截图再次 OCR、可能重复记账；缓存图片每次多一份且不清理。参照 feimiao_open 分支 removeExtra。
16. **退款候选永远不被 ack，确认表反复弹出**（`auto_record_sheet.dart:93`）：退款条不能勾也不回传 id，每次回前台都弹；且未勾选的候选也被一并 ack 丢弃。

### 预算/统计口径
17. **V2 预算周期用 Duration 算术，DST 时区下抛 ArgumentError 白屏**（`budget_plan_v2.dart:340`）：悉尼等夏令时时区整个受影响月份主页/预算页崩溃；美东则把月计划额度多算一天。中国时区休眠。应改日历日算术（DateTime(y,m,d) 构造）。
18. **v17 前的遗留独立负支出行：预算口径丢弃、统计口径保留**（`budget_transaction_family.dart:61`）：同一张主页卡「支出」与「预算已用」相差负行金额，分类占比可超 100%。迁移应给这类行回填或两个口径统一。

### 数据库
19. **restoreBackupPackage 在完整性校验前就打开包内数据库**（`app_repository.dart:8482`）：篡改/损坏的 zip（校验和在包内可自洽重算）→ 未捕获 DatabaseException，恢复无声中断。校验先行 + backup_view 补 catch。
20. **deleteTag 多步写无事务、不 bump updated_ms**（`app_repository.dart:19384`）：中途被杀留孤儿标签引用；违反同步时间戳约定，未来增量同步会漏推。

### 未提交 diff（本批改动引入/激活）
21. 【未提交diff】**「今年/去年+月份」修复把跨月区间收窄成单月**（`query_range.dart:44`）：「今年1月到6月一共花多少」只喂 1 月数据给 AI，答案必错；「去年3月和今年5月对比」只喂今年 3 月。改动前（整年超集）能答对。_explicitMonth 应只在问题里恰好一个月份且无区间连接词（到/至/-/和）时生效。

## 三、低危（15 条）

1. **统计 rangeSummary 的日桶用 Duration 算术**（`statistics_engine.dart:382`）：DST 切换日少一天、之后的账串桶（中国时区不触发，合计仍正确）。
2. **只设一次性区间预算时主页「今日可用」恒显 ¥0.00 满环**（`budget_engine.dart:76`）：日粒度解析要求存在循环主预算，一次性预算被排除 → 兜底成 0，误导额度耗尽。
3. **v13 预算迁移失败被 catch(_){} 吞掉且永不重试**（`app_repository.dart:4151`）：瞬时 I/O 错误 → 预算配置无声消失（.pre-v 备份可手动救）。
4. **exportBackupPackage 全量读内存再压 zip**（`app_repository.dart:8360`）：500+ 张收据照片的老用户低端机导出 OOM，数据越多越备份不了。应流式写盘。
5. **markReimbursed 不触发固定支出 occurrence 复核**（`app_repository.dart:9237`）：与 refundTransaction 口径不一致，报销后固定支出仍显示足额发生。
6. **待报销页每行显示当前账本名而非账单所属账本名**（`reimburse_view.dart:146`）：总账本视角下无法分辨归属。按 tx.bookId 反查（参照 ai_chat_panel 做法）。
7. **bill_review _commit 无 try/catch/finally**（`bill_review_view.dart:481`）：sqlite 异常 → 按钮永久转圈、归类工作全作废（账户失效路径已有上游兜底，主要触发面是磁盘满类错误）。
8. **xlsx 导入只解析第一个非空 sheet**（`import_export_view.dart:499`）：说明页在前的文件必然报「没找到表头」。应逐 sheet 尝试直到解析成功。
9. **导出文件名直接拼账本名**（`import_export_view.dart:164`）：账本名含 `/` 等字符导出必失败。过滤非法字符即可。

12. **parseWithLLM/classifyMerchants 缺兼容模型回退**（`llm_entry_parser.dart:116`）：账号不支持主模型时查账正常、AI 记账每次静默降级到本地规则。复用 LlmQuery 的 _postWithModelFallback。
13. **share_intake 的 finally 自我重入，Navigator 为 null 时无限微任务循环**（`share_intake.dart:118`）：触发条件苛刻（根 Navigator 未挂载），一旦触发 100% CPU 冻结到 ANR。ctx 为 null 注册帧回调后应直接返回不走重入。
14. 【未提交diff】**normalizeMoneyAmount「绝不原样落库」改了一半**（`app_repository.dart:11349/11040`）：批量导入两条活路径仍原样落库超精度金额（12.345），与本批自立的不变量矛盾。（importTransactions:10874 是死代码，无调用方。）
