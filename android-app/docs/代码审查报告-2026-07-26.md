verifyFileSha256 在 expected 为空时直接 return true；而 _verifyAndInstall（app_update_flow.dart:155）只传 info.sha256，没有像进程内下载路径那样回退到 x-feimiao-sha256 响应头（app_update.dart:291-294 的兜底只存在于前台 download() 路径）。代码注释自证 v177 版本就发生过「sha256sum 转义反斜杠前缀污染字段」事故，sanitizeSha256 会把脏值清成空串——一旦再发生，后台下载（默认主路径）的 APK 将零完整性校验直接交系统安装器，下载截断/损坏的包也不会被拦（DownloadManager 成功状态之外无 sizeBytes 复核）。签名不同时系统会拒装，但同签名的错误字节流无任何防线。

**证据**：

```
app_update.dart L182: if (expected.isEmpty) return true;  app_update_flow.dart L155: final okHash = await AppUpdate.verifyFileSha256(path, info.sha256);（无响应头兜底）；app_update.dart L49-51 注释: 「发布链路出过『sha256sum 转义反斜杠前缀』污染字段的事故（v177）」
```

**修复建议**：后台下载完成后在 _verifyAndInstall 里补两道兜底：①info.sha256 为空时用 HEAD/GET 请求读 x-feimiao-sha256 头再校验；②校验不了 sha256 时至少比对 info.sizeBytes 与文件实际大小，都拿不到就提示用户「无法校验完整性」再决定是否安装。

<details><summary>核实者结论（confirmed）</summary>

代码事实全部属实：app_update.dart:181-182 verifyFileSha256 在 expected.isEmpty 时直接 return true；app_update_flow.dart:155 _verifyAndInstall 只传 info.sha256，无响应头兜底（该兜底只在前台进程内 download() 路径 app_update.dart:288-294 存在，且 DownloadManager 路径由原生侧下载、Dart 侧本来拿不到响应头）；sanitizeSha256(52-56) 会把脏格式清成空串，注释(49-51)自证 v177 出过 sha256sum 反斜杠前缀污染事故；checkAppUpdate(72-78) 确认 DownloadManager 是默认主路径，前台下载只是 ROM 禁用时的兜底；_verifyAndInstall 也没有用 info.sizeBytes 做长度复核；冷启动接续分支(47行)走同一函数，同样零校验。因此「sha256 字段缺失/被清洗后，后台下载的 APK 无任何应用层完整性校验就拉起安装器」成立。但后果表述略有夸大：现代 APK 的 v2/v3 签名块覆盖整个文件，截断或损坏的字节流会在系统安装器处被拒装（表现为安装失败而非装入坏包），DownloadManager 的 successful 状态本身也按 content-length 判完整，所以「同签名的错误字节流无任何防线」实际能通过的只有同签名密钥签出的另一个合法 APK（如发布链路发错包），不是任意损坏数据。属防御加固缺口+失败时用户体验差（下满整包后安装报系统级错误、无明确提示），P2 恰当。

</details>

### [P2] #32 app_version.dart 的 buildNumber 靠手工与 pubspec 同步，无 CI/测试守护，漂移会造成更新死循环

- **位置**：`android-app/lib/core/app_version.dart:6`

AppUpdate.check() 用 `info.versionCode > AppVersion.buildNumber` 判断是否有新版本（app_update.dart:84），cleanupObsoletePendingDownload 也用它清理挂起下载。但 buildNumber 是手写常量，CI 的 verify_release_apk.sh 只校验 APK versionCode 与 pubspec.yaml 一致，完全不检查 app_version.dart。漂移已实际发生过一次（提交 bedfa95 "fix: app_version.dart 同步到 v1.203.0+205"）：若 pubspec 升到 206 而 buildNumber 仍是 205，用户装完 206 后启动静默检查仍认为自己是 205，会永久循环弹「发现新版本」并反复下载几十 MB 的同版本 APK；同时已下载的挂起包永远不会被 cleanupObsoletePendingDownload 清理。

**证据**：

```
app_version.dart L6: static const int buildNumber = 205; app_update.dart L84: return info.versionCode > AppVersion.buildNumber ? info : null; verify_release_apk.sh L86 只读 pubspec.yaml: PUBSPEC_VERSION=$(awk '/^version:/...' "$APP_DIR/pubspec.yaml")
```

**修复建议**：加一个纯 Dart 单测：读 pubspec.yaml 解析 version，断言与 AppVersion.version/buildNumber 相等（flutter test 是硬闸门，漂移即红）；或改用 package_info_plus 运行时取真实 versionCode，彻底消灭手工同步。

<details><summary>核实者结论（confirmed）</summary>

亲验属实。app_version.dart:6 buildNumber=205 为手写常量；app_update.dart:84 用 info.versionCode > AppVersion.buildNumber 判断更新，175 行 cleanupObsoletePendingDownload 也依赖它。verify_release_apk.sh:86 只从 pubspec.yaml awk 取版本，grep 整个 ci/ 目录（release_gate.mjs、release_gate.test.mjs、publish_update.sh）与 test/ 均无对 app_version.dart 的任何校验或测试。漂移史实确认：git log 中 3295b37「bump: v1.203.0+205」之后紧跟 bedfa95「fix: app_version.dart 同步到 v1.203.0+205」，即确实漏同步过一次靠人工补救；仅有文档级 runbook（COMMIT_AND_PUBLISH_RUNBOOK.md:80 的 sed 命令）无自动守护。唯一小偏差：下载需用户在弹窗点「下载更新」确认，不会无人值守反复下载，但每次启动静默检查（app_update_flow.dart:18-69）都会弹「发现新版本」的死循环描述属实。P2 合理。

</details>

### [P2] #33 更新 APK 存外部存储，Android 10 及以下存在校验-安装之间被第三方替换的窗口

- **位置**：`android-app/android/app/src/main/kotlin/com/qingji/qingji/MainActivity.kt:318`

后台下载目标是 getExternalFilesDir(DIRECTORY_DOWNLOADS)（MainActivity.kt:318），前台兜底下载写 getExternalCacheDirectories().first（app_update.dart:210-212）。Android 11 起 Android/data 对其他应用不可见，但 Android 7~10 上持有 READ/WRITE_EXTERNAL_STORAGE 的任意应用都能读写其他包的 Android/data 目录：Flutter 侧 verifyFileSha256 校验通过后到系统安装器实际读取 FileProvider URI 之间存在时间窗，恶意应用可在此窗口替换 APK（经典 verify-then-install TOCTOU）。同签名要求会挡掉大部分攻击，但降级为「校验形同虚设」。用户当前设备若是 Android 11+ 则不受影响，属潜在隐患。

**证据**：

```
MainActivity.kt L318: val dir = getExternalFilesDir(android.os.Environment.DIRECTORY_DOWNLOADS)；app_update.dart L210-212: final externals = await getExternalCacheDirectories(); ... dir = externals.first; app_update_flow.dart L155-166: 校验后再 AppUpdate.install(File(path))
```

**修复建议**：安装前把校验通过的 APK 先拷贝/rename 到内部私有目录（context.cacheDir 或 filesDir，update_file_paths.xml 已含 cache-path），对内部副本做 sha256 校验并从内部路径走 FileProvider 安装，消除外部可写窗口。

<details><summary>核实者结论（confirmed）</summary>

证据逐条属实：MainActivity.kt:318 `getExternalFilesDir(android.os.Environment.DIRECTORY_DOWNLOADS)`（DownloadManager 目标也是 setDestinationInExternalFilesDir，330-334 行），即共享外部存储的 Android/data/<pkg>/files/Download；前台兜底 app_update.dart:210-212 `getExternalCacheDirectories().first` 同为外部 app-specific 目录。app_update_flow.dart:155-166 确认时序：verifyFileSha256 通过后才 `AppUpdate.install(File(path))`，MainActivity.kt:411-425 installApkFile 用 FileProvider+ACTION_VIEW 交给系统安装器——从校验完成到安装器实际读取 URI 之间存在真实时间窗。系统版本前提成立：build.gradle.kts:51 `minSdk = flutter.minSdkVersion`（21/24，远低于30），Android 7-10 设备在支持范围内，而这些版本上持有存储权限的第三方应用确实可写其他包的 Android/data（scoped storage 到 Android 11 才强制隔离，Android 10 可用 requestLegacyExternalStorage 绕过）。报告者对影响的评估也准确克制：同包名替换会被系统同签名校验挡下，但换包名的恶意 APK 会以新装应用形式弹安装确认，用户在预期『更新』的心流里可能照点，SHA 校验在该窗口内确实形同虚设。攻击前提高（本机已装恶意应用+旧系统+用户确认安装框），修复也简单（下载到内部存储 getFilesDir/cacheDir，FileProvider 同样可服务），P2 恰当。

</details>
