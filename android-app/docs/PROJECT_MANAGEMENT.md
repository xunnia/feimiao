## 2. 项目章程

### 2.1 用户问题

肥喵记账解决的不是“录入一条数据库记录”，而是让普通用户能够低负担地完成以下闭环：

- 快速记下收入、支出、退款、报销和转账；
- 知道本周期花了多少、还能安排多少；
- 看懂账户、资产、负债和净资产，而不需要会计背景；
- 导入外部账单后仍能核对、纠错和回退；
- 使用 AI 时明确知道数据发给哪个服务商，并能控制模型；
- 在任何统计页看到一致、可解释、可追溯的数字。

### 2.2 产品定位

**定位**：个人财务工具，外观可爱，交互安静，账务严谨。

**核心价值排序**：

1. 数据不丢、金额算对；
2. 结果可解释、状态诚实；
3. 高频记账足够快；
4. 同类交互保持一致；
5. 增强能力按需出现，不把专业复杂度推给所有用户。

### 2.3 当前范围

已进入产品范围：

- 手动、快捷、AI、自动和定时记账；
- 退款、报销、转账、导入复核；
- 多账本、分类、标签、账户和存钱目标；
- 预算计划、周期、固定承诺与专项追踪；
- 统计、报告、Widget 和 AI 查账；
- 资产物品、估值、处置、账户校准和净资产核对；
- 完整本地备份、导入导出和应用内更新；
- 多 AI 服务商、模型管理和隐私授权。

当前限制或暂缓：

- 首要币种仍为 CNY；严格多币种折算不是当前默认能力；
- 银行账户自动聚合、证券交易引擎和企业会计不在近期范围；
- 多人共享账本方向已解锁，但真实共享需要账号、后端、同步冲突和权限模型，必须作为独立项目立项；
- iOS 不与 Android 功能批次顺带交付；
- 模拟器、截图或真机验收是否执行，以用户对当批的明确要求为准。

### 2.4 长期锁定原则

- **本地优先**：核心账本和计算不依赖远端服务才能使用；AI 与更新服务是可选外部能力。
- **统计单一真相源**：页面不能各算一套，任何指标先服从统计口径合同。
- **未知不能伪装为 0**：缺日期、缺汇率、缺估值、冲突或覆盖不全时返回 partial/unavailable 等真实状态。
- **冲减归原家族**：退款、报销和红冲不能作为无来源的新收入漂移到其他月份。
- **账户余额全局**：账户余额不因当前账本筛选而消失；归档不等于从净资产删除。
- **UI 同类同设计**：能用标准件时不得在页面另造第二套。
- **隐私按接收方授权**：切换向不同 AI 服务商发送数据时必须重新取得同意；密钥不进入普通备份、日志或 Git。
- **版本只前进**：Android versionCode、数据库版本和计算口径版本各自单调演进，不能混为一个编号。

## 5. 代码与架构地图

### 5.1 目录所有权

| 路径 | 职责 | 修改注意 |
|---|---|---|
| `lib/core/` | 纯领域逻辑、AI、预算、资产、统计、备份、安全、更新 | 优先写纯逻辑测试；不要依赖页面状态 |
| `lib/data/app_repository.dart` | SQLite schema/迁移、持久化、聚合读写、设置和跨域协调 | 高风险中心；变更要有 Repository/迁移测试 |
| `lib/views/` | 页面与业务流程编排 | 不得自行复制统计或账务公式 |
| `lib/widgets/` | 全局公共控件和交互标准件 | 同类需求先复用；新增件需证明跨页面价值 |
| `lib/theme/` | 主题、颜色、字体、尺寸、动画令牌 | 服从 UI 标准；禁止页面写死全局颜色 |
| `android/` | Android Manifest、签名接线、Worker、Widget、原生通道 | 需 Android 构建和原生行为验证 |
| `test/` | 单元、Widget、Repository、迁移、性能与回归测试 | 数据高风险改动必须补反例 |
| `ci/` | Release 验包、更新发布、门禁脚本 | 脚本改动要跑自身测试和语法校验 |
| `docs/` | 管理、规范、交接、审计和专项方案 | 区分 active 与 archive |
| `outputs/` | 历史 UI/验收证据 | 不是构建缓存；不要批量删除 |

### 5.2 当前架构约束

- `AppRepository` 是当前集中式数据入口，能保证一致性，但文件很大、跨域耦合高。新增共享公式优先落 `core` resolver，再由 Repository 适配；不要继续把页面算法塞回 Repository。
- Provider 负责应用状态注入；异步调用必须处理 mounted、重复提交和数据库未就绪状态。
- SQLite 是本地财务真相源。迁移必须幂等、事务化、可从旧版本连续升级，并在风险升级前保留备份。
- WorkManager/通知/Widget 属于后台消费者，必须读取与前台相同的持久化真相，不能依赖仅存在内存的页面状态。
- AI provider 身份是 `(providerId, model)`，不能只用模型名；相同模型名在不同服务商下必须保持独立。

## 6. 数据、统计与迁移治理

### 6.1 金额与事件

- 持久化和核心计算优先使用整数分或 Decimal；禁止用二进制浮点直接累加财务金额。
- 原交易与退款/报销组成交易家族；消费统计读取家族净额，退款到账同时还要进入账户结算事件。
- 归属日期、结算日期、估值日期、知识截止时间是不同轴，不能用单一 `date` 替代全部含义。
- 转账、校准、资产处置和负债变化不能为了“看起来有记录”伪造普通收入/支出。

### 6.2 结果质量

所有跨域结果应能区分：

- `available/current_exact`：数据和口径完整；
- `partial`：可给出部分结果，同时列明遗漏原因；
- `unavailable`：缺少关键证据，不能计算；
- `conflict/inconsistent`：来源互相矛盾，禁止静默挑一个；
- `notApplicable`：该指标对当前对象不适用；
- `stale`：结果曾正确，但输入或口径已更新。

UI 禁止把这些状态通过 `null ?? 0` 统一显示成 0。

### 6.3 数据库迁移门禁

每次 DB 版本变更必须满足：

1. 明确旧版本、目标版本、字段默认值和 legacy 语义；
2. 不伪造无法证明的日期、余额、汇率、估值或账户归属；
3. 一次升级可连续执行所有中间 migration；
4. migration 在事务内完成，失败不留下半套 schema；
5. 至少覆盖“旧库升级、重复初始化、备份恢复后升级、核心金额前后等价”；
6. 高风险迁移前自动创建可识别的 `pre-v*` 备份；
7. 降级安装不保证安全，回退方案必须说明 APK 与数据库是否兼容。

### 7.1 需求记录模板

每个需求至少记录：


当用户连续发送多条并明确说“先记录、说开始再做”时，只记录和澄清，不提前编辑代码。

### 7.2 优先级

| 优先级 | 定义 | 示例 |
|---|---|---|
| P0 | 数据损坏、金额错误、隐私泄露、无法启动/安装、签名或发布回退风险 | 跨月退款算错、API Key 进入备份、迁移破坏余额 |
| P1 | 核心流程不可用或用户明确的高优先级体验问题 | 模型选择看似成功但实际无效、记账保存失败 |
| P2 | 明显影响效率、一致性或可理解性，但有可用绕行 | 页面控件不统一、说明层级混乱 |
| P3 | 增强、探索、差异化和长期能力 | 投资层、复杂自动化、多人共享后端 |

同优先级下按“数据正确性 > 隐私安全 > 高频主流程 > 一致性 > 装饰性”排序。

### 7.3 Definition of Ready

进入开发前应满足：

- 用户目标和成功标准可复述；
- 已读取相关现有代码、规范和最近交接；
- 已分清修复现状还是新增产品能力；
- 统计/日期/账户/币种范围明确；
- 有参考图时已确认参考的是结构、风格还是逐像素目标；
- 高风险数据变更已有迁移、备份和回滚思路；
- 与同批其他任务边界清楚，避免一个页面同时被多人改。

### 7.4 批次与 WIP

- 默认一个批次解决一个完整用户问题；紧密耦合的两个阶段可合并一个 APK。
- 同一时间最多一个 DB migration 批和一个发布候选，避免无法定位回归。
- 给出上一批推送/提交命令后，不在用户执行期间开始破坏性大改。
- 任何批次必须做到“实现、验证、文档”一起结束，不能把半成品交给下一会话猜。
- 用户要求连续开发且每两批一个 APK 时，构建完成后继续下一批，不等待安装反馈；若反馈到来，优先判断是否阻断当前工作。

## 8. 状态流转与验收

```text
Inbox -> Clarified -> Ready -> In Progress -> Code Complete
      -> Automated Verify -> APK Verify -> User Accept -> Released -> Done
                         \-> Fix Required -> In Progress
```

状态定义：

- **Code Complete**：代码写完，不代表通过测试。
- **Automated Verify**：规定的 analyze/test 通过。
- **APK Verify**：Release 构建、身份、对齐、签名和哈希通过。
- **User Accept**：用户在要求的真机路径确认体验和数据。
- **Released**：远端版本指针和可下载产物已验证；本地 APK 不得写成已上线。
- **Done**：实现、验收、文档和发布状态描述一致。

## 9. 质量策略

### 9.1 按风险选择验证

| 变更 | 最低验证 |
|---|---|
| 文案/单一布局 | format、相关 analyze、必要 Widget 测试、文字溢出检查 |
| 纯领域逻辑 | 单元测试，包含反例和边界 |
| Repository/SQLite | 单元测试 + FFI Repository 测试 + 迁移等价测试 |
| 统计/预算/资产 | 口径反例、整数分守恒、退款/日期/范围/partial 状态 |
| AI provider/隐私 | 持久化重启、同名模型、切换服务商、无 key、授权重置、密钥净化 |
| 页面公共组件 | 受影响页面回归、窄屏/大字号/深色主题 |
| Android 原生/后台 | Android 构建、通道/Worker/通知/Widget 专项测试 |
| Release | analyze、完整或经批准的测试范围、Release build、aapt、16 KiB、V2 签名、证书和 SHA256 |

Windows 上 Repository 测试使用 `--concurrency=1`，避免多个测试文件争用全局 SQLite 测试路径产生假失败。

### 9.2 Definition of Done

一个功能只有同时满足以下条件才可标 Done：

- 行为满足需求，异常/空态/加载/禁用/删除/重启状态完整；
- 没有另造统计公式或第二套 UI；
- 新逻辑有与风险相称的测试，旧回归没有被删除来“变绿”；
- analyze 无 error；新 warning 必须解释或处理；
- DB/文件/隐私副作用已真实验证；
- 用户要求 APK 时，Release 身份、16 KiB、签名和哈希已验证；
- 当前状态、changelog 和必要规范已更新；
- 未把 APK、缓存、密钥、日志或中间截图误提交；
- 无仍在运行且属于本任务的构建/测试进程。

### 9.3 当前验证债务

## 10. 分支、提交与版本

### 10.1 分支

- 功能开发可使用 `feature/*`、`codex/*` 或 `claude/*`。
- GitHub Android CI 会对相关分支执行校验和构建。
- 当前 CI 只有 `codex/feimiao-p0-fixes` push 会使用固定签名并发布 `android-latest`；其他分支成功构建不等于已发布。
- 合并/推送前先确认目标分支，不得根据旧交接里的分支名猜测。

### 10.2 提交

- 工作树可能包含用户和其他代理改动；禁止 reset/checkout 覆盖未知修改。
- 精确 stage 源码、测试、文档、版本和必要原生文件，禁止 `git add .`。
- APK、AAB、密钥、日志、构建目录和本地归档永不进入功能提交。
- 一个提交应对应一个可解释批次；迁移、功能和测试应同提交或有清楚依赖顺序。

### 10.3 四类版本

| 版本 | 示例 | 规则 |
|---|---|---|
| versionName | `1.261.0` | 用户可见，按当前项目约定逐批递增 |
| versionCode | `275` | Android 覆盖安装身份，只增不减 |
| buildTag | `b0827-275` | 真机快速确认包，日期 + versionCode |
| DB version | `47` | 只在 schema/迁移变化时增加，不跟每个 APK 增加 |
| calculationVersion | `1` | 统计口径合同版本，不能用 DB/versionCode 代替 |

版本至少同步：`pubspec.yaml`、`lib/core/app_version.dart`、`lib/build_info.dart`、本机 `android/local.properties`。APK 内部版本以 aapt 结果为最终证据。

## 11. 构建、发布与回退

### 11.1 发布前机械流程

完整命令和故障处理以 `COMMIT_AND_PUBLISH_RUNBOOK.md` 为准，顺序不得颠倒：

1. 冻结范围并确认工作树没有半成品；
2. 同步版本；
3. format/analyze/test；
4. `flutter build apk --release --no-pub`；
5. 验证包名、versionName/versionCode、min/target SDK；
6. `zipalign -c -P 16`；
7. `apksigner verify --verbose --print-certs`；
8. 核对唯一签名者和固定证书 SHA256；
9. 计算并记录源 APK 与归档 APK SHA256；
10. 用户明确授权后才推送/发布；
11. 发布后验证远端 `version.json` 和下载产物哈希。

### 11.2 回退原则

- 本地只保留“当前候选 + 上一候选”两个 APK，作为安装对照和有限回退证据。
- **APK 可安装不等于数据库可降级**。如果新版本已把用户 DB 升级，旧 APK 不认识新 schema 时不能直接覆盖回退。
- 带迁移版本优先使用升级前自动备份恢复，而不是盲装旧 APK。
- 签名必须一致，否则 Android 会要求卸载，导致本地数据风险。
- 线上更新采用更高 versionCode 和原子版本指针；不得用同 versionCode 不同哈希覆盖。

## 14. 产物与磁盘维护

### 14.1 保留规则

必须保留：

- 源码、测试、规范、交接和 changelog；
- 当前 APK 与上一 APK；
- 当前实际签名 keystore、备用 keystore 和 `key.properties`，并建议做仓库外加密备份；
- 用户数据库、自动备份、迁移前备份和恢复兜底；
- `outputs/` 中已经纳入版本管理的关键验收证据；
- Git refs、工作树和所有可达提交。

可安全再生成、空间不足时可删：

- `android-app/build/`；
- `android-app/.dart_tool/`；
- `android-app/android/.gradle/`；
- Flutter、模拟器和 Playwright 运行日志；
- 已有当前/上一候选覆盖的更旧本地 APK 副本。

禁止直接手删：

- `.git/objects` 内任意文件；只运行标准 `git gc`；
- `android/app/*.jks`、`android/key.properties`；
- 不知道来源的数据库、`.bak`、媒体或导入文件；
- 注册中的 `.claude/worktrees` 或其他 Git worktree；
- `outputs/` 仅因为名字像输出目录就整目录删除。

### 14.3 建议维护周期

- 每次本地出包：归档新 APK，确认哈希后只保留当前+上一版。
- 每周或磁盘异常：检查一级目录大小，删除可再生 build/cache。
- 每月或大量变基后：先 `git count-objects -vH`，必要时运行标准 `git gc`。
- 每次提交前：检查 Git status，确认没有 APK、密钥、日志和构建目录。
