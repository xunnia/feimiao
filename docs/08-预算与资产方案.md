## 0. 结论先行

### 0.1 有数到底做得怎么样

**有数在“物品资产”这个细分方向里做得很好，但它不是完整个人资产管理的答案。**

它做好的不是银行账户、信用卡、贷款和投资组合核对，而是把“买过的东西”做成一个有照片、有陪伴时间、有日均花费、有目标进度、有退出结算的数字陈列柜。它回答的是：

- 我拥有什么？
- 这件东西用了多久？
- 买得值不值？
- 是继续用、闲置、卖掉，还是退役？

它最强的留存机制是：**用户录入一次，日均花费会随着时间自动下降，系统持续产生可回看的变化。**传统记账反复告诉用户“又花了多少钱”，有数会告诉用户“这台手机已经降到每天 8 元”。这种变化比静态净资产表更容易让用户回来，但它不自动证明“确实用值了”：物品即使一直闲置，分母也会变大，因此肥喵不能只因时间过去而庆祝或给价值判断。

但是它的日均成本和总资产净值不能直接当作严谨财务口径：

- `购入价 / 持有天数` 即使物品一直吃灰也会下降，所以它不是利用率。
- 普通物品的二手价值依赖主观估值，长期不更新会失真。
- 物品购入价、当前估值、持有成本和财务净资产是四个概念，不能混成一个数字。

因此，肥喵应学习有数的**照片陈列、低维护反馈和生命周期闭环**，不能拿有数的页面直接替换整个资产管理。

### 0.2 新版产品骨架

资产管理固定为一个入口、三个页面级视图：

```text
资产管理                                      [＋]
[ 总览 ] [ 资金 ] [ 物品 ]

总览：我现在整体有多少，数字是否可信，有什么待处理
资金：账户、投资余额、权益、负债和余额校准
物品：照片陈列、日均持有花费、保值率和生命周期
```

底层可以关联，用户心智必须分开：

1. **钱的资产**：账户余额、投资余额、权益、负债、净资产、校准和趋势。
2. **拥有的东西**：实物照片、购买账单、持有时间、使用状态、出售和退货。

预算继续是独立域：

- 预算回答“这段时间的钱准备怎么花、还能花多少”。
- 资产回答“钱和价值现在在哪里、发生了什么变化”。
- 同一笔购买可以同时进入预算支出并生成一个物品，但不能重复计算或互相抵消。

### 0.3 V2.1 相比 V2 的关键修正

1. 保留“总览 / 资金 / 物品”三视图，不推翻已经成立的产品骨架。
2. 一笔经济事件允许同时具有消费归属日 `attribution_date` 和账户结算日 `settled_at`；退款不再用一个日期兼顾两套互相冲突的统计。
3. 余额校准改为绝对 `target_balance` 锚点；差额只用于保存前解释，不作为后续余额真相。
4. 预算浏览固定区分“本周期 / 自然月 / 自然周 / 自定义”，任何按钮不再随计划类型改变语义。
5. 本周期改预算区分“把周期总额改为 X”和“在剩余期间追加/减少 Y”，最终都保存为本周期绝对目标额，禁止拼接新旧日均额度反推周期总额。
6. 同一账本同一日期最多一个日常主计划；专项明确改名为“专项追踪”，可以重叠观察但绝不能与主计划相加。
7. 物品统一使用净购置成本、累计持有投入、可变现净估值和最终净成本四个基数，退款只扣一次。
8. 归档只改变展示可见性；出售、退货、报废、丢失、赠送、结清才改变经济状态和计入净资产范围。
9. 自动快照是可重算的 `computed_snapshot`；只有明确核对且记录覆盖范围的结果才是 `verified_checkpoint`。
10. 修正总资产、资金净值、总负债和净资产的集合与算术，所有组成项必须互斥且可下钻。
11. “今日可用”只在能识别尚未发生的固定支出时给出可自由安排额；否则降级为诚实的日均参考，不冒充安全现金余额。
12. 物品日均持有花费是时间摊薄指标，不代表利用率或收益，不因单纯时间流逝触发“更值了”的庆祝。
13. 非 CNY、未知估值、缺少校准等情况显示为“未计入 / 不可计算”，绝不静默当作 0。
14. 主页、预算、统计、Widget、月报、AI 洞察和快速记账统一依赖专门的统计口径标准与 resolver，不再各自解释退款、笔数和同期比较。

## 1. 研究方法与证据边界

本次研究使用三类证据：

1. Apple App Store 官方产品描述、版本说明、截图和 Apple 托管评论。
2. 产品官方帮助中心、官方 FAQ 和官方更新日志。
3. 肥喵当前代码、数据库 schema、Repository 行为和测试。

本文将结论分为：

- **FACT**：官方资料或代码直接支持的事实。
- **INFERENCE**：根据产品结构、评论和使用成本作出的产品判断。
- **RECOMMENDATION**：结合肥喵定位给出的取舍，不冒充竞品事实。

限制：

- App Store 可见评论由 Apple 选择和排序，不能代表完整用户样本。
- 有数可见评论有重复文案，不能把每条都当作独立证据。
- 评分数不等于下载量、活跃用户数或留存率。
- 本次没有安装所有竞品，未把未验证的具体交互和计算公式写成事实。
- Bing 搜索出现验证码，搜索摘要没有被用作证据。
- Apple 旧 RSS 评论接口返回成功但没有评论条目；网页评论接口直接调用受限，本文只引用 App Store 页面可见内容。

## 2. 竞品深度结论

## 2.1 物品资产型

截至 2026-07-12，中国区 App Store 数据：

| App | 核心定位 | 评分 / 评分数 | 最值得学 | 主要维护风险 |
|---|---|---:|---|---|
| 有数 | 数字陈列、日均成本、卖出复盘 | 4.6 / 3923 | 照片优先、被动正反馈、目标成本 | 估值口径不透明；日均成本不等于利用率 |
| 持物 | 结构化资产台账、维护与估值 | 4.8 / 323 | 维护费用、结构图、批量管理、本地优先 | 容易向单位、库存、贵金属行情扩张 |
| 知我记物 | 收藏展示、提醒、回顾 | 4.5 / 50 | 多种录入、保修/保质期、回顾卡片 | 字段和视图过多，物品多后性能与筛选压力大 |
| 与物 | 日均/次均成本、极简物品管理 | 4.7 / 33 | 功能克制、附加费用、退出成本 | 次均成本需要持续打卡；样本量较小 |

### 有数：为什么打中用户

FACT：官方主轴集中在“目标日均成本、服役时间、持有成本、卖出盈亏、AI 抠图和数字陈列柜”。官方截图的首屏也是照片网格，不是账户表格；每件物品直接显示购入价、持有天数、日均花费和目标进度。

FACT：截至访问日，有数中国区约 3923 个评分，约为持物、知我记物、与物三者评分数之和的 9.66 倍。它只能说明市场吸引力明显领先，不能说明真实留存。

INFERENCE：有数的核心循环是：

```text
拍照/录入一次
    ↓
每天自动增加持有天数
    ↓
日均花费下降、目标进度上升
    ↓
用户得到“用得越来越值”的反馈
    ↓
继续使用 / 决定卖出 / 下次购买前回看
```

这个循环的价值在于“反馈自动发生”，而不是要求用户天天维护。

### 物品类产品共同的五个任务

| 用户任务 | 真正要回答的问题 | 推荐频率模型 |
|---|---|---|
| 盘点 | 我到底拥有什么，放在哪，有没有重复买 | 初次高峰，之后低频 |
| 判断值不值 | 用了多久，每天或每次花了多少 | 高频查看，低频录入 |
| 保管 | 发票、保修、保养何时到期 | 低频但高价值 |
| 购买前决策 | 手里的东西还没用够本，要不要再买 | 购买前偶发 |
| 退出复盘 | 退货、卖掉、赠送、报废后实际花了多少 | 低频但形成闭环 |

### 已暴露的真实痛点

- 有数用户要求套装部分卖出、购买平台字段；这会迅速引出组件、分摊成本和部分处置，首版不应贸然做。
- 持物用户认为逐次记录使用次数太复杂，更希望“常用 / 偶尔 / 闲置”这类低维护表达。
- 知我记物用户在数百件物品后遇到性能、筛选和信息密度问题，说明陈列柜必须懒加载、搜索和筛选先于更多视图。
- 与物用户指出附加费用在不同页面口径不一致，说明购入成本、附加成本、估值和出售收入必须共用一套公式。
- 数据安全是物品类的信任底线，照片若不能完整备份，功能越精美风险越大。

## 2.2 综合资产和预算型

| App | 真正强项 | 核心任务 | 维护负担 | 对肥喵的价值 |
|---|---|---|---|---|
| 钱往 | 国内记账 + 股票基金 + 债务 + 净资产 | 快速记账、看现金流和投资盈亏 | 中 | 学资产聚合和投资/日常并存，避免长页面和行情依赖 |
| MoneyWiz | 专业账户台账、核对、贷款、投资、多币种 | 导入、核对、预算、贷款拆分 | 中高 | 学账户详情、校准/核对和归档，不照搬专业 ERP 复杂度 |
| Monarch | 自动聚合、家庭协作、月度规划 | 审核新流水、看净资产、做月预算 | 低中 | 学总览和待审核；国内首版不做银行连接 |
| YNAB | 主动消费决策和零基预算方法 | 每日调整计划、每周核对、月末复盘 | 高且有意为之 | 学“账户是位置、预算是用途”，不强迫肥喵用户执行整套仪式 |
| Actual Budget | 本地优先、信封预算、off-budget 资产 | 手动同步、核对、只分配已有现金 | 高 | 学 on/off-budget 边界和可审计核对，不学自托管 UX |
| Cashew | 月/周/自定义预算和清晰图表 | 手动记账、看周期进度 | 中低 | 证明浏览周期与计划周期应该解耦 |

### 钱往

FACT：钱往把快速记账、预算、账户净资产、股票基金行情、每日盈亏、债务和多币种放在同一产品里。其可见评论中，“多资产管理”和“兼顾记账与投资”直接影响付费意愿。

INFERENCE：它的优势是覆盖完整，风险也是覆盖完整。评论同时出现股票菜单对非投资用户无关、投资列表过长、希望截图导入、信用卡分期复杂等问题。肥喵应学习“资金资产和日常账单底层相连”，不应立即复制证券行情和长持仓页面。

### MoneyWiz

FACT：MoneyWiz 支持手动账户、银行连接、简单/高级核对、余额调整、贷款本金和利息拆分、投资与多币种。高级 reconciliation 会要求期初、期末、日期和逐笔状态。

INFERENCE：它适合专业用户，但把这套完整心智放进肥喵会伤害“可爱、简单、好上手”的定位。最值得借鉴的是：账户必须有详情、历史、归档和明确核对入口。

### Monarch

FACT：Monarch 的手工账户官方建议用于车辆、珠宝、房产等“变化不频繁”的对象；月度预算与账户余额分工明确；新同步交易有 Needs Review；Goals 把真实余额进度和预算计划贡献分开。

INFERENCE：资产更新本来就应该低频，首屏应帮助用户发现“哪里需要处理”，而不是鼓励天天编辑估值。肥喵可以学待审核和目标双口径，不做银行连接首版。

### YNAB

FACT：YNAB 官方区分 daily、weekly/payday、turn-of-month 和 monthly/quarterly tracking routine。它明确说明“账户表示钱在哪里，预算分类表示钱要做什么”，Tracking accounts 只进入净资产、不进入预算，并反复提醒 Tracking 会增加视觉、心智和维护负担。

INFERENCE：预算的高频价值是做消费决定，资产的价值是低频确认位置和变化。两个域共享数据，但不能共用一个操作模型。

## 3. 用户真正反复使用的核心功能

频率不是为了堆入口，而是决定首屏优先级。

| 频率 | 用户问题 | 产品应提供 | 不应强迫 |
|---|---|---|---|
| 每天 / 每周 | 还能花多少？最近有没有记错？余额是否异常？ | 有条件的可自由安排额/预算日均参考、最近账单、待审核 | 每天更新房产/物品估值 |
| 每周 / 每月 | 净资产和负债怎么变了？该还什么？ | 全局净资产、流动资产、待还款、核对覆盖和估算趋势 | 逐笔专业 reconciliation |
| 每月 / 季度 | 手工账户是否需要校准？投资/物品估值是否过期？ | 轻量校准、估值日期、复核提醒 | 强制统一复核周期 |
| 购买发生时 | 这笔耐用品要不要变成物品记录？ | 从账单两步加入、自动带入金额日期 | 重填一整套资料 |
| 生命周期事件 | 退货、卖出、收回、报废后怎么算？ | 关联原账单和账户、完整事件链、可撤销 | 另造互不相认的记录 |
| 低频复盘 | 哪些东西最值、哪些长期闲置？ | 日均持有花费、保值率、状态和筛选 | 复杂库存和十几种图表 |

产品原则：

1. 高频页面负责“看懂和发现问题”。
2. 中频操作负责“快速校准和确认”。
3. 低频详情负责“完整生命周期”，不挤进列表行。
4. 一次录入后能自动产生的反馈优先于需要持续打卡的指标。
5. 任何资产数字都要能追到来源、日期和事件。

## 4. 明确借鉴与明确不借鉴

## 4.1 从有数和物品类产品借鉴

- 照片是物品首要识别，不是表单最后一个附件路径。
- 宽度允许时两列陈列比银行式 ListTile 更适合物品；窄屏和大字体自动单列。
- 首屏直接给持有天数、日均持有花费和状态。
- 目标日均花费可以提供，但属于行为反馈，不进入净资产公式。
- 退货、出售、报废、丢失和赠送必须有经济终止状态和最终复盘；归档只是展示隐藏，不属于结束状态。
- 从账单、照片和订单降低录入成本，比增加更多字段更重要。
- 没有待处理事项时整个区块消失，不用空卡占位。

## 4.2 不借鉴

- 不把购入价、当前估值、日均花费和净资产混成一个“总资产”。
- 不把“持有天数长”说成“使用频率高”。
- 不默认要求每件物品逐次打卡。
- 不在首版做套装拆分、部分出售、复数库存和单位换算。
- 不把 AI 抠图设为必经步骤；它是录入和展示增强，不是数据地基。
- 不做贵金属、外币、股票行情和自动估值首版。
- 不先做分享海报、贴纸墙和社交玩法。
- 不用高饱和荧光绿照搬视觉；继续服从肥喵六主题和颜色铁律。

## 4.3 从综合财务产品借鉴

- 账户有详情、近期活动、校准日期和归档。
- 顶部同时回答净资产、流动资产、负债和可信变化。
- 预算和账户分工：账户是钱的位置，预算是钱的用途。
- 手工资产显示“上次核对时间”，不要求每日更新。
- 新导入/AI 结果进入待审核，比一开始上 cleared/locked 更适合肥喵。
- 存钱目标和债务目标的实际进度来自真实余额；预算只表达本周期计划贡献。

## 4.4 不借鉴综合产品的重能力

- 银行自动聚合首版。
- MoneyWiz 全套贷款摊销、证券交易和多预算信封转移。
- YNAB 强制零基预算与每日核账仪式。
- Monarch 多预算模式和复杂 Goals 分配引擎首版。
- Actual 的自托管、密钥和手动银行连接 UX。
- 静默修改历史余额，或把校准差额伪装成普通收入/支出。

## 5. 统一产品架构

## 5.1 三层关系

```text
账单流水（发生了什么）
  ├─ 预算：这笔支出是否在计划内、还剩多少
  ├─ 资金：哪个账户减少、哪个负债变化
  └─ 物品：是否形成一个可持续使用和处置的东西

预算 = 流量计划
资金/物品 = 存量状态
账单/事件 = 两者之间的桥
```

同一事件可以被不同视图观察，但不能只靠一个日期或一个金额字段承担全部语义：

| 统计轴 | 回答的问题 | 主时间 | 典型事件 |
|---|---|---|---|
| 消费统计 | 这段时间实际消费了什么？ | `attribution_date` | 普通支出、附着原单的退款净额 |
| 账户现金流 | 钱在什么时候真正进出账户？ | `settled_at` | 支付、退款到账、转账、贷款还款、出售收款 |
| 预算执行 | 哪个计划周期被占用了多少？ | `attribution_date` + 计划周期 | 计入预算的净支出 |
| 资产状态 | 某时点拥有多少价值和负债？ | 事件发生时间 / 估值时间 / 校准锚点 | 余额、估值、权益、负债、处置 |

普通账单的两个日期通常相同；跨期退款、延迟到账、预授权转正式扣款等场景可以不同。任何页面都不能各算一套公式，具体合同见 `07-统计口径标准.md`。

## 5.2 资产范围

- 资产总览固定全局，不随抽屉当前账本变化。
- 资金账户和负债是全局对象。
- 实物、权益保留所属账本标签，可筛选，但筛选不改变顶部全局总额。
- 非 CNY 没有汇率时分币种展示，不静默相加；顶部必须写“人民币口径，未含 N 项外币资产/负债”，不能仍叫无条件完整净资产。
- 存量 `include_in_net_worth` 原样保留。
- 新增普通数码、家电、工具时默认不强迫计入净资产；房产、车辆、贵重物品、收藏品可推荐开启，但最终由用户确认。
- 归档只改变列表可见性，不得静默关闭 `include_in_net_worth`。非零账户、未结权益和未结负债即使归档，仍按经济状态计入合计。
- 多人共享账本上线后，资产总览默认仍是当前用户的私有全局域；共享成员只能看到被明确共享的账本流水和资产对象，不能因进入共享账本暴露个人存款或房贷。

## 5.3 顶部净资产的表达

保留一个主指标，但必须拆出来源：

```text
净资产                                      截至今天
¥216,800

资金资产 ¥190,000     计入的物品估值 ¥78,400
资金净值 ¥138,400     总负债 ¥51,600
总资产 ¥268,400
较上次完整核对 +¥3,240 · 2026/6/30
```

规则：

- `资金资产 = 账户正余额 + 投资余额 + 权益资产`，三个集合互斥；投资账户不能同时进入账户正余额和投资余额。
- `总资产 = 资金资产 + 明确计入净资产的实物可变现净估值`。
- `资金净值 = 资金资产 - 总负债`。
- `净资产 = 总资产 - 总负债 = 资金净值 + 计入的物品估值`。
- 本示例校验：`42,000 + 96,000 + 52,000 + 78,400 = 268,400`，再减负债 `51,600`，净资产为 `216,800`。
- 物品页始终可以显示物品购入成本和当前估值，不等于都进入主净资产。
- “较上次完整核对”只比较两个覆盖范围一致的 `verified_checkpoint`；不能拿“本月收入 - 支出”或任意自动快照冒充资产变化。
- 若只有部分账户核对，显示“已核对 X/Y 项”而不是全局可信变化；没有完整核对时隐藏比较值并显示“尚未完成完整核对”。
- 实物估值显示估值日期和来源；新补录的旧估值不能覆盖日期更晚的有效估值。未知估值显示“未估值”，不按 0 处理。

## 5.4 四类变化不能混名

- **收入/支出**：消费与收入分析使用，不直接等于净资产变化。
- **现金流入/流出**：账户发生额，包含转账、贷款本金、资产出售等非收支事件。
- **估值变化**：只改变存量价值，不进入普通收入、支出或预算。
- **口径/数据修正**：校准、补录、迁移、计入范围变化；必须单独标原因，不包装成经济收益或损失。

净资产变化可以由现金流、估值变化和口径修正共同造成。资产趋势若不能解释变化来源，只能标为“估算趋势”，不能标为收益曲线。

同币种转账只有在两端都属于同一净资产 scope 时才对净资产为 0；计入账户与不计入/范围外账户之间的转账会改变“已报告净资产”，但必须解释为范围内外资金移动，不是收入、消费或收益。

## 6. 预算规则模型（2026-09-30 用户定稿，替换原「预算 V2.1」）

> 原 V2.1 的本周期/自然月/自然周/自定义窗口、分类额度、固定支出预留、调整本周期（override）、专项追踪、月起始日，**全部停用**。旧数据留在库里不删、不再参与计算和显示（见 6.12）。本节之外凡是和本节冲突的预算描述（§0.3、§12.1、§13.1、§14 D12 等），以本节为准。

### 6.1 一句话

预算 = 给每一天定一个金额。一个月的预算就是这个月每天的金额加起来。用户只和「规则」打交道，页面只按自然月看。

### 6.2 三种设置

| 设置 | 用户填什么 | 说明 |
|---|---|---|
| 日常预算（一直有效） | 金额（整数元）+ 单位：每天 / 每周 / 每月 / 每年 | 可以有多条，按新建先后接力（6.4） |
| 特别安排（选日期） | 名称（可空）、金额 + 单位、开始日–结束日、钱从哪来：**从月预算里匀**（默认）/ **额外多给** | 排在日常预算前面（6.5） |
| 月底结余（每个账本一个） | 每月重新开始（默认）/ 省下的留给下个月 / 多退少补 | 6.6 |

颜色自动分配，不让用户选。日常预算不画色条；特别安排按新建顺序轮流取蓝、紫、粉、青、灰蓝。不用绿（只给预算健康）、金（收入）、橙（超支）。

### 6.3 金额拆到每一天

- 自然周是周一到周日；自然月、自然年按日历；闰年 366 天。
- 日常预算：每条规则按它自己单位的**整个自然周期**拆：每天 = 金额；每周 = 金额 ÷ 7；每月 = 金额 ÷ 当月天数；每年 = 金额 ÷ 当年天数。只精确到元，除不尽的零头按 1 元一份从这个周期的第一天起往后分，所以整周 / 整月 / 整年加起来**正好**等于金额。规则只覆盖周期的一部分时，就取那几天各自分到的数。
- 特别安排：先算这段日期一共多少钱，再平均分给这几天（零头同样从第一天起分）。一共多少 = 对每一天取「金额 ÷ 该单位的自然周期天数」再加总，四舍五入到元。例：每周 ¥2,000、10/1–10/7 → ¥2,000；每周 ¥1,500、10/1–10/5 → ¥1,071；每天 ¥300、9/25–27 → ¥900。
- 所有预算金额都是整数元（库里仍按分存，保证是 100 的倍数）。

### 6.4 日常预算的接力

- 新建一条日常预算，**一律从新建那个月的 1 号开始生效**，不管单位是日、周还是月。之前的月份不受影响。
- 某一天由「开始日 ≤ 这天」的日常预算里**最后新建**的那条管。例：5 月建每月 ¥5,000，10 月再建每月 ¥6,000 → 5–9 月按 5,000，10 月起按 6,000。
- **改已有的一条**（金额或单位）：它管的所有日子全部按新值重算，包括过去的月份。保存前提示「X月以来的每个月都会按新金额重新计算」。
- **删一条**：它管的日子交还给它之前的那条；前面没有就没有日常预算。删之前确认。
- 规则列表里，被后来那条接走的旧规则显示成「5月–9月」，收进「已结束」。

### 6.5 特别安排

- 选了日期的规则永远优先于日常预算，不论谁先建。
- 两条特别安排日期重叠时，重叠的日子归**后新建**的那条；前一条只保留它剩下的日子，那几天分到的钱不变。修改一条特别安排不改变它的先后。
- **从月预算里匀（carve，默认）**：那几天的钱从管这几天的日常预算里拿，**日常预算那个周期的总额不变**，其余日子平均变少。
  - 以日常预算的「一条规则 × 它的一个自然周期」为单位来匀。月预算就在这个月里匀；周预算在这一周里匀；年预算在这一年里匀。
  - 算法：这个周期里「没被特别安排占用的日子」和「被『匀』的特别安排占用的日子」原来各自分到的日常金额加起来，减去这个周期里所有「匀」的特别安排的钱，余下的平均分给没被占用的日子（零头从第一天起分），最少到 0。「额外多给」的日子不参与。周期里没有「匀」时，各天保持原来的份额。
  - 例：9 月每月 ¥4,000，中秋 9/25–27 每天 ¥300 → 9 月还是 ¥4,000；中秋 3 天共 ¥900；其余 27 天共 ¥3,100，22 天 ¥115、5 天 ¥114。
  - 例：10 月每月 ¥8,000，国庆 10/1–7 每周 ¥2,000 → 10 月还是 ¥8,000；国庆 5 天 ¥286、2 天 ¥285；其余 24 天每天 ¥250。
- **额外多给（extra）**：那几天 = 原本的日常金额 + 特别安排分到的钱，月总额变大。例：上面国庆选「额外」→ 10 月 ¥10,000。
- 那几天没有日常预算时，只能选「额外多给」，那几天的预算就是特别安排的钱。
- 保存时要拦下的情况：
  - 「匀」的钱比它所在的日常周期还多（其余日子会分不到钱）→ 提示「比 X月整月预算还多，要改成额外多给吗？」，不允许按「匀」保存。
  - 跨月的「匀」按天拆开，各月从各月的预算里匀；每个月都要单独满足上一条。
  - 事后改日常预算导致「匀」超了，计算照常，其余日子取 0，不报错。
- 保存前的预览写明：这段一共多少、每天约多少、这个月总额、其余日子每天约多少，以及会盖掉哪条特别安排的哪几天。
- 月中才加的「匀」，这个月其余日子（包括已过去的）都会重算，月总额不变。

### 6.6 月底结余

- 每个账本一个设置，三选一：
  - **每月重新开始**（默认）：上个月省下或超出都不影响这个月。
  - **省下的留给下个月**：上月结果 > 0 才带过来，≤ 0 按 0。
  - **多退少补**：上月结果正负都带过来。
- 上月结果 = 上月实际总额 − 上月已花；实际总额 = 每天预算之和 + 带进来的结余。所以会连着滚。
- 从打开（或切换、关闭）的那个月起生效：这个月按新设置取上个月的结果，更早的月份不变。库里按「从哪个月起用哪种」记录每次切换。
- 带进来的结余只加在这个月的实际总额上，不改每天的日历预算（日历和某一天详情里看的仍是规则算出的那天金额），「今天约」通过剩余金额自然变多或变少。
- 带进来的超支比这个月总额还多：还能花显示 ¥0，提示「X月超出的还有 ¥Y 没扣完，这个月先省着点」；这个月的结果照常为负，继续滚到下个月。
- 结转一律按自然月算，与日常预算的单位无关；「额外多给」算在当月总额里一起结转。

### 6.7 每天、每月、今天

- 一个月的预算 = 这个月每天预算之和；实际总额 = 预算 + 带进来的结余。
- 已花 = 这个月里**有预算的日子**的计入预算支出。没有任何规则覆盖的日子，支出不算、日历上也不标颜色。
- 还能花 = 实际总额 − 已花，显示时向下取整到元，负数不显示，改写「X月超出 ¥Y」。
- 今天约（每天早上定一次，白天只做减法）：
  - 今天的额度 = 今天开始时的剩余（实际总额 − 今天之前已花）× 今天的日历预算 ÷ 今天到月底各天日历预算之和。剩余 ≤ 0 或后面各天都是 0 时，额度为 0。
  - 今天的额度向下取整到元；今天还能花 = 今天的额度 − 今天已花；< 0 时显示「今天多花了 ¥X」，多花的第二天起自然摊到后面的日子。
- 剩几天 = 今天到月底，包含今天。
- 节奏：已花和「按日历预算到昨天应花」比。少于或等于 → 「比计划少花 ¥X · 节奏不错」（健康绿）；多于 → 「比计划多花 ¥X」（橙）；剩余不到实际总额 10% → 「只剩 ¥X 啦」。
- 计入预算的支出沿用现在的口径：只算支出家族净额 > 0（退款冲原单）；「不计入预算」、转账、收入不算；日期晚于今天的要等到那天才算；非 CNY 照旧排除并提示笔数。
- 账本范围：每个账本（含总账本）有自己的规则和结余设置；总账本的已花汇总所有「计入总账本」的账本。子账本的预算不会加到总账本上。

### 6.8 预算页

从上到下：

1. 顶栏：‹ 返回、「预算」、账本切换、＋ 新增规则。去掉「查看账本」说明行和本周期/月/周/自定义标签。
2. 大数字卡：「X月还能花 ¥N」；「今天约 ¥N · 还剩 N 天」；进度条（深色 = 已花，细竖线 = 按计划到今天该花到哪）；「已花 ¥N / X月预算 ¥N」；节奏一句话。开了结转时多一行「X月预算 ¥A + Y月省下 ¥B」或「Y月超出的 ¥B 从这个月扣」。
   - 过去的月份：「8月顺利收官，省下 ¥340」/「8月超出 ¥120」（开了结转再加「已留给 9 月」）。
   - 以后的月份：只显示那个月的预算和规则。
   - 没有规则：「给这个月定个小目标吧」+ 近 3 个自然月平均支出（取整到百）的建议 +「设个预算」。
3. 日历：周一开头，‹ › 翻月。过去的日子写当天已花（整数元，0 不写），超当天日历预算显示橙色；今天实心圆 +「今天」；以后留空；特别安排画彩色条和名字。点某一天弹「某一天详情」。
4. 规则列表：日常预算和特别安排按新建时间倒序，每行颜色点、名字（没填叫「日常」）、金额 + 单位、生效时间（「10月起」「9月25日–27日」「即将开始」）；「已结束」折叠。底部小字「日期重叠时，以后加的特别安排为准」。
5. 「月底结余 · 每月重新开始 ›」一行，点开三选一，每项附按用户自己数字算的例子。

### 6.9 新增 / 编辑规则、某一天详情

- 新增 / 编辑（底部弹层）：名称、预算（整数）、每天/每周/每月/每年、时间（一直有效 / 选日期，选日期用内嵌小日历点起止）、选日期时多一行「钱从哪来：从 X月预算里匀 / 额外多给」、预览、保存。编辑时右上角可删除。第一次新建时预算栏预填近 3 月平均建议。
- 某一天详情（点日历的某天，底部弹层）：标题日期 + 星期；这天归哪条规则管；三格：当天预算 / 花了 / 超了（没超不显示第三格）；「多花的会从后面的日子里自动匀出来，不用管它」；当天账单列表（沿用按天分组账单的行样式），点一笔进编辑。以后的日子只有预算和规则。

### 6.10 所有用到预算的地方用同一个算法

主页预算卡（月预算剩余 / 已超、今日可用、剩 N 天）、桌面小组件、统计页预算环、记账页顶部预算提示、喵洞察、AI 聊天里的预算上下文，全部调用同一个引擎函数（输入：账本、年月、今天；输出：6.7 的各个数）。主页卡片样式不变，只换数据来源。任何两处同一个数必须一致到元。

### 6.12 旧数据迁移（🔒，动手前单独经用户确认）

- 每个账本：取当前生效的 V2 日常主计划（`role = primary`、状态有效）的当前版本金额，建一条 base 规则（每月计划 → `month`，每周计划 → `week`），start_date 取该计划开始那个月的 1 号。没有 V2 主计划时，才用旧 `budget_periods` 里生效的每月预算；旧预算 `book_id` 为空（「全部账本」）时，给每个没有 V2 主计划的账本各建一条同额 base 规则，保证升级前后看到的一样（2026-09-30 用户定）。
- 旧的 `budget_plans` / `budget_plan_revisions` / `budget_cycle_overrides` / `budget_fixed_commitment_occurrences` / `budget_periods` / `budget` 表不删、不改，只是不再读。专项（`role = special`）不迁移。
- 迁移只在升级到 v50 时跑一次，已有 base 规则的账本跳过；升级前照旧自动备份。恢复旧备份后再次升级，同样按这条规则迁移。

### 6.13 这一版不做

## 7.4 余额校准

```text

系统计算余额        ¥2,680.35
实际余额            [¥ 2,712.80]
差额                 +¥32.45
核对时点            现在 · 2026/7/12 10:30
                    或：历史日终 · 2026/7/1
说明（可选）        微信实际余额
```

保存后写一条独立、可撤销的绝对余额锚点事件：

- `target_balance` 是该生效时点的绝对余额锚点；界面差额只用于解释“保存时系统值和实际值差多少”，不能成为后续累计真相。
- 查询某时点余额时，找到该时点之前最后一个未撤销锚点，从它的 `target_balance` 起只累计锚点之后的实际结算流水；无锚点时才从期初余额和精确期初时点计算。
- 默认“现在”使用保存时精确时间；之后发生的同日流水继续累计。只有用户主动选择“历史日终”时才使用所选日期当地日终，UI 必须明确写“该日结束时余额”，不能让一个只有日期的字段暗中采用日终语义。
- 同一时点多事件用 `effective_ms + sequence/id` 固定排序，不能依赖数据库偶然返回顺序。
- 后补锚点之前的历史账单不改变锚点之后的余额；后补锚点之后的流水正常影响余额。
- 不进入收入、支出、预算和消费统计。
- 校准也不属于真实现金流；资产变化解释中单列“余额校准/数据修正”。
- 撤销追加一条引用原锚点的撤销事件，使原锚点失效并回退上一有效锚点重算；不能写一个固定反向 delta。
- 单个账户校准只让该账户成为“已核对”，不能自动把全局净资产标为完整核对；保存后使受影响的计算快照失效并重算。
- MoneyWiz 把差额造为特殊收入/支出；肥喵不采用这种做法，避免统计污染。

## 7.6 指标口径

先锁定四个互不混用的基数：

```text
购置毛额     = source=transaction_allocations
               ? sum(allocated_gross)
               : manual_gross
购置退款     = source=transaction_allocations
               ? sum(allocated_refund)
               : manual_refund
净购置成本   = 购置毛额 - 购置退款/折让 + 未重复计入的购置费用
累计持有投入 = 净购置成本 + 维护/保险/配件等已关联净支出
可变现净估值 = max(0, 当前预计出售收入 - 预计出售费用)
实际净出售收入 = 实际出售价 - 实际出售费用
最终净成本   = 累计持有投入 - 实际净出售收入
```

购置退款只在“净购置成本”中扣一次；已经使用账单退款后净额作为购价时，不得在最终公式再次减退款。维护投入正常进入消费统计，但不自动抬高可变现估值。

金额约束：`manual_gross >= 0`、`0 <= manual_refund <= manual_gross`、购置费/维护/保险/配件金额非负；交易分配使用第 7.8 节逐条和合计约束。异常负值进入 conflict，不参与累计成本。

预计处置费高于售价时，物品资产估值下限为 0，潜在费用只作说明；只有形成真实支付义务才写账户流出或负债。实际净出售收入允许为负（例如付费报废），此时会提高最终净成本，但不能把负估值塞进“总资产”桶。

`实际持有天数 = max(1, 购买地本地自然日到结束日本地自然日的闭区间天数)`；持有中结束日取今天，已终止取经济终止事件日期。购买当天出售/退货也为 1 天，不能除以 0；跨时区不使用毫秒数除以 24 小时。购买日未知或结束早于购买日时，日均指标 unavailable 并进入待修正。

### 持有中

```text
日均持有投入 = 累计持有投入 / 实际持有天数
保值率       = 当前可变现净估值 / 净购置成本
日均价值变化 = (当前可变现净估值 - 净购置成本) / 实际持有天数
```

- 列表主指标沿用用户更易懂的“日均持有花费”，指标说明明确其计算值是日均持有投入；不叫“真实成本”“真实折旧”“使用价值”或“利用率”。
- 这个数会随时间自然下降，不代表使用更多或经济收益增加。系统不得只因时间流逝触发“更值了”庆祝；可搭配用户主动记录的最近使用、常用/闲置状态解释。
- 保值率和日均价值变化只有在存在有效可变现净估值时显示，并标估值日期/来源。
- `净购置成本 <= 0`、估值未知或币种不可折算时，保值率为“不可计算”，不能显示 `0%`。
- 某时点已有未撤销出售/退货/报废/丢失/赠送终止事件时，终止状态优先，价值按处置规则归零；生效日在终止之后的普通估值不再生效并进入冲突提示，不能把资产复活。撤销终止后才重新解析这些估值。
- 普通用户不需要每天估值。

### 已出售

```text
最终净成本     = 累计持有投入 - 实际净出售收入
最终日均净成本 = 最终净成本 / 实际持有天数
```

出售之后才有真正实现的退出成本。最终净成本小于 0 时，UI 显示“实现收益 ¥X”，不显示让普通用户难以理解的负成本。

### 使用次数

- 首版不要求逐次记录。
- 第二阶段由用户为特定物品主动开启。
- 开启后提供详情和物品卡快捷 `+1`，并支持撤销。
- 未开启时只使用“常用 / 偶尔 / 闲置”状态，不凭持有时长猜利用率。

## 7.8 新增物品

肥喵最有价值的差异化不是复制 AI 抠图，而是复用已经记过的账单。

### 路径 A：从账单加入，主路径

入口：账单更多操作 -> `加入我的物品`。

自动带入：

- 名称/商品说明。
- 金额和退款后净额。
- 购买日期。
- 所属账本和付款账户。
- 原账单图片。

用户只需确认物品分类、状态和可选照片。目标是两步完成，不重填完整表单。

账单关联约束：

- 关联对象保存 `allocated_gross_cents` 和 `allocated_refund_cents`，物品成本来自分配额，不直接重复读取整张订单。
- 同一账单可拆给多个物品，但必须同时满足：每条 `0 <= allocated_refund <= allocated_gross`、`sum(allocated_gross) <= order_gross`、`sum(allocated_refund) <= valid_order_refunds`，因此 `sum(allocated_net) <= order_net`。只校验净额不够，因为毛额和退款额可能分别超分；同一物品与同一账单的重复关联必须拦截。
- 未分配毛额/退款允许存在，但页面显示“尚有 ¥X 未分配”；退款新增后若打破约束，进入待确认，不静默按比例改写历史物品成本。
- 关联物品保存 `cost_quality=exact / partial / pending_refund_allocation / manual_unverified`。存在未分配退款时，日均只显示“按已知成本”并带待分配提示，保值率和最终成本降级为 unavailable；确认分配后恢复精确指标。
- 一件物品可关联多笔分期/尾款账单，各笔分配额求和形成购置成本；分期还款本金本身不能再次形成物品成本。
- 首版一件物品的购置、退款、附加支出和出售按物品 `currency_code` 关联同币种事件。存在异币事件且无带来源汇率时按原币分项展示，累计投入、保值率和最终净成本标 unavailable，不直接相加。
- 一账一物时默认自动分配全额；一账多物、部分退款无法唯一分配时必须让用户确认，不能按物品数量静默平均。
- 原账单被软删除后保留关联审计和已分配金额，物品不消失；恢复或重新关联时防止重复入账。

### 路径 B：新增物品后选择已有账单

从物品页 `+` 进入，先选“从最近账单加入”，展示最近耐用品支出并支持搜索。仍调用同一关联命令。

### 路径 C：手动补录

必填只有名称；金额和日期按来源场景要求。更多资料折叠。历史已有物品不得生成账户支出。填写成本时保存 `acquisition_cost_source=manual`；以后补关联真实账单必须让用户选择“用账单分配替换手动成本”并核对差异，不能把同一笔 1,000 元手动成本和 1,000 元账单再次相加。

### 路径 D：拍照 / AI 抠图

第二阶段增强。拍照和抠图帮助识别及陈列，但跳过后也能保存，不能成为数据录入阻塞点。

## 7.9 照片与凭证的完整闭环

当前 `photo_path` / `invoice_path` 只是路径字符串，UI 仍让用户手输路径，完整备份也没有打包资产照片。V2.1 不允许把它包装成已完成的照片能力。

真实闭环必须同时包含：

1. 相机/相册选图。
2. 复制到 App 受管 `asset_media/`，不能长期依赖外部临时路径。
3. 列表缩略图和详情原图展示。
4. 删除/替换时清理孤儿文件。
5. 完整备份 package v2 打包资产媒体并恢复重映射。
6. JSON 当前账本导出继续保持当前 scope 合同，不顺手改成全库。

首版可以继续复用单封面图和单凭证字段；多附件表放第二阶段。

## 7.10 生命周期

生命周期和展示可见性是两个独立维度：

- `economic_status`：owned / sold / returned / scrapped / lost / gifted。它决定是否仍拥有价值、是否允许处置和如何进入净资产。
- `visibility_status`：active / archived。它只决定默认列表是否展示，不改变余额、估值、`include_in_net_worth` 或历史统计。

“归档”不是结束状态。持有中的物品可以归档后仍计入净资产；已出售物品也可以留在历史列表而不归档。现有把归档同时写成 `include_in_net_worth=0` 的实现必须在 A0 先修正，不能沿用到新 UI。

历史迁移边界：物品和权益不能套同一条猜测规则。

- 当前代码只允许仍持有的 active/idle 物品进入 archived，因此旧归档物品可迁为 `visibility=archived / economic_status=owned / usage_status=unknown / inclusion_quality=needs_review`。归档时已丢失原计入意图，迁移继续保留旧 `include_in_net_worth=false` 和迁移前合计，待用户确认后才改变计入范围。
- 当前权益的单一 status 允许 active、partial_recovered、recovered 或 lost 之后再被 archived，不能一律恢复为 active/owned。迁移先读取归档前最后一个未撤销经济事件和 recovery 台账：明确 lost 事件恢复 `lost`；完整收回链且 remaining=0 恢复 `recovered`；`0 < remaining < original` 且数据一致时恢复 `partial_recovered`；`remaining=original` 且无终止冲突时恢复 `active`。`remaining=0` 但无法区分收回/损失，或事件、金额互相冲突时，使用 `economic_status=unknown / inclusion_quality=needs_review`。
- 所有旧归档权益均先保持 `visibility=archived` 和迁移前 include/合计；取消归档以后只改 visibility，不能再根据 remaining 重新猜 economic status。

| 事件 | 账单/账户 | 物品 | 预算/统计 |
|---|---|---|---|
| 新购买 | 付款账户减少，保留普通支出 | 新建在用物品 | 购买支出正常进入预算 |
| 从旧账单加入 | 不新增流水 | 建物品并链接原账单 | 不重复计算 |
| 退款/退货 | 复用原订单附着退款 | 标记退货，价值归零 | 原订单净额减少 |
| 更新估值 | 不造流水 | 新估值事件 | 不进收入/支出/预算 |
| 维护/配件 | 普通支出 | 关联附加成本 | 正常进入预算 |
| 出售 | 收款账户增加，交易标资产变动 | 状态已出售、价值归零 | 不冒充普通工资/经营收入 |
| 报废/丢失/赠送 | 默认不造账户流水 | 终止状态、价值归零 | 估值损失不冒充消费支出 |
| 归档/取消归档 | 不改历史流水 | 只切换展示可见性 | 不改净资产、预算和历史报告 |

部分出售、套装拆分和多数量分批成本留后续，首版只允许整项处置。

## 8. 预算与资产的统一账务规则

这些规则必须先锁定，UI 才不会出现“看起来对、总数却错”的问题。

## 8.1 购买耐用品

示例：用银行卡 8,000 元买相机，初始可变现估值 7,600 元，并选择计入净资产。

```text
账户             -8,000
预算支出         +8,000
物品当前估值     +7,600
净资产变化         -400
```

购买仍是消费和预算支出；物品作为存量价值进入资产。不能因为“加入物品”就把购买从预算中排除。

若普通物品不计入净资产：账户仍减少 8,000，预算支出仍为 8,000，物品只在物品页记录，不抬高主净资产。

## 8.2 退款/退货

- 继续复用附着原单的交易家族，但补齐双日期：`attribution_date` 继承原订单消费归属日，`settled_at` 记录退款真实到账日。
- 退款继承原订单账本、币种和消费分类，但**不强制继承原付款账户**。退款事件自己的 `settlement_account_id` 表示真实到账账户，默认原账户且可改；报销到账常与付款账户不同，必须让用户确认收款账户。
- 消费、分类和预算使用 `attribution_date` 冲减原消费周期；账户余额与现金流使用 `settled_at` 在真实到账日增加。创建/更新时间只作审计，绝不替代这两个日期。
- 物品从原购买账单识别退款后，提示或自动进入“已退货”待确认状态。
- 退款减少原订单净支出；不能再造一笔独立普通收入。
- 部分退款只减少该物品的已分配净购置成本；当**该物品的有效已分配购置额被全额退回且用户确认已退货**时终止该物品。一张多物订单只退其中一件，也可以只终止对应物品；不能用“整张订单是否全退”替代物品边界。
- 原订单不计收支时，退款同样不进入收支和预算，但仍在到账日进入账户现金流。
- 全额退款后的净支出为 0；“支出笔数”“消费订单数”和“退款事件数”分别按统计标准定义，不能用同一个 count。

## 8.3 出售

示例：相机出售前估值 6,200 元，成交价 6,100 元，平台从款项中扣出售费 100 元，实际净到账 6,000 元。

```text
收款账户         +6,000
物品当前估值     -6,200
净资产变化         -200
普通收入统计          0
普通支出/预算          0
实际净出售收入   6,100 - 100 = 6,000
最终净成本       累计持有投入 - 实际净出售收入
```

出售入账可继续使用 `income + excluded=1` 的账户变动语义，但 UI 叫“资产出售”，不显示为工资或经营收入。出售费属于处置成本：若从款项中直接扣除，只保存净到账和费用拆分；若另行扣款，写独立 `asset_sale_fee` 账户移动，仍不进入普通消费支出和预算，避免与最终净成本重复。购置费若未包含在原订单金额中，则作为普通购置支出进入预算，并只在净购置成本中加一次。

## 8.4 维护、保养和配件

- 关联一笔普通支出。
- 正常进入预算和消费统计。
- 同时进入该物品的持有总成本。
- 不自动抬高当前估值；维修花 1,000 不代表二手价值增加 1,000。

## 8.5 折旧和估值

- 折旧/估值变化只改变存量价值和净资产。
- 不进入预算、收入、支出和消费分类。
- 自动线性折旧必须标“模型估算”，手工估值必须标日期。
- 市场报价未来若增加，必须保留来源、时间和失败状态。

## 8.6 负债还款

示例：本期还款 3,000 元，其中本金 2,700，利息 300。

```text
还款账户         -3,000
负债本金         -2,700
利息支出           +300
预算支出           +300
净资产变化         -300
```

本金是资产和负债同时减少，不是消费；利息和手续费才是支出。

## 8.7 存钱目标和债务目标

- 真实账户余额/负债余额决定实际进度。
- 预算只表达“本周期计划贡献多少”。
- 行情上涨、估值变化或余额校准不能伪装成预算贡献。
- 同一账户绑定多个存钱目标时，不能把完整账户余额重复算给每个目标。**首版锁定一个专用账户只能绑定一个 active 目标**，目标实际进度取该账户可用余额并随真实支出下降；多目标共享账户留到分配台账阶段。
- 账户余额只决定资金上限，目标进度取已分配金额；目标间调拨是分配变化，不是收入、支出或现金流。
- 贷款本金还款和储蓄转账不属于消费支出，但会占用流动现金。未来“安全可花现金”必须预留这些承诺，不能塞进消费预算后重复扣除。
- 心愿物品第二阶段可关联现有存钱目标；购买完成后转为物品并链接真实账单。

## 9. 当前代码可复用能力与缺口

## 9.1 可直接复用

### 资金

- 账户类型：现金、储蓄卡、信用卡、存款、投资、贷款、其他。
- 期初余额、机构、币种、是否计入净资产。
- 当前账户余额公式已经使用全局流水和退款净额，可复用聚合结构；历史余额因退款只有原订单日期，尚不能视为正确现金流趋势。
- 权益资产已有原始/剩余金额、到期日、部分收回、全部收回、损失、归档和撤销最近收回。
- 净资产快照表已有 `global + snapshot_date` 唯一约束和结构拆分，可作为 computed cache 的迁移基础，不能直接冒充 verified checkpoint。

### 物品

- 稳定 UUID、bookId、购买价、当前值、购买日、品牌型号、位置、保修。
- 状态：使用中、闲置、出售、报废、丢失、赠送、归档。
- 估值历史、事件、账单关联、线性折旧。
- 新购买可生成普通支出；从已有账单加入不会重复支出。
- 出售生成 excluded 账户变动，撤销出售事务化。

### 无需 DB 即可派生

- 持有天数。
- 在退款和账单分配正确的前提下，用净购置成本及累计持有投入派生日均持有投入。
- 在存在有效估值时，用可变现净估值和净购置成本派生保值率。
- 估值新鲜度必须按 valuation 的 `effective_ms` 和来源派生，不能取资产普通编辑的 `updated_ms`。

## 9.2 现有实现不能冒充完成的能力

- 实物详情写着报废/丢失/赠送应从详情操作，但当前 UI 实际没有这些入口。
- 报废、丢失、赠送没有完整撤销能力。
- 照片和发票只是字符串路径，未接真实选图和媒体备份。
- 账户没有 UUID、created/updated、期初日期和归档状态。
- 账户没有详情、校准和可信余额趋势。
- 交易只有一个业务日期；附着退款当前写回原订单日，可以算对消费净额，但不能同时算对退款到账月现金流和历史余额。
- 当前归档物品/权益会关闭 `include_in_net_worth`，把展示隐藏错误地变成净资产下降。
- 当前资产状态把 `archived` 与 sold/returned/scrapped 等经济状态混在同一枚举中，无法独立表达“仍持有但隐藏”。
- 物品账单关联没有成本分配额；一账多物、分期多账和部分退款会重复读取整单金额。
- 当前估值字段容易被普通更新覆盖；缺少“按估值生效日选最新有效记录”的唯一派生规则。
- 负债没有还款命令、详情时间线、本金/利息拆分和负债事件。
- 快照主要靠资产页手动按钮，普通记账不会自动写；表内也没有快照类型、原因、覆盖范围、币种完整度、计算版本和核对质量。
- 全局净资产使用全量物品/权益，但页面列表和详情数据按当前账本加载，导致顶部包含、列表找不到。

## 10. 推荐数据调整

## 10.1 先增加全局查询，不先改表

新增明确 API：

```text
globalActivePhysicalAssets
globalArchivedPhysicalAssets
globalActiveReceivables
globalArchivedReceivables
physicalAssetDetailById(id)
receivableDetailById(id)
assetEventsForObject(type, id)
assetValuationsFor(id)
```

不能只把列表从 `_physicalAssets` 换成 `_allPhysicalAssets`：当前事件、估值、关联账单和收回历史也随当前账本重载，详情查询必须一起脱离当前账本。

## 10.2 交易双日期和事件类型

现有 `transactions.date_ms` 保留为消费/收入/预算归属时间，并在领域层明确别名 `attribution_ms`；新增：

| 字段 | 含义 |
|---|---|
| settled_ms | 可空；账户真实扣款/到账时间 |
| settlement_quality | exact / user_confirmed / legacy_assumed / unknown |
| settlement_account_id | 本事件真实结算账户；普通交易可映射现有 account_id，退款/报销不强制等于原单账户 |
| settlement_account_quality | exact / user_confirmed / legacy_assumed / unknown；与日期质量分开 |
| event_type | expense / income / refund / reimbursement / transfer / asset_sale / principal_payment / interest 等 |
| refund_of | 附着的原订单；退款继承原单账本、币种和消费分类，不继承结算账户 |
| created_ms / updated_ms | 审计时间，不参与消费或现金流窗口 |

新退款写入时 `date_ms=原订单归属日`、`settled_ms=用户确认或本次记录的真实到账日`，并确认到账账户。普通 legacy 交易可暂以 `date_ms` 和现有账户迁移为 `legacy_assumed`；**现有附着退款只保存了原订单日，真实到账日已经丢失，绝不能从 `updated_ms` 或今天静默伪造**：迁移为 `settled_ms=null / settlement_quality=unknown`。旧商家退款的原账户只能标 `settlement_account_quality=legacy_assumed`；旧报销常转入工资卡，不能假定原付款账户，标 unknown 并进入待确认。

消费投影仍可按交易家族净额读取 `date_ms`。账户当前余额包含已经存在的未知日期退款金额，但历史现金流和跨该事件的历史余额结果必须标 `partial`；账户未知时分账户余额/现金流也标 partial。全局净值只有在候选账户属于相同 include scope 时可保持金额，否则同样 partial。用户确认日期和账户后才进入精确结算时间线。不能继续让一个净额投影同时服务两者。

## 10.3 `account_balance_checkpoints`

| 字段 | 含义 |
|---|---|
| id / uuid | 审计身份 |
| account_id | 账户 |
| effective_ms / sequence | 锚点生效时点与同刻稳定顺序 |
| knowledge_cutoff_ms | 创建锚点时系统已经知道哪些事件 |
| target_balance | 用户确认的实际余额 |
| calculated_before | 创建时系统计算值，仅审计展示 |
| delta_at_creation | `target - calculated_before`，仅审计展示，不参与以后计算 |
| reason | manual / liability_mode_migration 等 |
| note | 说明 |
| status | active / reversed |
| reversal_of | 撤销哪条锚点 |
| created_ms / updated_ms | 审计与同步 |

余额查询使用最后一个有效 `target_balance` 锚点；撤销只改变锚点有效链并触发重算。禁止把 `delta_at_creation` 永久累加。

legacy unknown settlement 与锚点需要额外覆盖表：

```text
account_checkpoint_covered_unknown_events
  checkpoint_id
  account_event_uuid
  PRIMARY KEY(checkpoint_id, account_event_uuid)
```

覆盖表只接收**到账账户已经确认且与 checkpoint.account_id 相同**、但到账日期 unknown 的事件。“现在核对”时，实际余额已经吸收该账户在 knowledge cutoff 前存在的 unknown-date 事件，这些 UUID 写入覆盖表，锚点后不能再次相加。历史日终锚点不能自动覆盖所有 unknown-date：用户需逐项确认事件在锚点前或后，只有确认在前者写入覆盖表；未确认则该锚点及跨越查询保持 partial。

到账账户仍 unknown 的旧报销不能被任意单账户 checkpoint 写入覆盖表，也不能默认塞回原付款账户。单账户核对可以把**该账户自锚点时点起的当前余额**确认为 target，但未知事件本身及其他候选账户仍保持 partial；必须先让用户确认目标账户，再按“现在已吸收”或历史锚点前/后规则处理 unknown date。未来如需一次核对多个候选账户，另建显式 multi-account reconciliation，不能复用单账户覆盖表猜分配。锚点创建后新录入的 unknown-date 事件同样使对应余额 partial，直到确认日期或再次做“现在核对”；新退款强制记录真实结算时间和账户，因此覆盖表主要服务 legacy 迁移。

## 10.4 `accounts` 补字段

- `uuid`
- `created_ms / updated_ms`
- `opening_balance_effective_ms / opening_balance_sequence`
- `opening_balance_quality`：exact / legacy_unknown；历史存量无法证明期初时点时不画伪趋势
- `status`：active / archived / legacy_hidden
- `archived_ms`
- `last_verified_ms`
- `verification_interval_days` 可选

旧 `is_deleted=1` 映射为 `legacy_hidden` 或继续墓碑隐藏，不能自动显示成可恢复归档。

## 10.5 资产经济状态、可见性与估值

物品/权益至少拆开：

| 字段 | 含义 |
|---|---|
| economic_status | owned / sold / returned / scrapped / lost / gifted；权益使用 active / partial_recovered / recovered / lost / unknown，unknown 仅用于迁移歧义 |
| usage_status | active / idle / unknown；与是否仍拥有分开 |
| visibility_status | active / archived，只控制默认列表 |
| include_in_net_worth | 是否进入合计，独立于归档；经济终止时按明确规则关闭 |
| inclusion_quality | confirmed / needs_review；旧归档记录因原意图丢失进入待确认 |
| acquisition_cost_source | transaction_allocations / manual，二者互斥 |
| manual_gross_cents / manual_refund_cents | 仅 manual 来源使用；后来改账单来源时被替换而非相加 |
| ended_ms | 经济终止时间，归档不写这里 |
| archived_ms | 展示归档时间 |

估值记录补齐：

```text
asset_valuations
  id / uuid / asset_type / asset_id
  effective_ms            // 估值针对的时点
  recorded_ms             // 实际录入时间
  amount / currency_code
  source                  // manual / model / market
  status / reversal_of
```

`current_value` 若继续保留，只能作为最新有效估值的派生缓存；真相是 `effective_ms` 最新的未撤销记录。补录旧估值不覆盖新估值，估值新鲜度也不读取资产普通 `updated_ms`。

估值 resolver 先判断 as-of 时点的 economic terminal event，再选择 valuation。终止优先；后续估值保留审计但标 `inactive_due_to_terminal`，撤销终止后可重新参与。

`purchase_price` 若继续保留，也只能是当前 acquisition source 的派生缓存。手动来源和交易分配来源不得同时贡献净购置成本。

## 10.6 物品媒体

第一阶段继续使用 `photo_path` / `invoice_path`，但值必须指向 App 受管媒体。完整备份升级为 package v2 并打包 `asset_media/`。

第二阶段若支持多图/多附件，再建：

```text
asset_media
  id / uuid
  asset_type / asset_id
  media_type       cover / receipt / warranty / other
  local_path
  sort_order
  created_ms / updated_ms
```

## 10.7 物品账单分配、附加支出与使用次数

`asset_transaction_links` 首阶段即补：

- `allocated_gross_cents`
- `allocated_refund_cents`
- `cost_quality`（也可由待分配状态派生并缓存）
- 唯一约束 `(asset_type, asset_id, transaction_id, link_type)`

同一原订单同时校验逐条 refund 不超过 gross、gross 分配合计不超过订单毛额、refund 分配合计不超过有效退款、net 分配合计不超过订单净额。未分配余额允许存在并明确展示；退款无法唯一映射时保存待确认分配，不静默平均。第二阶段继续扩展 `link_type`：

- maintenance
- accessory
- insurance
- other_cost

使用次数单独建事件表，支持 `count_delta` 和撤销，不把大量使用事件塞进当前资产事件枚举。

## 10.8 计算快照与可信检查点

增加统一 `_scheduleNetWorthSnapshot()` 维护 `computed_snapshot`：

- 普通交易增删改。
- 退款、转账。
- 账户和校准。
- 实物估值、折旧、出售、退货、状态。
- 权益收回/撤销。
- 负债变化。

同一天只 upsert 一条 global 计算快照；连续动作 debounce/coalesce。页面 build 不写库，快照失败不阻断主操作并在下次启动补齐。

每条计算快照至少保存 `as_of`、`cause_set`、`scope_version`、`calculation_version`、币种覆盖、缺失估值数和数据质量。它是缓存，可在补录旧流水、退款、估值或调整范围后从最早受影响时点失效并重算；历史日期快照必须计算历史日状态，禁止把今天状态写进过去日期。

`verified_checkpoint` 单独表达用户明确核对：

- 单账户校准只验证该账户，不能把全局净资产自动标为已确认。
- 全局检查点记录实际覆盖的账户、负债、权益、物品估值和币种；只有两次覆盖范围与口径一致时才显示“较上次完整核对”。
- 当前日尚未结束的自动结果标 `provisional`；口径变化、迁移和补录导致的变化单独解释，不冒充经济收益。

全局核对不能只存 coverage 标签，必须保存不可变证据：

```text
net_worth_verified_checkpoints
  id / uuid / as_of / knowledge_cutoff_ms
  scope_version / calculation_version
  currency_coverage_json
  total_assets / total_liabilities / net_worth
  status                 // active / superseded / revoked
  supersedes_id / created_ms

net_worth_verified_checkpoint_items
  checkpoint_id
  object_type / object_uuid
  confirmed_amount / currency_code
  value_effective_ms / value_source / quality
  PRIMARY KEY(checkpoint_id, object_type, object_uuid)
```

header 和 items 创建后不可原地重算。后补流水、删除对象或修改估值不改变旧 checkpoint；发现错误时新建 superseding checkpoint 或追加 revoked 状态。比较读取两份 checkpoint 当时保存的 totals/items，而不是拿当前 Repository 重新解释旧核对。

机器判定“完整核对”的必要条件：items 覆盖当时所有 `include_in_net_worth` 对象，且每个 as-of 存量余额/估值可确认；needs_review 的计入范围、无法折算的必需币种或尚未被锚点吸收的新 unknown movement 会使结果 partial。已被“现在余额”锚点吸收的 legacy unknown settlement 不再妨碍当前存量核对；待分配物品成本若当前估值已单独确认，也只作为 lineage warning，不阻止净资产完整核对。过期估值需明确接受其日期。两次比较要求 scope 政策、币种覆盖和 calculation_version 一致，且各自在 as-of 时覆盖当时全部应计对象；正常新开/关闭账户或买入/处置物品允许 UUID 集合变化，并作为变化来源解释。若是漏项或口径变化则不算直接涨跌率。`scope_version` 只因计入政策/include/权限范围改变而提升，不因正常对象新增或终止提升。

## 10.9 存钱目标资金分配

首版使用“一个专用账户只能绑定一个 active 目标”。未来开放多目标共享账户时再新增：

```text
goal_allocations
  id / uuid
  goal_id / account_id
  amount_cents / currency_code
  effective_ms
  status / reversal_of
  created_ms / updated_ms
```

保存时同币种 active allocations 合计不得超过账户可分配余额；Repository 在同一事务内校验。但账户余额随后仍可能因正常消费下降，因此还必须派生 `overallocated = max(0, allocationsTotal - max(0, accountBalance))`：不阻止记账、不静默削减或重排目标，所有相关目标暂停显示“已足额”，给出补入资金/降低分配入口。目标之间调拨只改分配，不造普通收支、账户现金流或净资产变化。

## 11. 负债迁移的硬风险与替代方案

## 11.1 为什么上一版不能直接做

当前公式中：

- 负债类型账户若余额 `B >= 0`，这个余额先进入总资产。
- 同时 active profile 的 `currentPrincipal=P` 又进入总负债。
- 迁移前是 `assets +B / liabilities +P / net B-P`。

若静默把同一个账户调成 `-P`，迁移后变为 `assets 0 / liabilities P / net -P`。总资产和净资产都会少 `B`。所以“直接改成负数，同时保证总资产、总负债、净资产逐分不变”在数学上不可能。

## 11.2 过渡模式

每个负债账户增加 `balance_mode`：

| 模式 | 行为 |
|---|---|
| `ledger` | 余额是唯一真相；正余额算资产、负余额算负债；profile 本金只作合同/上次核对资料 |
| `legacy_hybrid` | 完全保留当前算法；正余额算资产，active profile 本金另算负债 |

首版不再增加含糊的 `profile` 模式。未来若做独立债务对象，再单独设计。

## 11.3 可自动等价迁移

- `B < 0`：可直接标 ledger，不改数值。若 `abs(B) != P`，提示合同资料和账面欠款不同，但不改合计。
- `B = 0 且 P > 0`：用 absolute checkpoint 把余额校准到 `-P` 再标 ledger，迁移前后三项可保持一致。
- `P = 0` 或 profile 非 active：按现有计数逐账户验证后可标 ledger。
- `B > 0 且 P > 0`：一律保留 legacy_hybrid，不得静默改值。

## 11.4 歧义账户的用户辅助校准

`B > 0` 可能代表真实溢缴款/押金资产，也可能是信用额度、符号录反或过期档案。系统不能仅凭正数推荐拆出一个资产账户。先显示当前账面余额、档案本金和当前口径，并询问这个正数实际代表什么，再提供：

1. **保持现状**：继续 legacy_hybrid，无数值变化。
2. **这是我真实拥有的余额，同时另有欠款**：新建普通资产账户保留 `B`；原负债账户调到 `-P` 并切 ledger。总资产、总负债、净资产不变。
3. **这不是资产，只保留欠款**：原账户调到 `-P`，必须预览总资产和净资产会减少 `B`，用户明确确认。
4. **档案已过期**：输入实际欠款，预览后校准。
5. **这是可用额度或录反了**：不创建资产，先由用户确认正确欠款或余额语义，再预览迁移。

所有变化走 absolute checkpoint 和迁移事件，可撤销；不造普通收支。A5 必须是独立高风险批，不能与预算迁移或资产 UI 合包。

11. computed snapshot、部分账户核对和完整 verified checkpoint 使用不同文案；普通记账不能自动获得“完整核对”标签。
12. 补录旧流水或改变计入范围触发受影响历史快照重算，并把变化标为数据/口径修正，不在今天制造虚假收益。
13. 共享账本成员无法看到未明确共享的个人账户、房贷、权益和物品。
14. 首版同一专用账户绑定第二个 active 存钱目标时阻止保存；未来分配台账中，分配后账户消费导致余额不足时显示 overallocated，不拦截消费也不静默改目标。
15. 完整 verified checkpoint 创建后，补录流水、修改估值或删除对象不改变其 header/items；纠错生成 superseding/revoked 记录，比较仍可审计。

## 13.3 物品

1. 从已有账单加入不生成第二笔支出。
2. 新购买同时记账时，账户、预算、物品估值和净资产变化符合第 8 节公式。
3. 退款后原订单净额和已分配物品净购置成本一致，退款只扣一次；某物品的有效分配额全退且用户确认退货后只终止该物品，不要求多物订单整单全退。
4. 出售后账户增加、物品价值归零，普通收入统计不增加。
5. 持有天数、日均持有投入、保值率和最终净成本使用第 7.6 节统一基数。
6. 未核对估值明确显示估值日期、来源和过期状态；未知值不写成 0 或实时净值。
7. 照片选取后完整备份、恢复到新路径，列表和详情仍可见。
8. 数百件物品时使用懒加载和缩略图，无全量原图解码。
9. 报废、丢失、赠送、出售、退货均有经济事件和允许范围内的撤销；归档只切换可见性。
10. 普通消费品默认是否计入净资产符合类型推荐，但存量开关绝不静默改变。
11. 一张订单创建两个物品时，分配净额合计不得超过订单净额；重复关联被拦截。
12. 一件物品关联多笔分期时只累计被分配的购置款，不把分期还款本金重复当成本。
13. 先录新估值再补录旧估值，当前估值仍取生效日更晚的有效记录。
14. 窄屏或字体达到 130% 时物品网格改单列；200% 字体、无图和估值未知状态仍可完成处置。
15. 购买当天出售或退货时持有天数为 1，日均指标不除零；结束早于购买日进入待修正。
16. 手动补录成本 1,000 后关联同一笔 1,000 账单，净购置成本仍为 1,000，必须替换来源而非相加。
17. 新退款尚未分配到多物订单时，相关物品 costQuality 降级，保值率/最终成本不显示伪精确值。
18. 一件物品存在异币购置/维护/出售且无汇率时分币种展示，累计投入和最终成本 unavailable。
19. 先录 7/10 估值再补录 7/1 出售/退货时，终止事件优先，后续旧估值不能把资产复活；撤销终止后才重新解析估值。

## 13.4 校准、快照与负债

1. 校准后余额精确等于目标值，收入、支出、预算和分类统计不变。
2. 历史日期校准只影响该日及之后。
3. 校准后补录锚点之前的旧账，锚点之后余额保持不变；补录之后的流水正常累计。
4. 连续两个校准后撤销第二个，余额回退到第一个有效锚点重算；不靠固定反向 delta。
5. 同日流水、校准与撤销按明确 sequence 得到稳定结果。
6. 旧 deleted 账户不会重新出现在归档列表。
7. 负债迁移覆盖 `B<0 / B=0 / B>0` 与 `P=0 / P>0 / inactive` 矩阵。
8. 自动等价路径的总资产、总负债、净资产逐分不变。
9. `B>0` 先确认代表真实资产、额度还是录入错误；任何拆分或只留欠款路径先展示差异并由用户确认。
10. 等价迁移同日 computed snapshot 不产生虚假净值波动，也不自动生成 verified checkpoint。
11. 本金还款不进支出，利息/手续费进入支出和预算；两者都按结算日进入账户现金流。
12. 单账户校准只标该账户已核对；覆盖范围不足时全局只能显示部分核对。
13. 已知到账账户但 unknown-date 的 legacy 退款在“现在核对”后可由同账户 checkpoint 覆盖，当前余额不重复相加；到账账户 unknown 的旧报销不能被原付款账户或任意单账户 checkpoint 覆盖，先确认目标账户。
14. 上午 10:00 “现在核对”余额 100，下午 15:00 支出 20 后余额为 80；只有显式“历史日终”才使用所选日期日终锚点。

## 14. 推荐直接锁定的产品决策

| 编号 | 决策 | 推荐 |
|---|---|---|
| D1 | 资产总览是否跟随当前账本 | 固定全局；账本只作物品/权益筛选 |
| D2 | 资产页一级结构 | 总览 / 资金 / 物品 |
| D3 | 普通物品是否默认计入净资产 | 不强迫；存量保留，重大资产按类型推荐开启 |
| D4 | 物品主指标 | UI 叫日均持有花费，公式用累计持有投入/天；不等同利用率、收益或真实折旧，不因时间流逝单独庆祝 |
| D5 | 物品新增主路径 | 从已有账单两步加入；一账多物和多账一物必须保存分配额 |
| D6 | 次均成本 | 第二阶段、用户主动开启 |
| D7 | 账户差额 | 绝对 target_balance 锚点；差额只作创建时审计，不改期初、不造普通收支或真实现金流 |
| D8 | 负债歧义迁移 | 保留 legacy_hybrid，用户辅助校准，禁止静默改值 |
| D9 | 预算浏览 | 本周期 / 自然月 / 自然周 / 自定义；“月”永远是自然月 |
| D10 | 月计划起始日 | 默认 1 日，高级设置支持 2 至 28 日 |
| D11 | 调整预算默认生效 | 默认下一完整周期；本周期修改保存绝对周期总额，不拼接新旧日额 |
| D12 | 专项能力 | 文案叫“专项追踪”，不额外增加可花额度，不与主计划相加（2026-09-30 已停用：专项追踪删除，见 §6） |
| D13 | 证券行情/自动汇率 | 暂缓，先保留投资账户余额和原币数据 |
| D14 | AI 抠图 | 展示增强，不作为首版必经流程 |
| D15 | 退款日期 | 消费/预算归属原订单日，账户现金流归属真实到账日，必须双日期 |
| D16 | 归档 | 只改变可见性；经济终止和 include_in_net_worth 由独立状态/动作决定 |
| D17 | 快照可信度 | computed snapshot 可重算；verified checkpoint 必须明确核对并保存覆盖范围 |
| D18 | 未知与零 | 未知、部分可计算、过期、不可折算和真实 0 分开表达 |
| D19 | 存钱目标 | 首版一个专用账户只绑定一个 active 目标；未来分配台账必须处理余额下降后的 overallocated，禁止重复占用 |
| D20 | 统计合同 | 收支、预算、现金流、余额、净资产、笔数和比较统一服从 `07-统计口径标准.md` |

这些决策在 V2.1 中视为锁定。实施阶段无需再次反复询问；只有出现数据迁移无法等价、共享权限冲突或用户主动改变产品方向时才重新打开，A5 具体迁移 UI 和证券级能力仍需单独评审。
