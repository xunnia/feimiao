## 0. 一页流程

1. 确认工作树稳定，没有别人写到一半的代码 →
2. 同步版本号（§2）→
3. analyze + 全量 test + 发布规则测试（§4）→

5. `verify_release_apk.sh` 验包 →
6. 归档到 `ci-artifacts/releases/` 并记录 SHA256 →

## 1. 环境前提（都是真踩过的坑）

- **所有 `.sh` 只在 Git Bash 里跑。** PowerShell 里敲 `bash` 调到的是 WSL，处理不了 Windows 路径，`stat`、`sha256sum` 第一步就会挂。`repack_rollback_apk.ps1` 是例外，它是 PowerShell 脚本。
- Git Bash 里如果找不到 `awk`、`sed`、`sort`，先执行 `export PATH="/usr/bin:/mingw64/bin:$PATH"`（2026-09-10 实测需要）。
- Flutter SDK 在 `C:\src\flutter`（Git Bash 下是 `/c/src/flutter/bin/flutter`）。工作目录一律是 `C:\src\xunni-codex\android-app`。
- 如果 flutter 命令一直卡在启动锁上：先结束 dart 进程，再删除 `C:\src\flutter\bin\cache\lockfile`。
- Java：`export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"`。
- Android SDK Build-Tools 必须装好。验包脚本会依次在 `ANDROID_SDK_ROOT`、`ANDROID_HOME`、`%LOCALAPPDATA%\Android\Sdk` 下找最新的 `aapt`、`apksigner`、`zipalign`，也可以用 `AAPT_BIN`、`APKSIGNER_BIN`、`ZIPALIGN_BIN` 覆盖。缺任何一个都直接失败，不会跳过。
- 发布脚本里的验包也要 `JAVA_HOME`（apksigner 要用 java），跑 `publish_update.sh` 前同样先 export，否则会在验包这一步失败、什么都不上传（2026-09-30 实测）。
- 发布还需要 `node`（生成 version.json、跑 `release_gate.mjs`）以及 `curl`、`ssh`、`scp`。
- **Windows 本地跑全量测试要加 `--concurrency=1`**。Repository 测试走 sqflite_common_ffi，并发跑会假失败。CI 在 Linux 上用默认并发。
- 签名材料是 `android/key.properties` 和 `android/app/*.jks`，已被 `android-app/android/.gitignore` 忽略。凭据见本机安全存储，不入库。**不要读出、打印、复制到聊天或 VPS。**
- VPS 部署用的 SSH 密钥和 known_hosts：见本机安全存储，不入库。

## 2. 版本规则

| 版本 | 当前值 | 规则 |
|---|---|---|
| versionName | `1.309.0` | 每个发布批 minor +1 |
| versionCode | `324` | 就是 Android 安装序号，**只增不减**；还必须大于 `rollback.json` 里所有 `installVersionCode` |
| buildTag | `b1002-324` | `b<MMDD>-<versionCode>`，显示在 AI 记账页副标题，用来在真机上认包 |
| DB version | — | 只在 schema 或迁移变化时增加，和 APK 版本无关 |

需要同步改的文件（已 grep 确认，入库的只有前三个）：

| 文件 | 字段 |
|---|---|
| `pubspec.yaml` | `version: 1.309.0+324`（验包脚本和 CI 从这里读期望值） |
| `lib/core/app_version.dart` | `version = '1.309.0'`、`buildNumber = 324`（原生读取失败时，检查更新用它兜底） |
| `lib/build_info.dart` | `kBuildTag = 'b1002-324'` |
| `android/local.properties`（不入库） | `flutter.versionName=`、`flutter.versionCode=`（`flutter build` 通常会按 pubspec 回写；历史流程一直手工同步兜底，能不能省**待核实**） |

```bash
cd /c/src/xunni-codex/android-app
OLD_N=1.309.0; OLD_C=324; NEW_N=1.310.0; NEW_C=325; NEW_TAG=b1003-325   # 示例；按实际填写
sed -i "s/^version: $OLD_N+$OLD_C/version: $NEW_N+$NEW_C/" pubspec.yaml
sed -i "s/version = '$OLD_N'/version = '$NEW_N'/; s/buildNumber = $OLD_C;/buildNumber = $NEW_C;/" lib/core/app_version.dart
sed -i "s/kBuildTag = 'b[0-9-]*'/kBuildTag = '$NEW_TAG'/" lib/build_info.dart
sed -i "s/flutter.versionName=.*/flutter.versionName=$NEW_N/; s/flutter.versionCode=.*/flutter.versionCode=$NEW_C/" android/local.properties
grep -n "^version:" pubspec.yaml; grep -n "version =\|buildNumber" lib/core/app_version.dart; grep -n kBuildTag lib/build_info.dart
```

**回退包占用序号：** 做兼容回退包（§6）时会用掉一个安装序号，之后的正常版本必须跳过它继续往上。先例：305 给 293 的回退包用了，所以正常版从 304 直接跳到 306。VPS 的 `finalize.py` 在发布时会强制执行这条规则（`Version reserved by rollback`）。

## 5. 发布到 VPS（生产操作，必须有用户明确授权）

### 5.1 命令

```bash
cd /c/src/xunni-codex/android-app
bash ci/publish_update.sh \
  "C:\src\xunni-codex\ci-artifacts\releases\feimiao-codex-v<versionName>-<versionCode>.apk" \
  "<versionName>" "<versionCode>" "<给用户看的更新说明>"
```

- `publish_update.sh` 现在只是一层转发，实际执行 `publish_update_vps.sh`。更新说明不填时，默认是「修复问题并改进体验。」。
- 可以用 `FEIMIAO_SSH_HOST`、`FEIMIAO_SSH_KEY`、`FEIMIAO_KNOWN_HOSTS` 覆盖默认值（默认值写在脚本里）。凭据见本机安全存储，不入库。
- SSH 以 `BatchMode=yes`、`StrictHostKeyChecking=yes` 连接。**不要为了连上而关闭主机指纹校验。**

### 5.2 脚本做了什么（按执行顺序）

1. 在本机运行 `verify_release_apk.sh`，检查项和 §4 相同。
2. 用 node 计算 SHA256，生成候选 `version.json`：`versionName`、`versionCode`、`sha256`（小写）、`releaseId=v<code>-<sha前12位>`、`sizeBytes`、`notes`、`url`。
3. 拉取线上 `https://updates.xunni.dpdns.org/version.json`，交给 `release_gate.mjs` 判断：
   - versionCode 更高 → `advance`；
   - 四个字段（versionCode、versionName、sha256、releaseId）全部一致 → `idempotent`；
   - 降级、同 code 但身份不同、JSON 损坏、网络失败 → 直接失败。
4. `ssh` 创建 `/srv/feimiao-updates/incoming/<releaseId>/`，再用 `scp` 上传 `app.apk` 和 `version.json`。
5. `ssh` 执行 `python3 /srv/feimiao-updates/bin/finalize.py <releaseId>`（仓库里的源码副本是 `ci/feimiao_vps_finalize.py`）。它在 `publish.lock` 排他锁内依次完成：
   - 检查候选包大小和 SHA256；
   - 拒绝降级（`Cannot downgrade production`）和同 code 身份冲突（`Identity collision`）；
   - 新 code 必须大于 rollback 目录里所有的 installVersionCode；
   - `releases/` 里出现未知文件、未登记的 APK 或软链接时，立即停止；
   - 先放入 `releases/<rid>.apk` 和 `.json`，再切换 `current.apk` 软链接，最后原子写入 `version.json`；
   - 裁剪 `rollback.json`，删除不再保留的旧包，清空 incoming，打印 `{"published":…,"retained":[…],"apkCount":…}`。
6. 再次拉取公网 `version.json` 跑 `release_gate`。输出 `idempotent` 表示线上已经是这个包。

**保留策略**（以 `finalize.py` 为准）：保留当前版本，外加按 versionCode/installVersionCode 从高到低的另外 2 个包，**最多 3 个 APK**，已发布的专用回退包也算在内。包不够 3 个时不凑数。清理只在新版本已经切换成功之后进行。

**失败时怎么办：** 在 `version.json` 切换之前失败，线上仍是旧版本，修好原因后重跑同一条命令即可。如果已经切换成功，重跑会走 `idempotent` 分支（会重新上传一遍约 118 MB 的包）。incoming 里的残留不影响线上，同一个 releaseId 重跑会覆盖；需不需要手工清理**待核实**。**不要手改线上的 `version.json` 或 `rollback.json` 来绕过门禁。**

## 6. 回退

**线上出问题：** 生产环境不能降级，`release_gate` 和 `finalize.py` 都会拒绝。正确做法是 revert 或修复，再用**更高的 versionCode** 走完 §2 到 §5 的完整流程，也就是「向前修复」。

**用户想回到旧版本：** Android 普通安装器会拒绝 versionCode 更低的包（`INSTALL_FAILED_VERSION_DOWNGRADE`），签名一致也没用。所以 VPS 上保留的旧正常包**不能**直接覆盖安装。另外，安装成功也不代表旧代码能读新 DB。带迁移的版本回退，优先用升级前的备份恢复。

**兼容回退包规则**：

1. PowerShell：`ci\repack_rollback_apk.ps1 -InputApk <历史包> -OutputApk <输出> -SourceVersionCode <原code> -CurrentInstalledVersionCode <当前线上code> -InstallVersionCode <新序号>`。脚本会改写 manifest 里的 versionCode，做 16 KiB 对齐，用本机固定 release 证书重签，再用 aapt 核对包名和序号。新序号必须同时大于原 code 和当前安装序号，而且是全局递增的，会占用正常版本的序号（见 §2）。
2. 用 `verify_release_apk.sh <输出> <versionName> <新序号>` 核对证书指纹。
3. 用真实数据库 fixture 验证 `databaseVersion` 和迁移兼容性。验证不了的版本不能进入目录。
4. `rollback.json` 的条目：`versionName`、`sourceVersionCode`、`installVersionCode`、`url`（不可变的 HTTPS 地址）、`releaseId`、`sha256`、`sizeBytes`，可选 `databaseVersion`。VPS 的 `finalize.py` 要求每个条目都满足 `releaseId == v<code>-<sha前12位>`、sha256 是 64 位小写十六进制、`sizeBytes > 0`。这里的 code 在条目没有 `versionCode` 时取 `installVersionCode`。

⚠️ **VPS 上还没有回退包的发布工具。** `publish_rollback_apk.sh` 和 `publish_rollback_catalog.sh` 仍然写 Cloudflare KV（用 `npx wrangler`），**不能用于 VPS**。以后要新增回退包，必须先把这条链路适配到 VPS（签名、序号、DB 兼容门禁），并拿到用户授权。**不要手改线上 JSON。** 另外，`finalize.py` 每次发布都会把 `releaseId` 不在保留集合里的目录条目删掉，指向外部归档的条目会不会被误删，**待核实**。

**应用内：** 设置里的「历史版本」读取 `rollback.json`。只有 `installVersionCode` 高于当前实际安装序号的条目可以点。实际安装序号由原生 `PackageManager` 通过 channel `feimiao/update` 的 `installedVersionCode` 读取，失败时退回 `AppVersion.buildNumber`。下载复用 SHA-256 校验和 FileProvider 安装流程，安装前会提示先导出备份。当前目录为空，没有可选的历史版本。

## 7. GitHub CI 现在的角色

以 `.github/workflows/android-ci.yml` 为准：

- **触发：** push 到 `claude/**`、`codex/**`、`main`，并且改动了 `android-app/**` 或这个 workflow 本身；任意改动了这些路径的 PR；手动 `workflow_dispatch`。同一个 ref 有新 push 时，会取消正在跑的旧构建。
- **所有触发都执行：** `flutter create` 补脚手架 → `pub get` → 发布脚本 `bash -n` 语法检查和 `node --test` 规则测试 → 生成启动图标（并删掉 anydpi 自适应 XML）→ `analyze --no-fatal-infos --no-fatal-warnings` → `flutter test` → `flutter build apk --release`。这是编译和测试的闸门，**不产出可以发布的包**。
- **只有 push 到 `codex/feimiao-p0-fixes` 才会：** 用仓库 Secrets 配置固定签名（缺任何一个就失败）→ 验包 + 线上 version.json 门禁 → 上传 artifact → 覆盖 GitHub Release `android-latest`（prerelease，资产名是 `肥喵记账.apk`）。
- **CI 不会发布到 VPS，也不影响 App 的更新通道。** 另外，迁移到 `xunnia/feimiao` 以后，origin 上没有 `codex/feimiao-p0-fixes` 这个分支，签名和 Release 这几步目前实际上不会被触发。新仓库有没有配置签名 Secrets，**待核实**。workflow 的门禁仍然读旧域名 `updates.xunni9481.dpdns.org`，靠 307 跳转才能工作。

## 8. 已废弃的方式（不要再用）

- **GitHub Release `android-latest`**（早期的 `qingji.apk` 和 `肥喵记账.apk` 下载链接）：已经不是 App 的更新源，只剩上面 §7 那个基本不会触发的 CI 步骤。
- **Cloudflare Worker + KV 分片**（`wrangler kv`、24MB 分片、`apk:<rid>:manifest`、`retention_policy.mjs` 的「保留 2 版」）：2026-09 起由 VPS 取代。Worker 现在只负责旧域名的 307 跳转。KV 里的旧分片已经过时，**不能**切回去用。`retention_policy.mjs` 只剩测试还在 CI 里跑。普通发版不需要 `wrangler deploy`，修改 Worker 属于生产变更，需要用户单独授权。

## 9. 坑清单

| 坑 | 后果 | 对策 |
|---|---|---|
| PowerShell 里的 `bash` 其实是 WSL | 路径和 `stat` 第一步就挂 | 只在 Git Bash 里跑 `.sh` |
| Git Bash 里 PATH 不全 | `awk`/`sed` 找不到 | `export PATH="/usr/bin:/mingw64/bin:$PATH"` |
| `flutter test \| tail` | 测试退出码被吞，挂了照样出包 | 输出写文件，查 `$?` |
| Windows 上并发跑测试 | Repository/SQLite 测试假失败 | `--concurrency=1` |
| `sha256sum <Windows路径>` | 哈希带 `\` 前缀，污染 releaseId | 用 stdin；发布后 curl 复验 |
| `git add .` / `-A` | 把半成品、垃圾文件、APK 一起提交 | 只 add 指定路径，再 grep 暂存区 |
| 版本号只改了一两处 | 验包失败或客户端更新判断出错 | 按 §2 表格全部同步，再 grep 核对 |
| 普通版用了已被回退包占用的序号 | `finalize.py` 拒绝发布 | 跳过已占用的序号 |
| 打开 R8 或 shrink | ML Kit 被裁，截图识别崩溃 | 保持 `isMinifyEnabled=false` |
| keystore 用错 | 无法覆盖安装，用户数据有风险 | 验包检查固定 DN 和 SHA-256 |
| 为连上 VPS 关掉主机指纹校验 | 可能被中间人攻击 | 不许关；修 known_hosts |
| 手改线上 JSON | 绕过身份、降级和保留门禁 | 只通过脚本发布 |
| 以为保留的旧包能直接回退 | 被安装器拒绝，或旧代码读不了新 DB | 按 §6 做兼容包，或用备份恢复 |
| 以为 CI 绿了就是已发布 | 线上其实没变 | 发布只看 §5，结果以公网 `version.json` 为准 |
| 刚给完推送命令就开始改大文件 | 用户推送时把半成品一起提交，CI 挂 | 等用户推完再继续 |
| 没有真机就写「已验收」 | 状态失真 | 明确写「安装/冷启动未验收」 |
