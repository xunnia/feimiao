# Android 性能复盘与实测（2026-08-28）

## 结论

本轮只落地有明确收益、且不改变账务口径的缓存/重复工作削减；没有为了“看起来快”删除动画、模糊、猫或建议能力。

### 已落地

1. `AppRepository.recordsForBookView(bookId)`：按仓库数据版本缓存已经完成退款归并和分类映射的 `TransactionRecord`。方法仍返回可变副本，兼容原调用约定；写入流水、重载账本或分类时失效。
2. `visibleTransactionsForBookView(bookId)`：复用同一版本边界缓存列表，避免报告/聊天重复过滤全局流水。
3. 喵助手建议缓存：用 `AppRepository.dataRevision + repository identity + 预算状态 + 时段 + recordOnly` 判断缓存，不再每次打开都复制并按 id 排序全量账单；真正需要更新时仍走原 `SmartSuggestionEngine.build`。
4. 只读调用点改用 `allRecordsRef`，避免无意义的整列表浅复制；可变 `allRecords` API 保留。
5. AI 账本上下文复用仓库已经按日期降序维护的 `visibleTransactionsRef`，移除每次提问前对全量流水的再次排序。
6. 搜索页在筛选前把关键词归一化一次，并用 `dataRevision + 筛选条件` 跳过重复计算；仓库无关的 rebuild 不再重新扫描账单。
7. `MonthlyPaceCard` 将当前月与 6 个月历史的 13 次流水扫描合并为一次，保留整月与同期截止日两套金额。

## 候选测量（10,000 笔流水）

测量用例：`test/performance_candidate_test.dart`。单次机器抖动较大，因此记录范围而不是把毫秒数写成硬门槛。

| 路径 | 优化前 | 优化后 | 判断 |
| --- | ---: | ---: | --- |
| `recordsForBookView` ×30 | 3,795–4,971 ms | 99–163 ms | 落地，约减少 96%–98% |
| `visibleTransactionsForBookView` ×30 | 18–22 ms | 4–15 ms | 顺手落地，收益较小 |
| `allRecords` 浅复制 ×100 | 2–11 ms | 0–5 ms（引用读取为 0 ms） | 不再继续拆 API，收益不足以冒险 |
| 建议内容指纹 ×5 | 约 39–73 ms（稳定引用） | 生产路径改为 O(1) 版本判断 | 落地，避免打开喵助手反复排序 |
| `monthlySummary` ×50 | 39–136 ms | 仍在同一抖动范围 | 未改算法，当前不是主要瓶颈 |
| AI 上下文可见流水过滤 + 排序 ×1 / 保持顺序 ×10 | 单次排序约 1.3–1.5 s；重复 ×30 约 41.2–45.3 s | 保持既有顺序 ×10 约 9–12 ms | 落地，避免每次提问的全量 `O(n log n)` 排序 |
| 无日期关键词扫描 ×3 | 约 148 ms（约 49 ms/次） | 暂未改 | 低于排序/网络等待量级；先保留语义清晰的字段匹配，真机 profile 证明为热点后再上倒排索引 |
| 搜索页重复筛选 | 每次依赖变化都会重新扫描 | 相同 `dataRevision`/条件直接命中缓存 | 落地；不改变匹配结果 |
| `MonthlyPaceCard` 计算 ×5 | 旧 13 次扫描约 24–57 ms | 一次扫描约 8–28 ms | 落地，约减少 40%–67% |

已有 10k 压测仍通过：读取全量约 110–133 ms，月度统计约 10–13 ms，净资产拆分 0 ms；阈值保持原有 `<1s / <300ms / <200ms`。

## 正确性护栏

- 缓存按仓库 `dataRevision` 和显式账本/分类重载失效；不会把新流水、退款或分类改动留在旧上下文里。
- 性能用例验证缓存命中只构建一次、返回值仍可由调用方修改而不污染缓存、写入一笔新账后下一次读取会重新构建。
- 没有连接 Android 真机，帧时间、GPU 栅格和真实 IME 仍需用户设备使用体验确认；本地压测不能替代真机 jank 统计。
- 暂不把 `monthlySummary` 或关键词匹配改成复杂倒排索引：当前 10k 数据下月度统计约 10–13ms、关键词一次约 49ms，收益不足以抵消索引失效和语义变化风险；先消除重复筛选和重复归一化。
